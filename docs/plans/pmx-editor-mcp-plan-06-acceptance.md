# 実装計画書06: 結合・受入検証

先行するすべての実装計画書の成果物がそろった状態で、システム全体の結合を受入シナリオで検証し、
恒久文書の整合を最終確認して、実装フェーズを完了させる。本計画の結果はすべて進捗
ドキュメント(`docs/plans/pmx-editor-mcp-progress.md`)へ記録し、恒久的な受入シナリオは
検証手順書(`docs/conventions/verification.md`)へ移送する。

## 前提と裏取り

1. **前段の完了**
   - 出典: 進捗ドキュメントの完了記録
   - 確かめた結果: 本計画は先行するすべての計画の完了条件が満たされた状態で開始する(検査体系・
     ホスト・ブリッジ・全ツール・配布パッケージが存在し、各計画の実機確認が済んでいる)。
     未達の計画があれば本計画は開始できない——開始条件として progress の記録で確認する。
2. **検証環境**
   - 出典: 検証手順書の必要環境(05でPowerShell 7を追加)
   - 確かめた結果: 必要環境は検証手順書が正本であり、本計画は新しい環境要件を追加しない。
3. **受入の判定基準**
   - 出典: 能力台帳(提供全能力)とツール契約のシグネチャ単位ゲート・行単位の自動E2E検査
   - 確かめた結果: 個別ツールの行単位の合否は、ツール契約が整備した自動E2E検査(実機エディタに
     対して自動実行するもの)と、イベント行の payload 変換を網羅するxUnitテストが判定済みで
     ある(行ごとに何がどこまで確かめられるかはツール契約が定めた保証の境界による)。本計画の受入シナリオは「代表的な利用の流れが
     結合状態で成立すること」を確認するもので、行単位の網羅確認を置き換えない(照合ゲートと
     検査記録の網羅の再実行でその状態を検証する)。
   - ただし手動確認一覧へ登録された項目((a)UI操作の発火/(b)目視での判断・観察/
     (c)自動判定の基準が無い の3類型。種別は「行」と「契約」の2つ)は、ツール契約側では登録と実施先の特定までで、**実施と結果の
     記録は本計画が受け持つ**(類型(a)(b)は該当シナリオで、類型(c)は専用手順
     「自動判定の基準が無い項目の確認」で消化する)。

## 仕様書とコードの食い違い

本計画の作成時点ではプロダクトコードは未実装である(実行時には先行するすべての計画の成果物が

## 確定する設計値

### 受入シナリオ(検証手順書へ移送)

配布パッケージから導入した実機のPMXエディタ+Claude Codeで、次の9シナリオを順に実行
する。各シナリオは操作と期待結果の対で確定し、外部のモデルファイルを必要としない
(空モデルから開始して自足する)。

**本計画で人手が行う確認は、この9シナリオと、手動確認一覧
(`docs/specs/pmx-editor-mcp-manual-checks.json`)に登録された全項目(種別「行」・
種別「契約」の双方)だけである**。ツール個別の検査はツール契約が整備した自動E2E検査(実機エディタに
対して自動実行するもの)とxUnitテスト(イベント行の payload 変換)が担い、本計画では人手で
1ツールずつ確認しない。手動確認一覧の登録項目
((a)UI操作の発火・(b)目視での判断・観察)は下記シナリオ3・5・6で消化する(実施先の見出しは
手動確認一覧に登録済みで、本計画はそれに沿って実施する)。**(c)自動判定の基準が無い**は、
件数が変化の基準結果の生成で決まりシナリオの流れへ組み込めないため、受入シナリオではなく
**検証手順書の専用の見出し「自動判定の基準が無い項目の確認」で一括して消化する**
(この見出し名を実施先の確定値とし、各項目の手順と期待結果はツール契約が登録済みのものを
使う。受入シナリオの後に置く)。
**実施の結果は手動確認一覧の各項目へ記録し**、そこで確定した契約の内容(Undo粒度が
Update単位であること等)はツール仕様書へ記す。

1. **導入と初期化**: 開始前にアンインストール手順を実行し、**未導入状態(登録・
   `_plugin` のDLL・展開フォルダなし)を確立する**(先行する計画の完了時点では開発用登録や
   デプロイ済みDLLが残り得るため)。その上でREADMEテンプレート手順どおりの新規導入を
   行う。展開先は `%LOCALAPPDATA%\pmx-editor-mcp-acceptance\app` の**展開済み絶対パス**
   とする(シナリオ4の保存試験フォルダ `%TEMP%\pmx-editor-mcp-acceptance` と重複しない
   専用フォルダ)。期待: `ping` が "pong"。続けてPMX初期化ツールを `confirm: true` で
   実行し、**空モデルを確立する**(以後のシナリオはこの状態からの続きとして実行する)。
2. **読み取り**: モデル情報(名前・要素数)の取得と頂点一覧の取得。期待: 正常応答で
   頂点件数0(シナリオ1で初期化済みのため)。
3. **編集と取り消し**: 頂点を追加(位置 [0,0,0])→一覧で件数1を確認→位置を [1,2,3] へ
   更新→取得で位置を確認→エディタのUndoを1回(期待: 位置が [0,0,0] に戻る)→さらに
   Undoを1回(期待: 頂点が消え件数0)。**このシナリオが手動確認一覧の「Undo粒度が
   Update単位であること」の実施先である**(ツール契約側ではエディタのUndo操作を要するため登録のみ
   行っている)。結果は手動確認一覧の当該項目へ記録し、確定した内容(Undo粒度がUpdate単位で
   あること)はツール仕様書へ記す。
4. **保存の確認要求**: まず頂点件数が0であることを確認する(シナリオ3の合格を前提とする
   ため。0でなければシナリオ3へ戻る)。続けて `confirm` 無しの保存呼び出し。期待:
   `TOOL_CONFIRM_REQUIRED`。
   `confirm: true` で保存する。保存先は `%TEMP%\pmx-editor-mcp-acceptance\test.pmx` を
   **展開した絶対パス**(ツールへは展開済みパスを渡す。フォルダは事前に作成し、
   対象ファイルが存在しないことを確認——存在すれば削除——してから実行)。期待:
   ファイルが**新規に**作成される。
   シナリオ後にフォルダごと削除する。削除できない場合はエディタがファイルを保持している
   可能性があるため、その旨を記録し、**自動E2E検査がエディタを終了させた後**に削除する。
   (PMXファイルを開き直した後のコネクタ再利用の確認は、CAP-015 がパスを引数に取ることが
   一次資料で確定しているため自動E2E検査が行う。本シナリオでは扱わない。)
5. **ビュー**: まず**目視の判定材料を作る**——空モデルには何も描かれず視点の違いを判別
   できないため、頂点を3つ、非対称な位置([0,0,0]・[10,0,0]・[0,10,0])に追加する。
   次に**ビューポートのクライアント領域サイズを取得して記録する**(既定 `maxLongSide` の
   512に対して縮小が起きるかは実寸で決まるため、仮定せず実測する)。
   **視点を変える前に**ビューポート画像を1回取得しておく(目視の比較対象)。そのうえで視点の
   変更(カメラ位置 [0,20,-40]・注視点 [0,10,0])を行い、画像の取得を `maxLongSide` 既定(512)
   のまま1回、`maxLongSide: 256` を指定して1回行う。
   **画像を返すツールは3系統ある**(PMXビュー・変形ビュー・サブビューのクライアント画像取得。
   CAP-120・CAP-168・CAP-239)。手動確認一覧は画像を返すツールごとに1件を登録するので、
   **3系統すべてについて画像を取得し、内容が意図どおりかを目視する**(変形ビュー・サブビューは
   既定の `maxLongSide` で1回ずつでよい。表示されていない場合は該当ビューを表示してから
   実行する)。3系統を消化しないと完全一致のゲートを満たせない。期待: いずれも画像コンテンツが返り、
   **3頂点の配置が視点に応じた見え方で描かれている**(目視。変更前に取得した画像と見え方が
   変わっていることを判定材料にする)。縮小の `warnings`(元寸法と縮小後寸法)が付くかは、
   **記録した実寸の長辺と指定値の大小で決まる**——実寸の長辺が指定値を超える呼び出しにだけ
   付く。既定(512)・指定(256)のそれぞれについて、記録した実寸からどちらであるかを判定する。**既定の呼び出しでMCPの出力サイズ警告が表示されないこと**を観察して
   記録する(表示される場合は既定を下げる設計変更としてユーザーへ報告する)。`maxLongSide`
   の最大値2048の妥当性は、ビューポートをそれ以上に広げないと長辺2048の応答を作れないため
   本計画では確かめない(ツール仕様書が未検証として記録する)。
   **このシナリオが手動確認一覧の(b)目視での判断・観察の項目の実施先である。**
6. **イベント**: イベントコネクタを生成→Viewイベントリスナを作成(対象イベント:
   マウス左クリック)→エディタのビュー中央で左クリックを1回→`view_poll_events` で取得→
   リスナ解放→コネクタ解放。期待: `type` が対象イベントの識別子・`sourceHandle` が
   リスナのハンドルIDのイベントが1件以上取得できる(取得できない場合は不合格として
   操作位置・回数を記録する)。**同じ流れを UIモデルイベントリスナについても1回行う**:
   まず**クリックできる面を持つ最小のモデルを作る**——空モデルへ頂点3つ([0,0,0]・[10,0,0]・
   [0,10,0])と、その3頂点を参照する面1つ、材質1つを追加する(空モデルには描画される形状が
   無く、クリック位置を特定できないため)。これをUIモデルとして原点に1つ登録し(可視・
   最前面)、**その面がビュー中央に大きく映るよう視点を設定する**(カメラ位置 [0,0,-30]・
   注視点 [0,0,0])。→UIモデルイベントリスナを作成(対象イベント: MouseDown)→
   **ビュー中央を左クリック**→`view_poll_events` で取得→リスナ解放→UIモデル解放→
   PMX初期化で空モデルへ戻す。期待: `type` が
   UIモデルイベントリスナの MouseDown の識別子・`sourceHandle` がそのリスナのハンドルIDの
   イベントが1件以上取得できる。手動確認一覧はリスナ型ごとに1件を登録するので、
   View と UIモデルの両方を消化しないと完全一致のゲートを満たせない。
   **このシナリオが手動確認一覧の(a)UI操作の発火の項目の実施先である。**
7. **モーション**: VMDビルダでモーションを構築(ボーン名「センター」・フレーム0と30の
   2キーフレーム)→ハンドル解放。期待: 各操作が成功する。
8. **エラー系**: 次の3つを独立した操作列として実行する。
   (a)エディタが起動していなければ**エディタを起動し**、`ping` が "pong" を返すことを
   確認してから、範囲外インデックス(999999)の取得。期待: `TOOL_INDEX_OUT_OF_RANGE`。
   (b)エディタ未起動: 全エディタを終了した状態で、**接続履歴のない新しい
   Claude Codeセッション**から `ping` を呼び出す。期待: `BRIDGE_NO_EDITOR` の案内。
   (c)切断後の自動再接続(呼び出しツールはすべて `ping`): エディタを起動し `ping` を
   1回呼び出して接続を確立する(期待: "pong")→エディタを終了し `ping` を呼び出して
   切断を検出させる(期待: 03の分類により `BRIDGE_CONNECTION_LOST` または
   `BRIDGE_NO_EDITOR`)→エディタを再起動し、**追加の登録操作なしで** `ping` が "pong" を
   返すことを確認する(初回接続ではなく切断後の再接続経路の検証)。
9. **複数エディタ**: 2つ目のエディタを起動し、その現在モデルのモデル名を
   "acceptance-b" に設定しておく(1つ目は空のまま)。05の再登録手順で2つ目へ切り替え、
   モデル名の取得で "acceptance-b" が返ることを確認する(pingは両エディタで同じ応答に
   なるため判定に使わない)。**後処理**: 完了後、**2つ目のエディタを終了して単一エディタ
   状態へ戻した上で**、登録を通常のユーザースコープ登録(環境変数なし)へ戻し、
   セッションを再開してpingで確認する(PID固定の登録を利用者環境に残さない。複数起動の
   まま環境変数なしにすると自動発見が `BRIDGE_MULTIPLE_EDITORS` になるため、終了が先)。

シナリオで用いる具体のツール名・引数名・スキーマは、ツール仕様書の確定値を
用いる(上記の試験値——座標・保存先・視点・イベント種別・ボーン名・フレーム・範囲外
インデックス——は本計画で確定済み)。受入シナリオの正本は検証手順書へ移送し、ツール名
まで確定した形で記載する。

### 一括検証と文書整合(進捗ドキュメントへ記録)

- **全検査の一括実行**: 検証手順書の検査一覧(ビルド・整形・テスト・スクリプト構文・
  PowerShell構文・パッケージ生成・照合スクリプト・**自動E2E検査**・**MCP経路の2検査**
  (群単位の検索での発見可能性/宣言あり・なしのA/B対照による宣言の有効性))を
  すべて実行し、
  全合格を確認する。自動E2E検査は実機のエディタを起動した状態で1コマンド実行する
  (`scripts/e2e-tools.mjs`)。
- **長時間放置後のコネクタ再利用の確認**: `--soak` 経路を1回実行する(通常の一巡には
  含めていない)。所要8時間の待機を含み、通常の一巡は最終段でエディタを終了させるため、
  **他の検査と同じエディタインスタンスを共有せず、単独で先に完走させてから**上記の一括実行に
  進む。**エディタの起動・終了順序を次のとおり一意に定める**: (1)シナリオ9まで残っているエディタを
  終了する。
  (2)この検査専用にエディタを1つ起動する。(3)`--soak` を完走させる。(4)そのインスタンスを
  終了する。(5)一括実行のためにエディタを起動し直す。
- **網羅の再確認**: 照合ゲート(シグネチャ集合・能力対応表・スキーマ・型役割・
  除外一覧・危険操作三者一致)と、行単位・経路キーの検査記録の網羅(全行が**自動E2E合格・
  イベント行の payload 変換をxUnitで全行網羅・手動確認一覧への登録と記録**のいずれかで
  あること・未分類ゼロ・不合格ゼロ・イベントの代表発火の登録がリスナ型の集合と、画像の
  目視確認の登録が画像を返すツールの集合と、それぞれ完全一致すること)を再実行して
  確認する(ツール群実装の完了時からの乖離検出)。
- **文書整合の最終確認**: 対象は**Git追跡下の全恒久文書**(README と `docs/` 配下の
  全ファイル。除外はその時点で存在する計画書 `docs/plans/pmx-editor-mcp-plan-0*.md` のみで、
  **進捗ドキュメントは対象に含める**)とし、列挙漏れを防ぐ(IPC仕様書・型役割表等の
  機械可読正本・第三者ライセンス正本も自動的に対象へ含まれる)。検査は次の2つを確定する:
  (a)**計画書参照の残存検査**: 対象ファイル(進捗ドキュメントを含む)に対して文字列
  `pmx-editor-mcp-plan-0` のMarkdownリンクが無いことを検査する(進捗ドキュメントは
  計画書名をテキストとして記録してよいが、削除後に切れるリンクは張らない——この記録
  規則も進捗ドキュメントの冒頭に明記する。進捗以外の恒久文書は文字列ヒット0件を合格と
  する)。
  (b)**リンク切れ検査**: 対象Markdownファイルの相対パスリンクを抽出し、リンク先
  ファイルの存在を検証するスクリプト `scripts/check-doc-links.ps1`(本計画のステップで
  作成)を実行し、欠落0件を合格とする。
  両検査は実行コマンド・合格条件つきで検証手順書へ登録する。

## 実装ステップ

1. 開始条件を確認する(進捗ドキュメントで先行するすべての計画の完了記録を確認。未達があれば停止して
   ユーザーへ報告する)。**あわせて受入検証の実行識別子を作る**: RFC 4122 の
   8-4-4-4-12桁の16進表記(小文字)で1つ生成し、進捗ドキュメントの見出し
   「受入検証の実行識別子」の節の未実施の印を、その値だけの行へ置き換えて、手動確認一覧の全項目の
   `result` を `not_run`・`evidence` と `checkedAt` を空文字へ初期化する。以後の手動確認は
   結果を記録するときに `checkedAt` へこの識別子を書く。**この開始操作(生成・記録先・値の
   形式・初期化・一致検査の手順)は検証手順書へ移送し、そこを正本とする**(受入シナリオの前に
   置く。進捗ドキュメントは値を記録する場所であって手順の正本ではない。移送しないと、
   一致検査の基準値をいつ作るかが失われる)。`checkedAt` の形式そのものは手動確認一覧の
   スキーマが定める。
2. 受入シナリオ1〜9と**不合格時の開始状態復元規則**を、ツール仕様書の確定値でツール名・
   引数まで具体化し、検証手順書へ「受入シナリオ」として移送する(以後は検証手順書が
   正本)。**移送後の見出しは、各シナリオの太字の名称をそのまま用いる**(「導入と初期化」
   「読み取り」「編集と取り消し」「保存の確認要求」「ビュー」「イベント」「モーション」
   「エラー系」「複数エディタ」)。手動確認一覧が実施先として記録した見出しがこれと
   一致することを、移送の完了条件として検査する。
   **シナリオ番号は移送後も維持する**: 受入シナリオは検証手順書でも1〜9の順序付き項目として
   記載し、本文と復元規則の中の番号による相互参照(「シナリオ3へ戻る」「2〜5はPMX初期化で
   件数0へ戻す」等)はそのまま有効とする。実施先の記録に見出しを使うのは、計画書ごと
   消える番号を**文書をまたぐ識別子**にしないためであり、移送先の文書内で完結する相互参照を
   禁じるものではない。
   移送時に、**計画書番号による参照**(番号に助詞を続けた形)・
   **本計画への自己参照**(「本計画」「本計画書」)・**本計画の実装ステップへの参照**
   (「ステップN」「実装ステップ」。実装ステップは移送されない)は、恒久文書・登録済み検査
   への参照または自己完結した記述(READMEテンプレート=`docs/guides/package-readme.txt`、
   接続エラーの分類=アーキテクチャ仕様書のブリッジエラー契約、Undo粒度=ツール仕様書の
   検証記録、再登録手順=READMEテンプレートの該当節、出力画像の設計値と未検証の範囲=
   共通契約仕様書の出力画像の記述、手動確認一覧=
   `docs/specs/pmx-editor-mcp-manual-checks.json`、
   計画が定めた設計値への参照 = 「**IPC仕様書・アーキテクチャ仕様書・共通契約仕様書・
   ツール仕様書・導入手順書・READMEテンプレート**が定める設計値、**本手順書に登録された
   検査の実行コマンドと合格条件**、`docs/specs/` 配下の機械可読正本(能力対応表・型役割表・
   スキーマ正本・除外一覧・手動確認一覧・サンプル値表・想定質問文)が定める値、および
   **能力台帳**へ追記された危険操作・契約注記・非対応シグネチャの件数」。列挙する対象を
   散文の仕様書に限らないのは、設計値がそれ以外の恒久成果物にも置かれるためである。
   受入シナリオは配布パッケージから導入して実行するので、導入手順・パッケージ内容・
   再登録手順の修正も報告対象に入る)へ
   **置換し、移送後の本文にこれらの参照を残さない**(残存検査は完全ファイル名しか検出しない
   ため、この置換を移送の完了条件とする。検査文字列は計画書番号に加えて「本計画」・
   「ステップ」+数字・「実装ステップ」とする)。
3. 検証手順書の受入シナリオを実機で実行し、続けて**専用手順「自動判定の基準が無い項目の
   確認」を実行して、類型(c)の全項目の結果を手動確認一覧へ記録する**(この専用手順は受入
   シナリオの後に置き、開始状態の復元はPMX初期化で件数0へ戻すこととする)。結果を進捗
   ドキュメントへ記録する。不合格が
   あれば原因を修正し、**当該シナリオの開始状態を復元してから**再実行する(復元規則:
   シナリオ1はアンインストール手順を実行して未導入状態——登録・DLL・展開フォルダなし——
   へ戻す/2〜5はPMX初期化で件数0へ戻す(シナリオ4は前置のフォルダ・ファイル準備が冪等なので
   **シナリオ4の先頭から**再実行する)/6・7は残ハンドルを解放ツールで解放する/
   8は**全エディタを終了した状態**へ戻し、不合格になった操作列((a)(b)(c)のいずれか)を
   **その操作列の先頭から**再実行する((b)は新しいセッションで、(c)は先頭の「エディタを
   起動」から始まるため、全エディタ終了が3操作列共通の一意な開始状態になる)/9は2つ目のエディタを終了して
   単一エディタ状態へ戻し、登録を通常のユーザースコープ登録へ戻して**セッションを再開し
   pingで確認する**。復元後は当該シナリオから独立に再実行できる。
   修正が上記の恒久文書が定める設計値に影響する場合は設計変更としてユーザーへ報告する)。
4. `scripts/check-doc-links.ps1` を作成して文書整合の2検査を検証手順書へ登録し、
   文書整合の最終確認(リンク切れ・計画書参照の残存)を実行して結果を進捗ドキュメントへ
   記録する。
5. **最終状態で** `--soak` 経路を単独で実行し(所要8時間。他の検査と同じエディタ
   インスタンスを共有しない)、合否を進捗ドキュメントへ記録する。完走後に全検査の一括実行
   (文書整合の検査で追加したスクリプト・検査を含む)と網羅の再確認を行い、結果を進捗ドキュメントへ
   記録する。
6. 本計画書を削除候補としてユーザーへ報告する(削除はしない)。

## 完了条件

- 受入シナリオ1〜9がすべて合格し、進捗ドキュメントに記録されている。
- 全検査の一括実行(自動E2E検査・MCP経路の2検査を含む)と照合ゲート・検査記録の網羅の
  再確認が合格している。
- `--soak` 経路(長時間放置後のコネクタ再利用)が合格している。
- 手動確認一覧の**全項目**(種別「行」・種別「契約」の双方)が本計画の受入シナリオ、または
  類型(c)の専用手順「自動判定の基準が無い項目の確認」で消化され、
  結果が一覧の各項目へ記録されている(全項目の `result` が `pass`・`evidence` が非空・
  `checkedAt` が、受入検証の開始時に進捗ドキュメントへ記録した実行識別子と一致する)。
- 恒久文書の相互参照に切れが無く、実装計画書への参照が恒久文書に残っていない。
- 受入シナリオが検証手順書へ移送され、本計画書が削除候補として報告済みである。
