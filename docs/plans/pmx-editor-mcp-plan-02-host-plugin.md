# 実装計画書02: 常駐ホスト基盤

pmx-editor-mcp のエディタ側プラグインDLL(ホスト)の基盤を実装する。個別のMCPツールは
含めない(ツール実装は実装計画書04)。アーキテクチャとIPCプロトコルの設計値をここで確定し、
完了時にアーキテクチャ仕様書(`docs/specs/pmx-editor-mcp-architecture.md`)とIPC仕様書
(`docs/specs/pmx-editor-mcp-ipc.md`)へ移送する。

## 前提と裏取り

1. **プラグインの常駐とUIスレッド到達**
   - 出典: 能力台帳の「実機確認で確かめたこと」
   - 確かめた結果: 起動時実行オプションを持つIPEPlugin実装DLLを配布物の `_plugin` へ置くと
     Run がUIスレッド(スレッド1)で呼ばれ、そこで生成した不可視FormのInvokeにより
     ワーカースレッドからPEPlugin API呼び出しをUIスレッドへ委譲できた。名前付きパイプの
     サーバースレッドは常駐後も稼働し続けた。
2. **プラグインDLLはロード後もファイル差し替え可能**
   - 出典: 記載なし(配置運用の方式選定のための実測)
   - 確かめた結果: エディタ(PmxEditor_x64.exe)がロード中のプラグインDLLを、OSのごみ箱への
     移動で除去し、別名の新DLLを同フォルダへ配置する操作が成功した(ファイルロックで
     失敗しない)。ロード済みインスタンスは旧DLLのまま動き続け、新DLLは次回起動の
     インスタンスから有効になる。デプロイの上書きコピーはエディタ終了後の反映で運用する。
3. **net48で名前付きパイプのACL指定と同梱依存ゼロのJSON処理ができる**
   - 出典: 記載なし(実装方式の選定のための実測)
   - 確かめた結果: PipeSecurity(現在ユーザーのSIDにFullControlを許可するPipeAccessRuleを
     追加)付きの NamedPipeServerStream 生成コードと、System.Web.Extensions 参照による
     JavaScriptSerializer のシリアライズ呼び出しコードを、.NET Framework付属csc
     (4.8.9221.0)で System.dll・System.Core.dll・System.Web.Extensions.dll 参照のもと
     コンパイルし、エラー0で成立した。
4. **PEPlugin.dll の参照は各自の導入物から解決する**
   - 出典: PMXエディタ配布物の利用規約(パッケージ内データの再配布禁止)
   - 確かめた結果: 能力台帳の生成時に、配布物の `Lib/PEPlugin/PEPlugin.dll`
     (v0.0.8.9、.NET Framework 4.0ターゲット)を参照してリフレクション列挙が成立した。
5. **ブロック中の待受・読み取りを別スレッドのDisposeで解除できるのは、パイプを
   PipeOptions.Asynchronous で生成した場合に限る**
   - 出典: 記載なし(停止手順の解除機構を選定するための実測)
   - 確かめた結果: .NET Framework付属csc(4.8.9221.0)でビルドしたx64コンソールプログラム
     (CLR 4.0.30319.42000)で、NamedPipeServerStream の待受・読み取りをブロックさせた別スレッドを
     立て、さらに別のスレッドから Dispose した。**PipeOptions.None では、Dispose 自体は即座に
     返るのに WaitForConnection も接続後の Read も3秒経って戻らなかった**(同期I/Oの完了まで実際の
     ハンドルクローズが遅延されるため)。**PipeOptions.Asynchronous では、同期APIのまま
     WaitForConnection が2msで IOException となり、接続後の Read は0バイトを返して即座に戻った**
     (BeginWaitForConnection の場合は6msで ObjectDisposedException のコールバックが呼ばれた)。
     ダミークライアント接続による解除は PipeOptions.None でも成立し、待受は正常終了した。
6. **JavaScriptSerializer の文字数上限はシリアライズにも効き、その超過は循環参照と同じ例外型で
   返る**
   - 出典: 記載なし(出力上限超過の判定方式を選定するための実測)
   - 確かめた結果: .NET Framework付属csc(4.8.9221.0)でビルドしたx64コンソールプログラム
     (CLR 4.0.30319.42000。表示言語が日本語の環境)で、MaxJsonLength の既定は 2097152 だった。既定のまま300万文字の
     文字列を Serialize すると InvalidOperationException(「文字列の長さが maxJsonLength
     プロパティで設定されている値を超えています」)になり、MaxJsonLength を int.MaxValue に
     すると同じ入力が長さ3000002の本文へ成立した。循環参照を含むオブジェクトの Serialize も
     同じ InvalidOperationException(「循環参照が見つかりました」)で、**型では区別できず、
     いずれのメッセージも実行環境の言語に翻訳されるため文面でも区別できない**。MaxJsonLength を
     33554432 にした DeserializeObject は同じ300万文字の本文を解析できた。
7. **プラグインDLLは `_plugin` 直下と `_plugin\User` の両方から読み込まれる**
   - 出典: PMXエディタ配布物の `_plugin` にあるファイル
     `ユーザー作成プラグインはUserフォルダ内への配置を推奨.txt`(本文も同じ推奨と `user.path` に
     よる外部参照先の指定を挙げる。両方に置いた場合の挙動は記載がないため実測した)
   - 確かめた結果: 同じホストDLLを両方へ置いてエディタを起動すると、起動の記録が2回残り、
     メニュー項目も2つ現れた。パイプ名はプロセスIDで決まり、インスタンス数を1にしているため、
     2つ目の待受は `System.IO.IOException`(「すべてのパイプ インスタンスがビジーです」)で
     作れず、再試行を繰り返した。`User` だけに置くと起動の記録は1回で、handshake・pingとも
     期待どおり応答した。

## 確定する設計値

### プロジェクト構成(アーキテクチャ仕様書へ移送)

- `src/HostPlugin/PmxEditorMcp.HostPlugin.csproj`: net48クラスライブラリ。成果物名
  `PmxEditorMcp.dll`。プラットフォームは AnyCPU(実行対象は x64 版エディタ
  `PmxEditor_x64.exe` のプロセス)。`Microsoft.NETFramework.ReferenceAssemblies` 1.0.3 を参照。
- `tests/HostPlugin.Tests/PmxEditorMcp.HostPlugin.Tests.csproj`: net48・xUnit。
  UIスレッド・エディタ実機に依存しないロジック(プロトコル解析等)を対象。
- 両プロジェクトを `PmxEditorMcp.sln` に追加する。

### PEPlugin.dll のパス設定とデプロイ(アーキテクチャ仕様書へ移送)

- リポジトリ直下の Git管理外ファイル `local.props`(`.gitignore` へ追加)に、PMXエディタ
  導入ディレクトリを `PmxEditorDir` プロパティで定義する。追跡される
  `Directory.Build.props` が存在時のみImportし、未定義でホストをビルドした場合は
  「local.props に PmxEditorDir を定義せよ」という明示エラーで失敗させる。
- PEPlugin.dll 参照: `$(PmxEditorDir)\Lib\PEPlugin\PEPlugin.dll` をHintPathで参照
  (Private=false。配布物のDLLはコピーしない)。
- デプロイ: ホストcsprojの `Deploy` ターゲット(Buildに依存、`$(PmxEditorDir)\_plugin\User\` へ
  変更時のみコピー)。コマンドは
  `dotnet build src/HostPlugin/PmxEditorMcp.HostPlugin.csproj -t:Deploy` の1回で完結する。
  配布物が利用者の作成したプラグインの置き場として `User` を勧めている。ホストDLLの置き場は
  ここ1つとする。`_plugin` 直下と `User` の両方にあると2つ読み込まれ、同じパイプ名のホストが
  2つになり、インスタンス数1の待受を後発が作れない(「前提と裏取り」7)。

### プラグインのライフサイクル(アーキテクチャ仕様書へ移送)

- クラス `PmxEditorMcpPlugin`(PEPluginClass派生)。オプションは起動時実行+メニュー登録
  (メニュー文言「PMX Editor MCP」)。
- 起動時実行: 不可視Formを生成してハンドルを確保し、稼働世代を1つ作ってIPCサーバースレッド
  (背景スレッド)を開始する。例外はすべて捕捉してログへ記録する(エディタを巻き込まない)。
- 稼働世代: 受付停止フラグ・公開中のパイプインスタンス・IPCサーバースレッドの参照を1つの
  「稼働世代」としてまとめて保持し、開始のたびに新しい稼働世代を作る。停止手順・状態判定・
  UIディスパッチの可否はすべて稼働世代の単位で決まり、停止した稼働世代での禁止を新しい稼働世代へ
  持ち越さない。
- メニュー再実行: 稼働状態(状態区分・パイプ名・接続状態・応答サイズ予算・ログパス)を
  メッセージボックスで表示し、そこからホストの停止・開始を選べる(起動時実行のやり直しはしない)。状態区分は
  「稼働中」「停止処理中」「停止済み」「開始せず(予算設定が不正)」の4つで、メニュー再実行の
  たびに判定する(「停止処理中」と「停止済み」の別は、停止した稼働世代のIPCサーバースレッドが
  終了済みかで決まる)。「稼働中」なら「停止しますか?」、「停止済み」なら「開始しますか?」を
  既定「いいえ」のはい/いいえで確認し、はいのときだけ停止・開始を行う。その結果は表示しない
  (状態は次のメニュー再実行で分かる)。開始が受け付けられなかったときは、開始できなかった理由を
  ログへ記録する。「停止処理中」と「開始せず(予算設定が不正)」では問いを出さず、なぜ開始
  できないかを状態表示の本文に含める。停止・開始の操作は排他ロックで直列化する(呼び出し
  スレッドを仮定しない)。
- ホストの停止手順(メニューからの停止とDisposeが共有する): 排他ロックの下で (1)現在の稼働世代の
  受付停止フラグを立てる (2)その稼働世代が公開しているパイプインスタンスがあれば閉じる
  (PipeOptions.Asynchronous で生成しているため、WaitForConnection・読み取りのブロックが即座に
  解ける) (3)以後その稼働世代ではUIディスパッチを行わない。**呼び出しスレッドをブロックして
  IPCサーバースレッドの終了を待つことはしない**——メニューからの停止もDisposeもUIスレッドから
  呼ばれうるため、ここで待つと、UIスレッドへのInvokeを待っている要求処理があるときに相互待ちに
  なり、待ちが必ず空振りする。
- IPCサーバースレッドの待受ループ(停止手順との競合を閉じる): 1回の反復は、排他ロックの下で
  自分の稼働世代の受付停止フラグを確認し、立っていればループを抜け、立っていなければ新しいパイプ
  インスタンスを生成して稼働世代へ公開するところから始める。ロックを解いてから WaitForConnection と
  要求処理を行う。停止手順が「フラグを立てる」と「公開中のインスタンスを閉じる」を同じロックの
  下で行うため、フラグ確認をすり抜けて生成されたインスタンスが閉じられないまま待受に残ることは
  ない。停止で閉じられたインスタンスは、待受中なら WaitForConnection が例外で戻り、接続中なら
  読み取りが0バイトを返して戻る(いずれも切断として扱う)。ループ内の例外は捕捉してログへ記録し、
  フラグが立っていればループを抜ける(立っていなければ次の反復へ戻る)。停止した時点で要求を
  処理中だった場合は、その要求の処理を終えてから次の反復へ入り、そこでフラグを見て終了する。
  パイプインスタンスの生成に失敗したときは500ミリ秒置いて次の反復へ戻り、失敗の原因が解消する
  まで繰り返し試みる(直ちに再試行すると失敗が続く間ずっと回り続けるため)。この間も状態区分は
  「稼働中」のままとし(区分を増やさない)、記録は連続する失敗の最初の1回と復帰の1回に限る
  (同じ記録の反復でローテーションが有用な履歴を押し流すのを避ける)。
- メニューからの開始: 「停止済み」からのみ受け付ける。「停止処理中」は前の稼働世代のIPCサーバー
  スレッドがまだ終了していない状態(停止した時点で処理中だった要求が残っている等)である。この間に
  新しい稼働世代を開始すると、旧世代が処理中の要求と新世代が受ける要求が並行し、要求の直列処理
  (同時実行1)とUIディスパッチの直列性が崩れるため開始せず、なぜ開始できないかを状態表示の
  本文に含める。この状態は前の稼働世代のスレッドの終了で解消し、次のメニュー再実行では
  「停止済み」と判定されて開始できる。「開始せず(予算設定が不正)」からの開始は、環境変数を
  読み直しても同じ結果になるため受け付けない(同じくなぜ開始できないかを本文に含める)。
  開始は新しい稼働世代を作ってIPCサーバースレッドを開始する。パイプ名はエディタのプロセスIDで
  決まるため停止・開始をまたいでも同じ名前になり、衝突しない。不可視Formは起動時に生成した
  ものを作り直さずに使い続ける。
- Dispose の停止順序: (1)上記の停止手順を実行する(IPCサーバースレッドが残っていても背景
  スレッドなのでプロセス終了で回収されることを許容する) (2)不可視FormをClose/Disposeする
  (3)base.Dispose() を呼ぶ。
- PEPlugin API呼び出しは必ず不可視FormのInvokeでUIスレッドへ委譲する(スレッドセーフティを
  仮定しない)。Invokeで開始したUI処理は中断しない。

### IPCプロトコル(IPC仕様書へ移送)

- トランスポート: 名前付きパイプ。パイプ名は `pmx-editor-mcp-<エディタのプロセスID>` の
  1本のみ(所有権・再選出の問題を持たない)。ブリッジがどのホストへ接続するか
  (自動発見と環境変数 `PMX_EDITOR_MCP_PIPE` による明示指定)は実装計画書03が確定する。
- 接続: パイプインスタンス数1(同時接続1)。切断されたら待受に戻る。要求はホスト
  インスタンス内で直列処理(同時実行1)する。パイプは **PipeOptions.Asynchronous で生成する**
  (APIの呼び方は同期のままでよい。このオプションでなければ、停止手順がパイプを閉じても待受・
  読み取りのブロックが解けず、ホストを停止できない——「前提と裏取り」5)。伝送モードはバイト
  (メッセージの境界はパイプでなく改行区切りが決める)。入出力のバッファは各65536バイト。
- アクセス制御: PipeSecurityで現在ユーザーのSIDのみにFullControlを許可する。
- メッセージ形式: UTF-8(BOMなし)。1メッセージ1行、出力の区切りはLF(入力はLF・CRLFの
  両方を受理する)。本文はJSON-RPC 2.0のサブセット:
  - 要求: `jsonrpc`(固定 "2.0"・必須)・`id`(数値または文字列・必須。通知=id無し要求は
    使用しない)・`method`(文字列)・`params`(オブジェクト。省略可)。
  - 応答: `jsonrpc`・`id`(要求と同値)・`result` または `error{code,message}`。`id` と
    `message` の例外はエラーと切断の規則が定める。
  - シリアライザは JavaScriptSerializer(System.Web.Extensions。同梱依存ゼロ)。既定の
    MaxJsonLength は 2097152 文字で、そのままでは16MiB契約を満たせない(「前提と裏取り」6)。
    解析では MaxJsonLength を 33554432 に設定する(16MiBのUTF-8本文は最大 16,777,216 文字
    なので、その2倍)。組み立てでは MaxJsonLength を int.MaxValue にしてシリアライザ側の上限を
    実質外し、上限の判定は本文のバイト数で行う(下記の出力上限超過)。
- 読み取りは生バイトを上限付きで行う: 累積バイト数が上限を超えた時点で読み取りを打ち切り、
  全文をメモリに保持せずに上限超過として扱う(改行の到来を待たない)。デコードは厳格な
  UTF-8で行い、不正なバイト列は構文不正として扱う。
- ハンドシェイク: 接続後の最初の要求は `handshake`(params: `protocol`=1)でなければ
  ならない。成功応答は `result` = `{"protocol":1,"hostVersion":"<ホストDLLのアセンブリ
  バージョン文字列>","budgetChars":<ホストが読んだ応答サイズ予算の文字数。数値>}`。
  `budgetChars` はブリッジが自分の設定値と照合するための項目である。handshake 済みの接続で
  引数が有効な handshake を再度受けたときは、状態を変えず同じ成功応答を返す(引数が不正・
  番号が不一致のときは下記の規則どおりに扱う)。プロトコル番号の変更は互換を壊す変更のたびに
  行う。
- **応答サイズ予算の設定**(ホスト側。アーキテクチャ仕様書へ移送): ホストは環境変数
  `PMX_EDITOR_MCP_BUDGET_CHARS` から応答サイズ予算の文字数を読み、**未設定時の既定は
  100,000** とする。値の構文は ASCII数字のみからなる10進表記で、符号・前後の空白・先頭の
  ゼロ・ASCII以外の数字は受理しない。有効範囲は **10,000 以上 500,000 以下**。構文違反・
  範囲外のときは既定値へ落とさず、**IPCの待受を開始せず**、理由をログへ記録してメニュー
  再実行の状態表示にも出す(エディタは巻き込まない)。読み取った値を handshake 応答の
  `budgetChars` に載せる。**この値をどう使うか**(警告枠との内訳・`limit` の逆算・この値を
  選んだ理由)は共通契約仕様書が定める。ホストは値を読んで載せるところまでを担う。
- 基盤メソッド: `handshake` と `ping`(result: 文字列 "pong")。
  例: 要求 `{"jsonrpc":"2.0","id":1,"method":"ping"}` → 応答
  `{"jsonrpc":"2.0","id":1,"result":"pong"}`。ツールに対応するメソッドは実装計画書04が
  追加する。
- サイズ制限: 1メッセージ=1行の本文(区切りのLF/CRLFを含まない)のUTF-8バイト数で
  上限16MiB。入力・出力の両方向に適用する。**これは名前付きパイプの上限であり、応答サイズの
  設計目標ではない**: MCPクライアント側の出力上限は**トークン数**で定められており、
  バイト数の上限を満たしてもその上限を満たす保証にならない。実効の応答サイズ予算は
  共通契約仕様書が別に定める。16MiBを応答サイズの設計値として流用しないこと。
- 判定の順序: 1件の要求に対して次の順で適用し、最初に当たったところで応答を決める。
  (1)入力メッセージの上限超過 (2)UTF-8のデコードとJSON構文 (3)要求構造 (4)handshake ゲート
  (5)handshake のプロトコル番号 (6)メソッドの検索 (7)引数の検査 (8)実行(処理タイムアウト・
  予期しない例外・応答の上限超過)。この順により、最初の要求が構造不正のときは -32600 を返して
  接続を維持し(-32003 で切断しない)、構造が妥当で `method` が handshake 以外(空文字列を
  含む)のときは -32003 で切断する。
- エラーと切断の規則(応答の `id` は、各項で特に断らないかぎり要求と同値とする。要求idを判別
  できないときは null とする):
  - JSON構文不正(UTF-8として不正なバイト列を含む): `error` code -32700(idはnull。本文を
    解析できないため要求idを判別できない)を返して切断する。
  - 要求構造の不正(トップレベルが配列・`jsonrpc` の欠落や "2.0" 以外・`method` 欠落・
    `method` が文字列以外・`id` の欠落や許容外の型): code -32600 を返す(接続維持)。
    `method` が空文字列のときは構造不正とせず、対応する処理が無いものとして未知メソッドで
    扱う。`id` の不正と `params` の不正が同時にあるときは -32600 を先に判定する(応答に
    要求idを載せられるかがこれで決まるため)。
  - handshake前にhandshake以外の要求: code -32003 を返して切断する。
  - プロトコル番号不一致のhandshake: code -32001 を返して切断する(非互換の接続拒否)。
    `protocol` の欠落・数値以外は番号の不一致ではないため -32001 とせず、不正な引数として扱う。
  - 未知メソッド: code -32601(接続維持)。不正な引数: code -32602(接続維持)。`params` が
    オブジェクト以外(配列・文字列・数値・null)であることと、メソッドが要求する引数を
    満たさないことの両方が不正な引数にあたる。
  - 入力メッセージの上限超過: code -32004(idはnull。JSON解析前に判定するため要求idは
    使わない)を返して切断する。
  - 出力(応答)の上限超過: 組み立てた本文のUTF-8バイト数が上限(16MiB)を超えたら、結果を
    破棄し code -32005 を返す(接続維持。大きな応答の回避はツール契約(実装計画書04)の
    ページングが担う)。**判定にシリアライザの例外を使わない**——文字数上限の超過は循環参照と
    同じ例外型で返り、メッセージも実行環境の言語に翻訳されるため区別できず、-32603 とすべき
    失敗まで -32005 へ落ちる(「前提と裏取り」6)。組み立てはシリアライザ側の上限を外して行い、
    得られた本文を自分で測って判定する。文字数で重ねて判定しない: UTF-8のバイト数は文字数
    以上なので、バイト数の判定が文字数の判定を含む。上限は処理タイムアウトの値と同様に
    テストから差し替え可能に実装する。入力と違って組み立て後の全量が一度メモリに載るが、
    応答の量はツール契約(実装計画書04)のページングが抑えるため許容する。
  - 要求処理中の予期しない例外(応答の組み立てが上限以外の理由——循環参照・シリアライズ
    できない値——で失敗した場合を含む): code -32603 を返す(接続維持。handshake済み状態は
    維持し、例外はスタックトレース付きでログに記録する)。
  - ホスト側の要求処理が120秒を超過: code -32002 を一度だけ返す。開始済みのUI処理は
    中断できないため、その完了までは次の要求を読み取らない(直列保証を維持する)。
    完了後の結果は破棄し、二重応答しない。超過はログに記録する。タイムアウト値は
    テストから差し替え可能に実装する。
  - 上のどのエラーでも、組み立てたエラー応答のUTF-8バイト数が上限を超えるときは `id` を null
    にし、なお超えるときは `message` を空にして、コードだけは返す(いずれもキー自体は残す)。
    接続を切るかどうかはコードごとの扱いを変えない——ここで書き込みに失敗させると、接続を
    保つはずのエラーがすべて切断に化ける。

### 危険操作の公開方針(アーキテクチャ仕様書へ移送)

- 危険操作(エディタ終了・ファイルの上書き保存・モデル初期化)に対応するツールは、
  引数 `confirm: true` の明示を必須とし、無い場合は実行せずエラーを返す。対象ツールの
  指定は能力台帳の備考とツール契約(実装計画書04)が行う。

### ログと診断(アーキテクチャ仕様書へ移送)

- ホストのログ: `%TEMP%\pmx-editor-mcp-host-<エディタのプロセスID>.log`(インスタンス間で
  競合しない)。1MiB(1,048,576バイト)超で同名 `.1` へローテーション(1世代)。
  ローテーションに失敗しても追記は続ける(ローテーション先が開かれ続けている間に記録全体が
  止まるのを避ける。閾値を一時的に超えることは許容する)。
- 記録内容: 起動・停止(メニューからの停止・開始を含む)・接続・切断・エラー(例外は
  スタックトレース付き)・処理タイムアウト。処理タイムアウトの記録にはメソッド名を含める。無いと
  記録から得られるのは「何かが超過した」だけになり、UIスレッドを占有したまま固まった操作を後から
  突き止められない。含めてよいのはメソッドの検索に一致した名前(基盤メソッドを含む)だけで、
  一致しなかった名前は接続の相手が任意の文字列を置けるため記録しない。
- 要求の内容は記録しない(モデルデータを含みうるため)。ここでいう要求の内容とは `method` 以外の
  すべて——他の項目・契約外の余分なメンバー・本文をそのまま写したもの——を指す。ログへ記録される
  例外のうち要求の値に触れうるもの(要求処理の予期しない例外と待受ループの例外)は、そのメッセージ
  にも要求の値を引用しない。要求元へ返すだけで記録しない説明(不正な引数の説明など)はこの制限の
  対象外で、問題の値を指してよい。
  ホストの外から来る例外のメッセージは制御できないため、そこへ要求の値が引き写されて記録される
  ことは残存リスクとして受け入れる(制御できる箇所を塞いだうえでの残余で、ツールの失敗を追う
  手掛かりがメッセージしか無い)。
- 現在のログパスはメニュー再実行の状態表示で確認できる。

## 実装ステップ

1. `local.props` 機構(`Directory.Build.props`・`.gitignore` 追記)と
   `src/HostPlugin/PmxEditorMcp.HostPlugin.csproj`(PEPlugin.dll参照・Deployターゲット)を
   作成し、ソリューションへ追加する。`_plugin` 直下にホストDLLが残っていれば取り除く
   (「前提と裏取り」7)。
2. プラグイン骨格(PEPluginClass派生・起動時常駐・不可視Form・メニュー再実行時の状態判定と
   状態表示・停止/開始操作・共有の停止手順・Dispose停止順序・ログ)を実装する。
3. IPCサーバー(パイプ待受・ACL・改行区切りJSONの読み書き・handshake・ping・エラーと
   切断の規則・制限・切断復帰)を実装する。プロトコル解析はUIに依存しない形に分け、
   xUnitテストを書く(対象: 構文不正・不正UTF-8バイト列・要求構造不正・handshake前拒否・
   プロトコル番号不一致・予算設定の構文違反と範囲外で待受を開始しないこと・handshake 応答の
   `budgetChars` が読み取った値になること・未知メソッド・不正引数・入力上限超過(改行なしで
   上限を超える入力を含む。応答idはnull)・出力上限超過(上限を差し替えて確かめる)・
   組み立ての失敗が -32005 でなく -32603 になること・処理内例外・処理タイムアウトの記録に
   メソッド名が入ること・要求の値が記録されないこと・シリアライザ既定上限より大きく16MiB以下の
   要求の受理と応答の返却・
   タイムアウト後の一回だけのエラー応答と完了までの次要求非読取・接続中/処理中の
   Dispose停止(呼び出しスレッドを待たせずにIPCサーバースレッドが終了することと、その稼働世代で
   以後UIディスパッチを行わないこと)・停止手順の実行後にIPCサーバースレッドが終了して状態区分が
   「停止済み」になることと待受が無いこと・待受ループの反復開始直後に停止しても、生成された
   パイプインスタンスが閉じられずに待受へ残らないこと・停止→開始で同じパイプ名の待受へ戻り、
   開始後の稼働世代が要求を処理して handshake に応答すること・新しい稼働世代が前の稼働世代の
   UIディスパッチ禁止を引き継がないこと・IPCサーバースレッドが終了する前は「停止処理中」と
   判定して開始を拒否し、終了後は「停止済み」と判定して開始できること・「開始せず(予算設定が
   不正)」からの開始を拒否すること)。
4. `scripts/e2e-check.mjs` の未設定箇所を確定値で実装する。
   - 起動引数: 第1引数を対象エディタのプロセスIDとする。第1引数の直後に `--hold` を置くと、
     全応答を受け切ったあとも切断せずに待ち続ける(接続を張ったままの確認に用いる)。
     残りは送る要求で、メソッド名単体か、メソッド名の直後に `params` のJSON表記を続けた2語で
     表す(他の位置に置いた `--hold` は要求として送らず、置き場所の誤りとして拒む)。
     要求を省略したときの既定の並びは、`handshake` に `{"protocol":1}` を与えたものと
     `ping` の2件とする。
   - 接続先: 第1引数のプロセスIDから `pmx-editor-mcp-<エディタのプロセスID>` を組み立てる
     (固定名は持たない)。
   - 要求の符号化: 要求を `jsonrpc`・`id`・`method`・`params`(省略時は付けない)のオブジェクトに
     し、BOMなしUTF-8の1行にしてLFを付す。`id` は1から始めて要求ごとに1ずつ増やし、採番した値を
     モジュール内の変数へ保持する。
   - 応答の取り出し: LFまでを1行として切り出し、厳格なUTF-8でデコードして解析する。`id` が
     保持した値と一致しない応答(ホストが `error` の応答で `id` を null とする場合を除く)と、
     `result` も `error` も持たない応答は例外とする。表示する文字列は `result` または
     `error` のJSON表記とする。
5. デプロイコマンド1回で配置し、実機のPMXエディタで実機動作確認を行う:
   handshake・pingの期待応答/今回の起動でホストログに残る起動の記録が1回だけであること/
   エディタを2つ起動して各PID名パイプへ個別に接続できること/プロトコル番号不一致のhandshakeが
   拒否されること/パイプのDACLが現在ユーザーのみであること/エディタ終了(Dispose)でパイプが
   消えること/接続を張ったままエディタを終了してもエディタがハング・クラッシュしないこと/
   メニューからの停止でパイプが消えて確認クライアントが接続できなくなり、メニュー再実行の
   状態表示が「停止済み」へ到達すること/停止後にメニューから開始すると同じパイプ名で再び
   接続でき、handshake・pingが期待応答を返すこと/エディタを閉じずに停止と開始を繰り返せる
   こと/接続を張ったままメニューから停止しても、エディタがハング・クラッシュせず、メニュー
   再実行の状態表示が「停止済み」へ到達すること(「停止処理中」なら再実行して確かめる)。
   確認後、検証手順書の実機動作確認手順へ確定した具体値(パイプ名・デプロイコマンド・
   確認クライアントの起動方法・期待応答・上記確認ケース)を追記する。
6. 確定事項をアーキテクチャ仕様書とIPC仕様書として作成する(「確定する設計値」を到達状態の

   `_plugin\User\` 1つにすること・PipeOptions.Asynchronous でのパイプ生成(これでなければ
   停止手順がブロックを解除できない)・出力の上限をシリアライザの例外でなく本文のバイト数で
   判定すること(例外では上限超過と循環参照を区別できない)——を設計判断の理由として記載する。
   本計画書にしか無い恒久情報を残さない。「前提と裏取り」への参照は、参照先の節ごと移送されない
