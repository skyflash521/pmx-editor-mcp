# 実装計画書01: 検証基盤整備

pmx-editor-mcp の検査(ビルド・整形・テスト・スクリプト構文・実機動作確認)を定義し、
実行できる環境を整備する。確定した検査は検証手順書(`docs/conventions/verification.md`)へ
移送する。

## 前提と裏取り

1. **.NET SDK で net48 クラスライブラリを環境非依存にビルドできる**
   - 出典: 記載なし(ビルド方式の選定)
   - 確かめた結果: .NET SDK 10.0.400 で、TargetFramework=net48・
     `Microsoft.NETFramework.ReferenceAssemblies` 1.0.3 をPackageReferenceする最小
     クラスライブラリを `dotnet build` し、エラー0で成功することを実測した(参照
     アセンブリはNuGetから解決されるため、.NET Framework Developer Pack の導入有無に
     依存しない)。
   - ホスト(PMXエディタ側プラグイン、net48)をdotnet CLIでビルドできる。

2. **sln形式のソリューションを名前指定で作成できる**
   - 出典: .NET 10 のソリューションテンプレートは既定が slnx 形式(公式の破壊的変更)
   - 確かめた結果: `dotnet new sln -n PmxEditorMcp --format sln` で `PmxEditorMcp.sln` が
     生成されることをSDK 10.0.400で実測した。
   - 形式・名前を明示すれば検査コマンドの対象ファイル名を固定できる。

3. **dotnet format が利用できる**
   - 出典: 記載なし(実行環境の事実)
   - 確かめた結果: `dotnet format --version` が 10.0.400 を返すことを実測した。

4. **実機動作確認の経路が成立する**
   - 出典: 能力台帳(`docs/specs/pmx-editor-mcp-capability-ledger.md`)の根拠となった
     E2Eスパイクの実測
   - 確かめた結果(スパイク時の実測記録。値は検証専用でありツール契約の値ではない):
     検証専用プラグインDLL(.NET Framework付属csc 4.8.9221.0でビルド)を配布物の
     `_plugin` へ配置してPmxEditor_x64.exeを起動し、名前付きパイプ(名称 pmx_mcp_spike2)へ
     Node.js 25.6.1のクライアントから要求を送って、ping→pong・モデル名取得・頂点数取得の
     応答を得た。さらに同パイプへ中継するstdioブリッジを `claude mcp add` で登録し、
     Claude Code CLIのヘッドレス実行からツール呼び出しで pong と 頂点数0(空モデル)の
     応答を得た。ホスト側のPEPlugin API呼び出しは不可視フォームのInvokeでUIスレッドへ
     到達できた。
   - 実機動作確認はこの経路の再現として定義できる。ただし本計画(01)の時点ではホスト
     (実装計画書02)とブリッジ(実装計画書03)が未実装のため、実機動作確認の初回実行は
     02以降になる。

## 確定する設計値

### 検査一覧と合格条件

| 検査 | コマンド | 合格条件 |
|---|---|---|
| ビルド | `dotnet build PmxEditorMcp.sln -warnaserror` | 警告・エラー0 |
| 整形 | `dotnet format PmxEditorMcp.sln --verify-no-changes` | 差分0 |
| テスト | `dotnet test PmxEditorMcp.sln` | 全テスト成功 |
| スクリプト構文 | `node --check scripts/e2e-check.mjs` | エラー0 |
| 実機動作確認 | 下記の手順 | 手順内の各確認が期待どおり |

- ソリューションはリポジトリ直下の `PmxEditorMcp.sln`(sln形式)の1本とする(中身の
  プロジェクト構成は実装計画書02が確定する)。
- net48プロジェクトの参照アセンブリは `Microsoft.NETFramework.ReferenceAssemblies` 1.0.3 の
  PackageReferenceで解決する(Developer Pack非依存)。
- テストは xUnit を用いる。UIスレッドやエディタ実機に依存する部分は単体テストの対象外とし、
  実機動作確認で担保する。

### 必要環境

- .NET SDK: 最新の安定版(本計画の実測は 10.0.400)
- Node.js(実機動作確認クライアントとブリッジの実行。本計画の実測は 25.6.1)
- Claude Code CLI(MCP経路の確認に使用)
- Windows x64 と PMXエディタ配布物(本計画の実測は PmxEditor_0273)

### 実機動作確認の手順(枠組み)

1. デプロイコマンドを1回実行し、ホストDLLのビルドとPMXエディタ配布物(各自の導入物)の
   `_plugin` フォルダへの配置を行う。**デプロイは1コマンドで完結すること**を要件とし、
   方式はMSBuildのDeployターゲット(ビルドに依存し、成果物に変更があった場合のみ
   コピーする)+Git管理外のローカル設定によるデプロイ先指定とする。具体のコマンド・
   ローカル設定ファイルは、PEPlugin.dllのパス設定機構と一体の設計値として実装計画書02が
   確定し、確定と同時に検証手順書の本手順へ追記する。
2. `PmxEditor_x64.exe` を起動する(プラグインが起動時にロードされ、名前付きパイプの
   待受が始まる)。
3. `scripts/e2e-check.mjs` を実行し、疎通と取得系ツールの応答を確認する。
4. `claude mcp add` で登録したブリッジ経由でMCPツールを呼び出し、期待応答を確認する。

本計画で確定するのはこの枠組みと分担まで。**パイプ名・ツール名・要求/応答形式・期待値・
`claude mcp add` の登録コマンド・後処理は、ホストとブリッジの設計値として実装計画書02
(パイプ契約)と03(ブリッジ・MCP登録)が確定し、確定と同時に検証手順書の本手順へ追記する**
(この分担自体を検証手順書に明記して移送する)。実機動作確認の初回実行と合格判定は、
02(パイプ直結の確認)・03(MCP経由の確認)の各完了条件が担う。

### 不合格時の対応

- ビルド・整形・テスト・スクリプト構文の不合格: 修正して再実行するまで変更を確定させない。
- 実機動作確認の不合格: ホストのログ(`%TEMP%\pmx-editor-mcp-host.log`)とブリッジの
  標準エラー出力を確認し、原因を修正して手順を再実行する。

## 実装ステップ

1. リポジトリ直下でソリューションを作成する:
   `dotnet new sln -n PmxEditorMcp --format sln`
2. `dotnet build` / `dotnet format --verify-no-changes` / `dotnet test` が空のソリューションで
   成立することを確認する。整形の判定規則は現行の `.editorconfig` をそのまま確定入力とする
   (規則の変更は本計画の範囲外)。
3. 実機動作確認用の確認クライアント `scripts/e2e-check.mjs` の骨組み(名前付きパイプへ
   接続して要求を送り、応答を表示する)を作成し、`node --check` が通ることを確認する
   (接続先・要求/応答形式の具体値は02の確定後に同スクリプトへ反映する)。
4. 検査一覧・合格条件・必要環境・実機動作確認の枠組みと分担・不合格時の対応を
   `docs/conventions/verification.md` へ移送する(本計画書の「確定する設計値」を正本化する)。
5. ビルド・整形・テスト・スクリプト構文の4検査を実行して成立を確認し、進捗ドキュメント
   (`docs/plans/pmx-editor-mcp-progress.md`。本計画のステップごとに、実行したコマンドと
   合否を記録する)へ結果を記録する。完了後、本計画書を削除候補として報告する。

## 完了条件

- ビルド・整形・テスト・スクリプト構文の4検査が定義どおり成立している。
- 実機動作確認の枠組み・分担(02/03が具体値を追記する)が検証手順書に記載されている。
- `docs/conventions/verification.md` が検査一覧の正本になっている。
