# 実装計画書05: 配布・導入整備

pmx-editor-mcp を利用者へ配布できる形に整備する。配布パッケージの生成を1コマンド化し、
導入手順書を作成する。確定した恒久情報は導入手順書(`docs/guides/installation.md`)・
検証手順書(`docs/conventions/verification.md`)・アーキテクチャ仕様書
(`docs/specs/pmx-editor-mcp-architecture.md`)へ移送する。

## 前提と裏取り

1. **配布対象の成果物**
   - 出典: アーキテクチャ仕様書のプロジェクト構成(ホスト:
     `src/HostPlugin/PmxEditorMcp.HostPlugin.csproj`、成果物名 `PmxEditorMcp.dll`、
     net48・AnyCPU)・実装計画書03(ブリッジ: `src/Bridge/PmxEditorMcp.Bridge.csproj`、
     net10.0コンソール、成果物名 `PmxEditorMcp.Bridge.exe`)
   - 確かめた結果: ホストは仕様書で、ブリッジは計画書で、成果物名・フレームワークが確定済み。
     能力台帳の実機確認は検証専用DLLとハンドロールのブリッジによる**経路方式の成立**
     (DLLの `_plugin` 配置・パイプ・`claude mcp add` 経由の応答)の根拠であり、最終成果物
     どうしの成立は、ホストは検証手順書の実機動作確認、ブリッジとツールは実装計画書03・04の
     完了条件(各実機確認)と本計画ステップ4の実測が担う。本計画はその2成果物を配布形に包む。
2. **再配布しない物**
   - 出典: アーキテクチャ仕様書の PEPlugin.dll の参照(利用規約が配布物のパッケージ内データの
     再配布を禁じているため、各自の導入物を参照するだけにする)
   - 確かめた結果: PEPlugin.dll・PMXエディタ本体は再配布禁止のため配布物へ含めない方針が
     同仕様書で確定している。ホストDLLはPEPlugin.dllを参照するのみで同梱しない
     (エディタが実行時に解決する)。
3. **導入側の前提環境**
   - 出典: READMEの開発環境と、.NET Framework 4.8 がWindows 10
     (バージョン1903以降)・Windows 11 にOSコンポーネントとして含まれるというOS仕様
   - 確かめた結果: Windows x64・PMXエディタ(x64版)・Claude Code CLI。ブリッジ
     (net10.0)は自己完結型(self-contained)で発行するため .NET ランタイムの追加導入は
     不要。ホストDLL(net48)は .NET Framework 4.8 を要するが、上記OSにはOS同梱であり
     追加導入不要——能力台帳の実機確認でも、追加導入なしの本開発機(Windows 11)で
     net48プラグインDLLがエディタから実行できている。利用者向け前提には対応OS
     (Windows 10 バージョン1903以降/Windows 11)を明記する。
4. **ブリッジの自己完結型・単一ファイル発行**
   - 出典: 一般の .NET SDK 機能(win-x64 向け self-contained + PublishSingleFile)
   - 確かめた結果: 本リポジトリのブリッジ構成(net10.0+ModelContextProtocol 2.2.0)での
     発行成立は**未検証**である。実装ステップ1で発行と起動・MCP応答を実測し、成立を
     確認してからパッケージ生成に組み込む。成立しない場合(単一ファイル化と依存の
     非互換等)は、フレームワーク依存発行+導入手順への .NET ランタイム前提の追加へ
     切り替える設計変更としてユーザーへ報告する。

## 仕様書とコードの食い違い

本計画の作成時点ではプロダクトコードは未実装である(実装フェーズは計画書の番号順の
ため、本計画の実行時には先行する計画の成果物が存在する)。突き合わせ範囲: アーキテクチャ仕様書・
IPC仕様書・実装計画書03〜04・検証手順書・能力台帳の全文。食い違いは無い。

## 確定する設計値

### バージョンの正本(アーキテクチャ仕様書へ移送)

- バージョンはリポジトリ直下の `Directory.Build.props` の `Version` プロパティを単一の
  正本とし、ホスト・ブリッジのアセンブリバージョンと配布パッケージ名がこれを共有する。
  初版は `0.1.0` とし、以後の更新は配布のたびに手動で上げる(自動採番はしない)。

### 配布パッケージ(導入手順書・検証手順書へ移送)

- パッケージは `dist/pmx-editor-mcp-<バージョン>.zip`(`dist/` はGit管理外。`.gitignore` へ
  追加)。内容は次の5点のみ:
  - `PmxEditorMcp.dll`(ホスト。Releaseビルド)
  - `PmxEditorMcp.Bridge.exe`(ブリッジ。Release・win-x64・self-contained・単一ファイル
    発行。発行プロパティは `SelfContained=true`・`RuntimeIdentifier=win-x64`・
    `PublishSingleFile=true`・`IncludeNativeLibrariesForSelfExtract=true` を明示し、
    ネイティブDLLも単一exeへ含める——exe 1ファイルだけで動作する契約)
  - `README.txt`(利用者向け導入手順の正本。下記)
  - `LICENSE.txt`(リポジトリの LICENSE 全文の複製)
  - `THIRDPARTY.txt`(第三者ライセンス表示。正本は追跡ファイル
    `docs/guides/package-thirdparty.txt`。作成規則は次のとおり確定する:
    本文の構成は(a)NuGet依存のエントリ群: 対象パッケージ(下記の解析対象)ごとに、
    次の固定形式のエントリを置く——1行目は見出し `## <パッケージID(小文字正規化)>
    <バージョン>`、2行目は `license: <SPDXライセンス式>`、続けて `source:` 行(下記。
    複数行可)、続けて範囲マーカー `-----BEGIN LICENSE <パッケージID>-----` 〜
    `-----END LICENSE <パッケージID>-----` の間に転記本文。`source:` 行と転記元の規則:
    `source: files <パッケージ内相対パスのセミコロン区切り>`(NuGetキャッシュ内の当該
    パッケージに同梱されるライセンス・NOTICE類の全ファイル。複数ある場合はファイル名
    昇順に連結)と `source: spdx <ID>`
    (SPDXライセンス式が指す標準本文。正本は追跡ファイル `docs/guides/licenses/<ID>.txt`。
    ステップ1でSPDXライセンスリストから転記して作成し、以後この追跡ファイルと照合する
    ——外部の版に依存しない)。**パッケージ本体のライセンス本文が同梱ファイルに含まれない
    場合(NOTICEのみ同梱等)は両方の `source:` 行を併記する**。**期待本文の連結規則**
    (一意に確定): 構成要素はspdx標準本文(併記時は先頭。複数IDの場合はID昇順
    ——ASCII順——で並べる)→各同梱ファイル(ファイル名昇順)の順とし、**各構成要素の
    直前に必ず区切り行を置く**(先頭要素にも置く)。
    区切り行はspdx本文が `--- spdx <ID> ---`、ファイルが `--- <ファイル名> ---`。
    ライセンス本文が同梱されていればfilesのみ、同梱ファイルが皆無ならspdxのみとする。
    (b)「.NETランタイム」見出し: 自己完結型発行で同梱されるランタイム自体のライセンスと
    第三者通知として、ビルドに用いる .NET SDK のインストールディレクトリに同梱される
    LICENSE.txt と ThirdPartyNotices.txt(.NET導入ディレクトリ直下の実ファイル名)の
    **全文転記**を、それぞれ範囲マーカー
    `-----BEGIN RUNTIME LICENSE-----` / `-----BEGIN RUNTIME NOTICES-----`(対応するEND)で
    区切って置く。依存変更時の更新は、下記の内容物検査の依存集合照合が失敗することで
    強制される——この保守規則は検証手順書へ移送する)
- `README.txt` の正本は追跡ファイル `docs/guides/package-readme.txt` とし、`package.ps1` は
  これを無加工で `README.txt` としてzipへ収録する。テンプレートは**単体で導入を完了できる
  全手順**(前提・導入・確認・更新・アンインストール・トラブルシューティング)を含める
  (配布先ではリポジトリ内パスを解決できないため、参照だけの記載にしない)。
- 生成は `pwsh scripts/package.ps1` の1コマンドで完結する。スクリプトは
  (1)ホストのReleaseビルド、(2)ブリッジのReleaseの自己完結型単一ファイル発行、
  (3)zipの作成、(4)**内容物検査**を行い、検査不合格時は失敗させる。内容物検査の項目:
  上記5点が存在しそれ以外が含まれないこと/PEPlugin.dll が混入していないこと/
  `README.txt` が `docs/guides/package-readme.txt` とバイト一致すること/`LICENSE.txt` が
  リポジトリの `LICENSE` とバイト一致すること/`THIRDPARTY.txt` が
  `docs/guides/package-thirdparty.txt` とバイト一致すること/**依存集合照合**:
  THIRDPARTY正本の先頭の機械照合ブロックと実解決結果の完全一致を検査すること。
  照合ブロックの形式は次のとおり確定する——本文先頭に
  `-----BEGIN PACKAGE LIST-----` 〜 `-----END PACKAGE LIST-----` で区切り、1行1項目
  `<パッケージID(小文字正規化)> <バージョン>` を(ID,バージョン)の昇順・重複なしで
  列挙し、末尾に `sdk <ビルドSDKバージョン>` の1行を置く。**解析対象**はホストとブリッジの
  2プロジェクトの `dotnet list package --include-transitive --format json` の和集合とし、
  除外リスト(追跡ファイル `docs/guides/package-excluded-packages.txt`。1行1パッケージID。
  初期内容は `microsoft.netframework.referenceassemblies` と
  `microsoft.netframework.referenceassemblies.net48` の2行。判定基準=
  コンパイル参照のみで発行出力に含まれないビルド専用パッケージであり、追加時は当該
  アセンブリが発行出力に無いことを確認して行う——この基準と確認方法も検証手順書へ
  移送する)を適用して除く。同一IDが異なるバージョンに解決された場合は別行として双方を
  記載する((ID,バージョン)の組で一意)。**ハッシュの正規化規則**: 本計画のハッシュ照合は
  すべて「UTF-8デコード(BOM除去)→改行をLFへ正規化→末尾の改行を除去」したバイト列の
  SHA-256とし、範囲マーカー行自体は範囲に含めない(BEGIN行の直後からEND行の直前まで)。
  検査は次のすべて:
  (i)照合ブロックのパッケージ一覧が解析結果(同じ正規化・整列・除外適用)と完全一致
  (過不足・バージョン差異ゼロ。削除済み依存の残留も不一致として検出)。
  (ii)sdk行がビルドに使うSDKバージョンと一致。
  (iii)本文のランタイム転記範囲(RUNTIME LICENSE / RUNTIME NOTICES の各マーカー間)の
  正規化ハッシュが、ビルドSDK同梱の当該原本ファイルの正規化ハッシュと一致(本文の
  誤転記・SDK更新時の陳腐化を本文側で検出)。
  (iv)照合ブロックの各(ID,バージョン)が本文の見出し `## <ID> <バージョン>` と過不足なく
  対応し、各エントリに `license:` 行(非空)と `source:` 行があり、転記範囲の正規化
  ハッシュが「`source:` の指す転記元から連結規則どおりに生成した期待本文」の正規化
  ハッシュと一致すること(files指定=キャッシュ内ファイル、spdx指定=追跡標準本文)。
  (v)**網羅性・メタデータ検査**(依存更新時にも機械で再確認される): 各エントリの
  `source: files` の集合が、NuGetキャッシュ内の当該パッケージのライセンス・NOTICE類
  ファイルの機械列挙(名前パターン LICENSE*・NOTICE*・THIRD-PARTY*・COPYING*、大文字
  小文字無視、全階層)と一致すること(漏れゼロ)、`license:` 行がパッケージの
  nuspecメタデータのライセンス式と一致すること、**`source: spdx` 行を持つエントリでは、
  そのID集合が `license:` のSPDXライセンス式に現れる全ライセンスIDの集合と一致する
  こと**(複合式——AND/OR——は式中の全IDを必要本文とする。ライセンス本文を同梱する
  filesのみのエントリはこの検査の対象外)、および `source: files` のファイル集合に
  ライセンス本文ファイル(名前パターン LICENSE*・COPYING*)が1つも含まれない場合は
  `source: spdx` 行を必須とすること(NOTICEのみ同梱時のSPDX併記の省略を検出)。
- 検証手順書の検査一覧へ「パッケージ生成: `pwsh scripts/package.ps1` / 合格条件:
  スクリプトが成功し内容物検査を通過」を追記する。PowerShellスクリプトの構文検査は
  次のとおり確定する: `pwsh -NoProfile -File scripts/check-ps-syntax.ps1`(対象は
  `scripts/` 配下の全 .ps1。各ファイルを
  System.Management.Automation.Language.Parser の ParseFile で解析し、パースエラーが
  1件でもあれば終了コード1)。合格条件は終了コード0。この検査も検証手順書へ登録し、
  READMEの開発環境へ **PowerShell 7(pwsh)** を記す(Windows標準の powershell.exe とは
  別物のため)。

### 導入手順書(`docs/guides/installation.md` を新設)

- 利用者向け手順の**正本はパッケージ同梱の `README.txt` テンプレート**
  (`docs/guides/package-readme.txt`)とし、導入手順書はテンプレートへの参照と開発者向けの
  節で構成する(同じ手順を二重管理しない)。テンプレートは次の内容で作成する:
  - 前提: Windows 10(バージョン1903以降)または Windows 11 の x64/PMXエディタ
    (x64版)/Claude Code CLI。.NETランタイムの追加導入は不要(ブリッジは自己完結型、
    ホストが使う .NET Framework 4.8 は上記OSに同梱)。
  - 導入手順: (1)**専用の新しいフォルダを作成し**、その中へzipを展開する(既存の
    フォルダへ直接展開しない——アンインストール時にフォルダごと削除するため)。
    (2)`PmxEditorMcp.dll` をPMXエディタ導入
    フォルダの `_plugin\User` へコピーする。(3)`claude mcp add --scope user pmx-editor-mcp --
    "<展開先の PmxEditorMcp.Bridge.exe の絶対パス>"` で登録する(パスは空白を含み得るため
    **引用符で囲む**——テンプレートのコマンド例も引用符つきで記載する。**利用者向けの
    登録と削除はすべて `--scope user`(ユーザースコープ)で統一する**——実行
    ディレクトリに依存せず、どのプロジェクトからでも同じ登録を利用・操作できるため。
    開発者向けのローカルスコープ登録(03)とは別物であることをテンプレートに明記する)。(4)PMXエディタを
    起動し、Claude Code から `ping` ツールの応答("pong")で導入を確認する。
  - 複数エディタ起動時の扱い: **登録は一度だけで、エディタを起動し直しても登録し直さない**
    ことを明記する。接続先はブリッジが待ち受けているホストの列挙で決めるので、エディタが複数
    起動していても、ホストが待ち受けているエディタが1つなら自動で決まる。2つ以上のホストが
    待ち受けているときは接続先を決められないというエラーになり、候補のパイプ名が列挙される。
    その場合は、対象にしないエディタのプラグインメニューからホストを停止して待受を1つに絞る。
    あわせて、ツールの応答が先頭行で接続先のパイプ名を名乗ること、接続先が別のエディタへ
    移ったときはその旨が本文に出ることを記載する。
  - 更新手順(順序を確定): (1)Claude Codeのセッションを終了する(ブリッジプロセスの
    停止)。(2)PMXエディタを終了する。(3)展開先と `_plugin\User` の同名ファイルを新しい
    zipの内容で上書きする。(4)PMXエディタを起動する(ホストDLLは次回エディタ起動から
    有効——アーキテクチャ仕様書の確定挙動)。(5)Claude Codeを開始し、ping応答を確認する
    (エディタのプロセスIDが変わっても登録の操作は要らない)。
  - アンインストール手順(順序を確定): (1)Claude Codeのセッションを終了する(ブリッジ
    プロセスの停止。実行中はexeがロックされ削除に失敗するため)。
    (2)`claude mcp remove --scope user pmx-editor-mcp`。(3)PMXエディタを終了する。
    (4)`_plugin\User` の
    `PmxEditorMcp.dll` と、導入時に作成した専用の展開フォルダを削除する。
  - 開発者向けの節: リポジトリからの導入(`local.props` の `PmxEditorDir` 設定→
    Deployターゲット→開発時のMCP登録。ホストはアーキテクチャ仕様書、ブリッジは実装計画書03が
    確定した具体値を検証手順書から参照する)。
- README(リポジトリ直下)には概要と導入手順書へのリンクを追記する(READMEの本文は
  最小限を維持する。手順の正本は、利用者向けが `package-readme.txt` テンプレート、
  開発者向けが導入手順書の開発者向けの節、という分担のままとする)。

### 配布時の注意(導入手順書へ移送)

- PEPlugin.dll・PMXエディタ本体は配布物に含めず、含めてはならない(再配布禁止)。
  パッケージ生成の内容物検査でも混入を機械検査する。
- ホストDLLがブロックされた場合(ダウンロードしたzip由来のブロック属性)の解除手順
  (エクスプローラーのプロパティからの許可)は、利用者向け正本である
  `package-readme.txt` のトラブルシューティングに記載する(パッケージ単体で復旧手順が
  届くようにする)。

## 実装ステップ

1. ブリッジの自己完結型・単一ファイル発行を実測する(上記の発行プロパティ4点を明示した
   発行コマンドの成立と、**発行されたexeを空の一時ディレクトリへ単独コピーして**の起動・
   MCP initialize/ping応答——発行ディレクトリ内の残存DLLに依存しないことの確認)。
   成立しない場合は前提4の設計変更としてユーザーへ報告して停止する。除外リスト `docs/guides/package-excluded-packages.txt` を作成し、ホスト・
   ブリッジ両プロジェクトの `dotnet list package --include-transitive --format json` の
   和集合(除外適用後)と、各パッケージの同梱ライセンス・NOTICE類(他に同梱ファイルが
   無いことも確認)、必要なSPDX標準本文(`docs/guides/licenses/` へ転記)、ビルドSDK同梱の
   LICENSE.txt・ThirdPartyNotices.txt から、照合ブロック付きの
   `docs/guides/package-thirdparty.txt` を作成規則どおりに作成する。
2. `Directory.Build.props` へ `Version`(0.1.0)を定義し、ホスト・ブリッジが共有することを
   確認する。`scripts/package.ps1`(発行→zip→内容物検査)と
   `scripts/check-ps-syntax.ps1` を作成し、`dist/` を `.gitignore` へ追加する。
   パッケージ生成検査とPowerShell構文検査を検証手順書へ登録する。
3. `docs/guides/package-readme.txt`(利用者向け手順の正本テンプレート)と
   `docs/guides/installation.md`(テンプレート参照+開発者向けの節)を作成し、READMEへ
   概要とリンクを追記する。
4. 生成したパッケージを用い、READMEテンプレートの手順どおりに実機確認する(既存の
   開発用登録がある場合は一旦解除してから行い、確認後に元へ戻す): (a)新規導入
   (zip展開→DLL配置→MCP登録→エディタ起動→ping応答)。(b)更新手順(手順どおりの
