# pmx-editor-mcp 実装進捗

実装計画書01〜06の実行状況を記録する。新規の作業者(エージェント)はこの文書だけで
現在位置を把握し、続きから作業を引き継ぐ。

## 記録規則

- 実装は計画書01から番号順に進める。各ステップの完了時にチェックを付け、実行記録へ
  「ステップ・実行したコマンド・合否」を追記する。
- 計画書は実装完了後に削除される前提のため、本文書から**計画書ファイルへのMarkdown
  リンクを張らない**(計画書名はテキストとして記録する)。
- 本文書には進捗の事実だけを記録する(設計値・手順を書かない。正本は各仕様書・
  検証手順書)。
- 中断するときは引き継ぎ記録へ「現在位置・次の作業」を残す。
- **引き継ぎ記録に未解決事項を残さない。** その場で解決するか、担当する計画書へ書く。担当が
  無く必要性も示せないものは、書かずに捨てる。書けば片付いたように見えるが、何も解決していない。
- 受入検証の実行識別子は、下記「受入検証の実行識別子」の節へ値だけを記録する
  (生成・初期化・照合の手順と値の形式は検証手順書が正本)。

### 03-4 の実施方法と結果

登録は開発中のビルド成果物を指す形で行った。
[検証手順書のブリッジの実機動作確認](../conventions/verification.md#ブリッジの実機動作確認)の
操作列を、Claude Codeのヘッドレス実行1回=1セッションの中で、手順1から手順7まで書かれた順に
通した。手順のあいだのエディタ側の状態変更(起動・終了・プラグインメニューからの停止と開始)は
別のプロセスから行い、セッション側は合図を待つだけの使い捨てのスクリプトを挟んで待たせた。
メニューの操作はUI Automationで行い、状態表示の本文(状態・パイプ名・接続・応答サイズ予算・
ログの所在)も読んで確かめた。

セッションが呼んだ ping は全部で10回で、返った本文は次のとおりだった。エディタは順にA・B・Cと
起動し、それぞれのプロセスIDがパイプ名として本文へ現れている。

| 手順 | ping | 返った本文 |
|---|---|---|
| 1 | 1回目 | BRIDGE_NO_EDITOR |
| 2 | 2回目 | Aのパイプ名を名乗って pong |
| 3 | 3回目 | BRIDGE_CONNECTION_LOST |
| 3 | 4回目 | BRIDGE_NO_HOST |
| 4 | 5回目 | Aのパイプ名を名乗って pong |
| 5 | 6回目 | BRIDGE_CONNECTION_LOST |
| 5 | 7回目 | BRIDGE_MULTIPLE_HOSTS(AとBの候補がプロセスIDの昇順) |
| 6 | 8回目 | AからBへ変わった事実を伝えて pong |
| 7 | 9回目 | BRIDGE_CONNECTION_LOST |
| 7 | 10回目 | BからCへ変わった事実を伝えて pong |
