# 実装計画書03: MCPブリッジ基盤

pmx-editor-mcp の外部プロセス側=stdio MCPサーバー(ブリッジ)の基盤を実装する。個別の
MCPツールは含めない(ツール実装は実装計画書04)。ブリッジの設計値をここで確定し、完了時に
アーキテクチャ仕様書(`docs/specs/pmx-editor-mcp-architecture.md`)へ追記で移送する。

## 前提と裏取り

1. **公式MCP C# SDKで、本計画が依存する機能が動作する**
   - 出典: 記載なし(実装方式の選定のための実測)
   - 確かめた結果: .NET SDK 10.0.400・net10.0 で、NuGetパッケージ `ModelContextProtocol`
     2.2.0(+ `Microsoft.Extensions.Hosting` 10.0.0)を用いた最小サーバーを作り、
     (a) stdioトランスポートの構成、(b) 属性(McpServerToolType/McpServerTool)による
     ツール登録、(c) MCPクライアント相当のstdio対話での initialize・tools/list・
     tools/call の往復(pingがテキスト "pong" を返す)、(d) CallToolResult による
     isError=true+テキスト本文のエラー結果生成、のすべてを実測した。
2. **MCP経路の成立**
   - 出典: 能力台帳の「実機確認で確かめたこと」
   - 確かめた結果: stdioで改行区切りJSON-RPCを話すブリッジを `claude mcp add` で登録し、
     Claude Code CLIのヘッドレス実行からツール呼び出しが成功した(スパイクでは
     ハンドロール実装。本計画ではSDKに置き換える)。
3. **ホスト側IPC契約**
   - 出典: 実装計画書02の「IPCプロトコル」(確定済み設計値)
   - 確かめた結果: パイプ名はPID付き1本・handshake必須・改行区切りJSON-RPCサブセット・
     エラーコード表、が02で確定している。本計画はその契約のクライアント側を実装する。
4. **ツール定義への `_meta` 付与**
   - 出典: Claude Code の MCP ドキュメント(`code.claude.com/docs/en/mcp` の
     「Raise the limit for a specific tool」節)
   - 確かめた結果(一次資料): MCPサーバーは `tools/list` 応答のツール項目へ
     `_meta["anthropic/maxResultSizeChars"]` を宣言でき、Claude Code はそのツールの
     テキスト結果のしきい値を宣言値(ハード上限500,000文字)へ引き上げる。ツール契約は全ツールへ
     この宣言を付けることを設計値としている。
   - 確かめた結果(一次資料): `ModelContextProtocol.Core` 2.2.0 に同梱される
     ドキュメントXMLに、`ModelContextProtocol.Server.McpMetaAttribute` と
     `ModelContextProtocol.Server.McpServerToolCreateOptions.Meta` の記載がある。前者は
     「MCPサーバープリミティブ(ツール・プロンプト・リソース)のメタデータを指定し、
     `Tool.Meta` を埋めて `tools/list` の応答へ含める。`tools/call` の結果へは伝播しない」、
     後者は「`Tool.Meta` の初期値として設定する `JsonObject`」と記載されている。付与できるかどうかの
     分岐は無くなった。
   - **採る経路**: `McpServerToolCreateOptions.Meta` へ `JsonObject` を渡し
     `McpServerTool.Create` でツールを作る形とする。属性の側は採らない——属性の値は
     コンパイル時定数であるのに対し、付与する値は環境変数から実行時に決まり、対照実験の
     宣言あり/なしの切り替えも実行時に要るため、属性では表せないから。
   - **残る未検証**: 宣言した値をClaude Code側が実際にしきい値として使うかは、
     こちらの実装ではなくクライアントの挙動なので、対照実験(下記の設計値)で確かめる。

### MCPサーバーとしての構成(アーキテクチャ仕様書へ移送)

- トランスポートはstdio(SDKのstdioサーバートランスポートを使用)。サーバー名は
  `pmx-editor-mcp`、バージョンはブリッジのアセンブリバージョン。
- ログ・診断は標準エラー出力へ出す(stdioのプロトコルストリームを汚さない)。
- 基盤で登録するツールは `ping` のみ(ホストへ中継し、ホストの応答文字列を返す)。
  ツール群の登録機構は「1ツール=ホストの1メソッドへの中継」を基本形とし、ツール定義の
  一覧からの登録は実装計画書04が能力台帳・ツール契約に基づいて行う。
- 登録機構は、`tools/list` に出る各ツール定義へ `_meta` を付与できることを要件とする
  (付与する鍵は `anthropic/maxResultSizeChars` の1件)。**値は環境変数
  `PMX_EDITOR_MCP_BUDGET_CHARS` から取り、未設定時の既定は 100,000 とする**。構文と有効範囲は
  ホスト側と同一(ASCII数字のみの10進表記、符号・前後の空白・先頭のゼロ・ASCII以外の数字は
  受理しない。10,000 以上 500,000 以下)で、違反時は既定値へ落とさず**標準エラー出力へ理由を
  1行出して終了コード 2 で終了する**。この値を選んだ理由と、ホスト側のゲートとの内訳は
  共通契約仕様書が定める。
- **ホストとの予算一致**: ブリッジは起動時にホストへ接続しない(遅延接続の契約を変えない)。
  `tools/list` はブリッジ自身の設定値から応答する。ホストとの一致は**毎回の handshake で**
  応答の `budgetChars` を自分の値と照合して担保し、不一致なら接続を閉じて
  `BRIDGE_BUDGET_MISMATCH` を返す(プロセスは終了させない)。**回復の条件**: 不一致で閉じた
  接続は再利用せず、次のツール呼び出しで通常どおり新規に接続して handshake をやり直す
  (自動の再試行はその1回に限り、同じ呼び出しの中で繰り返さない)。そこで一致すれば通常の
  動作へ戻り、なお不一致ならまた `BRIDGE_BUDGET_MISMATCH` を返す。

### ホストへの接続(アーキテクチャ仕様書へ移送)

- 接続先パイプ名の解決順序:
  1. 環境変数 `PMX_EDITOR_MCP_PIPE` が定義されていればその名前(複数エディタ起動時の
     明示指定手段)。
  2. 未定義なら自動発見: プロセス名 `PmxEditor_x64` のプロセスを列挙し、
     ちょうど1個ならそのPIDから `pmx-editor-mcp-<PID>` を用いる。0個または2個以上なら
     ツール呼び出しに対してエラーを返す(0個: エディタ未起動の案内。2個以上: 候補の
     パイプ名を列挙し環境変数での指定を案内)。
- 接続のライフサイクル: ツール呼び出し時に未接続なら接続してhandshake(protocol=1)を行い、
  以後は接続を維持して再利用する。切断を検出したら次の呼び出しで再接続する。
  接続・handshake・ホスト要求の待機上限は125秒(ホスト側の処理タイムアウト120秒に
  往復の余裕5秒を加えた値)。
- 並行性: 同時に未完了となり得るホスト要求は1件に限る。接続確立(handshake含む)から応答
  受領までを排他区間とし、並行したMCPツール呼び出しは到着順(FIFO)の待ち行列で処理する
  (単純な排他だけでは順序が保証されないため、実装は順序付きの待ち行列とする)。
- 待機上限超過・読み取り中断・要求送信後のMCP呼び出しキャンセル時: その接続を無効化して
  閉じる(遅延して届く応答を次の要求の応答として誤読しないため)。次の呼び出しで新規に
  接続・handshakeする。実行されたか不明な要求を自動で再送しない。
- 待ち行列で未送信のMCP呼び出しがキャンセルされた場合: 待ち行列から除外するだけとし、
  接続は閉じない(応答待ち中の先行要求を巻き添えにしない)。
- 待ち行列から取り出された後、接続確立またはhandshakeの途中でキャンセルされた場合:
  その接続処理を中止し、部分的に確立した接続は閉じて再利用しない(排他区間内のため
  巻き添えになる先行要求は存在しない)。次の呼び出しで新規に接続する。
- エラーの変換: エラーはMCPツール結果(`isError`=true、テキストコンテンツ1件)で返し、
  本文は「エラーコード: メッセージ」の形式とする(ブリッジ自体は落とさない)。
  - ホストのJSON-RPC `error`: コードは `HOST_<数値コード>`(例 HOST_-32601)、メッセージは
    ホストのmessageをそのまま用いる。
  - ブリッジ内エラーのコード: `BRIDGE_NO_EDITOR`(エディタ未起動。起動の案内を含む)/
    `BRIDGE_MULTIPLE_EDITORS`(複数起動。候補のパイプ名を改行区切りで列挙し、環境変数
    `PMX_EDITOR_MCP_PIPE` での指定を案内)/`BRIDGE_CONNECT_FAILED`(接続の確立に失敗)/
    `BRIDGE_HANDSHAKE_MISMATCH`(handshakeの不成立。handshake処理中にホストが返す
    JSON-RPCエラー——プロトコル番号不一致の-32001を含む——と、handshake成功応答の
    内容不正——resultがオブジェクトでない・protocolが1でない・hostVersion欠落・
    `budgetChars` 欠落または数値でない——は
    HOST_ 形式ではなくこのコードへ変換し、接続を閉じる。分類の原則: handshake成立前の
    一切の不正はこのコード、成立後の応答不正は BRIDGE_PROTOCOL_ERROR)/
    `BRIDGE_BUDGET_MISMATCH`(handshake は成立したが、応答の `budgetChars` がブリッジ自身の
    応答サイズ予算と一致しない。両方の値を本文に含め、接続を閉じる。**毎回の handshake で
    照合する**ので、切断後の再接続でホストの設定が変わっていた場合もここで捕まる。ブリッジの
    プロセスは終了させず、一致するホストへ接続できた時点で通常の動作へ戻る)/
    `BRIDGE_CONNECTION_LOST`(応答待ち中の切断・読み取り中断)/
    `BRIDGE_PROTOCOL_ERROR`(handshake後のホスト応答の不正: JSON構造不正・要求と
    一致しないid・不正なUTF-8・サイズ上限超過。検出時は接続を無効化して閉じる)/
    `BRIDGE_TIMEOUT`(待機上限超過)/`BRIDGE_REQUEST_TOO_LARGE`(送信前検査での
    要求サイズ超過。要求は送信せず、接続は維持する)。
- 要求送信前の検査(IPCクライアント側): ホストへ送る要求本文のUTF-8バイト数を送信前に
  検査し、16MiBを超える場合は送信せず BRIDGE_REQUEST_TOO_LARGE を返す(ホスト側の
  -32004切断を誘発しない)。
- ホスト応答の検証(IPCクライアント側): 応答の読み取りはサイズ上限(16MiB)付きで行い、
  改行が来ない巨大応答も上限で打ち切る。厳格なUTF-8でデコードし、JSON-RPC応答構造
  (jsonrpc・id・result/error)と要求idとの一致を検証する。違反の分類は接続の段階で決まる:
  handshakeの応答受領まで(成立前)のあらゆる不正は BRIDGE_HANDSHAKE_MISMATCH、
  handshake成立後の応答不正は BRIDGE_PROTOCOL_ERROR とする。

## 実装ステップ

1. `src/Bridge/PmxEditorMcp.Bridge.csproj` と `tests/Bridge.Tests` を作成し、
   ソリューションへ追加する。
2. 接続先解決(環境変数・自動発見・0個/複数時のエラー文言)とホストIPCクライアント
   (接続・handshake・要求応答・並行呼び出しの直列化・切断検出と再接続・待機上限・
   上限超過時の接続破棄・応答の検証)を実装し、xUnitテストを書く(対象: 解決順序・
   0個/複数時のエラーコードと本文・ホストエラーからMCP結果への変換形式・テスト内に
   立てた名前付きパイプサーバーを相手にした handshake成功/プロトコル不一致・成功応答の
   内容不正(protocol不一致・result欠落・`budgetChars` 欠落等)が
   BRIDGE_HANDSHAKE_MISMATCH になること・**予算の環境変数の構文違反(符号付き・空白入り・
   先頭ゼロ・ASCII以外の数字・非整数)と範囲外で終了コード2で終了すること・`budgetChars` が
   ブリッジの予算と一致しない場合に最初のツール呼び出しの handshake で
   BRIDGE_BUDGET_MISMATCH になり接続が閉じられ、プロセスは継続すること・再接続時にも同じ
   照合が働き、一致するホストへ変われば回復すること**・
   接続再利用・切断後の再接続・応答待ち中の切断が BRIDGE_CONNECTION_LOST になること・
   handshake成立後の id不一致/構造不正/不正UTF-8/巨大応答の打ち切りが
   BRIDGE_PROTOCOL_ERROR になり、同じ不正をhandshake応答で発生させた場合は
   BRIDGE_HANDSHAKE_MISMATCH になること・送信前検査で16MiB超の要求が送信されず
   BRIDGE_REQUEST_TOO_LARGE になり接続が維持されること・
   待機上限超過とその後の接続破棄・並行呼び出しの直列化(要求の到着順どおりに処理される
   こと)・先行要求の実行中に待機中の後続呼び出しをキャンセルしても先行要求が完了し
   接続が維持されること・要求送信後のキャンセルで接続が閉じられ同一要求が再送されない
   こと・接続確立中またはhandshake途中のキャンセルで接続が閉じられ次回呼び出しが
   新規接続になること)。
3. SDKでstdioサーバーを構成し、`ping` ツール(ホスト中継)を登録する。プロジェクト作成時に
   前提4で確定した経路で `_meta`(`anthropic/maxResultSizeChars`)の付与を実装し、`tools/list` の応答に
   既定値が現れること・環境変数で上書きした値が現れること・**ホスト未接続でも自分の設定値を
   返すこと**を、xUnitテストで確認する。
4. ブリッジを `claude mcp add` で登録し、実機のPMXエディタとClaude Codeで実機動作確認
   (ping応答/エディタ未起動時の BRIDGE_NO_EDITOR 案内/エディタ2つ起動時の
   BRIDGE_MULTIPLE_EDITORS 候補列挙と、環境変数指定での接続成功)を行う。確認後、
   検証手順書の実機動作確認手順へ確定した具体値(登録コマンド・ツール名・期待応答・
   複数起動時の確認)を追記する。
5. 確定事項をアーキテクチャ仕様書へ追記で移送する(ブリッジの構成・接続解決・並行性と
   タイムアウト後の接続状態・エラー契約。本計画書にしか無い恒久情報を残さない)。
6. 全検査(ビルド・整形・テスト・スクリプト構文・実機動作確認)を実行して成立を確認し、
   進捗ドキュメントへ実行コマンドと合否を記録する。完了後、本計画書を削除候補として
   報告する(削除の実行はユーザーの指示があったときのみ)。
