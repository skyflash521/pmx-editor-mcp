# 実装計画書04: ツール群実装

能力台帳(`docs/specs/pmx-editor-mcp-capability-ledger.md`)の「提供」全能力をMCPツールとして
実装する。全ツールに共通するドメイン契約(共通契約)と、能力からツールへの写像規則をここで
確定し、完了時に共通契約仕様書(`docs/specs/pmx-editor-mcp-common-contract.md`)と
ツール仕様書(`docs/specs/pmx-editor-mcp-tools.md`)へ移送する。

## 前提と裏取り

1. **ツール化対象と担当区分**
   - 出典: 能力台帳(提供465能力に担当区分モデル/セッション/ビュー/変形・モーションを割当済み)
   - 確かめた結果: 台帳は生成の完全性ゲート(未処理型ゼロ+ドキュメントXML突き合わせ)を
     通過しており、要調査は残っていない。
2. **基盤契約**
   - 出典: 実装計画書02(IPCプロトコル・UIスレッド委譲・危険操作方針)・03(ツール登録機構・
     エラー変換)
   - 確かめた結果: ホストの直列処理(同時実行1)・エラー本文「コード: メッセージ」形式は
     ブリッジ基盤までの確定値とスパイク実測に基づく。ツール登録は、ブリッジ基盤が
     `McpServerToolCreateOptions` を渡す生成関数の形に確定させている(属性は採らない)。
3. **モデルアクセスの往復**
   - 出典: 能力台帳の「実機確認で確かめたこと」
   - 確かめた結果: UIスレッドへのInvoke経由で GetCurrentState からモデル情報(モデル名・
     頂点数)を取得してMCPクライアントへ返す往復が実機で成立した。GetCurrentState が複製を
     返し Update で反映する方式は一次資料で確認済み。Update・Undoの粒度は未実測のため、
     本計画は「Undo粒度がUpdate単位になること」を確定値とせず検証項目とする(下記のUndo
     契約参照)。
4. **SDK個別APIの仕様**
   - 出典: PMXエディタ配布物に同梱のSDKドキュメントXMLとプラグイン解説書(能力台帳の
     生成に用いた一次資料と同一)
   - 確かめた結果: 本計画の設計値が依拠する次の事実を該当記載で確認した:
     型別の解放API(UIモデルのRelease・イベントコネクタとイベントリスナの各Release・
     テキストコントロールのDispose)/UIモデルイベントリスナがUIモデルとイベントコネクタの
     両方に依存して作成されること/View・UIモデルの公開イベント種別/テクスチャ用Bitmapの
     32bit ARGB要件/LockUndoの保証範囲がUpdate時のUndo登録に限られること。
5. **Cプラグイン連携コネクタの保持可能期間**
   - 出典: 検証専用プラグインを実機のPMXエディタへ配置して行った実測
   - 確かめた結果: `GetCPluginRunArgsClone`(引数はホストプラグイン自身のモジュールパス)で
     取得したRunArgs複製の `Connector` を1個だけ保持し、`PXCBridge.BuilderInitialize`/
     `PrimitiveBuilderInitialize`・選択頂点インデックス取得・`GetCurrentPmx`・`ViewCtrl`・
     `SystemCtrl`・イベントコネクタの生成と解放、の各経路がいずれもその1個で成立した。
     名前付きパイプの切断・再接続をまたいでも、`InitializePMX` によるモデル初期化を
     はさんでも、同じコネクタで成立した。`ViewCtrl` から得たビュー制御のクライアント領域
     サイズは 730×562 であった(この値は出力画像の既定値の選定で参照する)。再取得するとRunArgs複製は別インスタンスになるが
     `Connector` は同一インスタンスを指す(参照比較で一致)。`ModulePath` は引数に渡した
     文字列がそのまま入るだけである(SDKドキュメントの記述どおり)。
     → 設計値「起動時1回取得・常駐保持・終了時破棄」は成立する。
   - **未検証として残るもの**: 経過時間は93秒までしか確認していない(数時間〜終日の放置後は
     未検証)/モデルの差し替えは `InitializePMX` のみで、PMXファイルを開き直した場合は
     未検証/エディタ終了時の後始末(破棄経路)は未検証。実施先は次のとおり。
     - 長時間放置: 自動E2E検査の `--soak` 経路(8時間。下記「行単位の検査は自動実行する」)。
       **これで覆えるのは数時間の放置までで、24時間の放置は未検証のまま残る**
       (残存リスクとして受容する)。
     - 終了時の後始末: 自動E2E検査の最終段でエディタを終了し、ホストのログにCプラグイン
       コネクタの破棄と全ハンドル解放の記録があることで判定する。この2つはホストのログの
       記録内容(起動・停止・接続・切断・エラー・処理タイムアウト)に含まれていないため、
       記録内容への追加をホスト基盤への追加要件として実装ステップで立てる。
     - **長時間放置とPMXファイルの開き直しに共通する注意**: 待機後・開き直し後にAPIが成功する
       ことだけを合格条件に
       すると、実装がその都度 `GetCPluginRunArgsClone` を再取得していても合格してしまい、
       「取得1回・常駐保持」の回帰検査にならない。**ホストのログへ「Cプラグインコネクタの取得」も
       記録し、検査の全区間を通じて取得の記録が1件だけであることを判定条件に含める**
       (この記録もホスト基盤への追加要件に含める)。
     - PMXファイルの開き直し: CAP-015(`IPEFormConnector.OpenPMXFile`)を用いる。一次資料
       (SDKドキュメントXML)で同シグネチャは PMXファイルパスを引数に取り真偽値を返すことを
       確認済みで、ファイルダイアログは開かない。よって自動E2E検査で消化する——検査専用の
       一時フォルダへ保存したPMXを開き直し、その後に**保持中の `IPXCPluginConnector` を
       直接の出所とするツール(選択頂点インデックスの取得。CAP-252)と、そのコネクタから
       接続初期化時に導出してホストが常駐保持する常駐アクセスオブジェクトを出所とするツール
       (ビュー制御のクライアント領域サイズの取得。CAP-277)**をそれぞれ呼んで正常応答に
       なることを確かめる(Cプラグイン連携でない経路のツールでは、保持中のコネクタが失効して
       いても成功するため検査にならない)。
     成立しない場合は取得タイミングの見直しを設計変更としてユーザーへ報告する。
6. **MCPクライアント側の応答サイズ上限**
   - 出典: Claude Code の MCP ドキュメント(`code.claude.com/docs/en/mcp` の
     「MCP output limits and warnings」節)
   - 確かめた結果: Claude Code はMCPツール出力が10,000トークンを超えると警告を表示し、
     既定の上限は25,000トークンである(環境変数 `MAX_MCP_OUTPUT_TOKENS` で変更可。警告の
     しきい値は固定)。注釈なしでしきい値を超えた結果は、会話へそのまま載らずディスクへ
     退避されてファイル参照に置き換えられる。ツールが `tools/list` 応答の
     `_meta["anthropic/maxResultSizeChars"]` を宣言すると、テキストコンテンツについては
     `MAX_MCP_OUTPUT_TOKENS` に依らずその値がしきい値になる(**ハード上限は500,000文字**)。
     画像コンテンツは注釈の対象外で、`MAX_MCP_OUTPUT_TOKENS` の対象のままである。
   - 突き合わせた実測: `IPXVertex` の全公開プロパティを本計画の値表現(SDXベクトル=数値配列・
     参照=index)で写像した頂点1件の、空白を除いたJSONは**431バイト**であった。1件がこの大きさ
     なので、一覧を500件返せば215,500バイトになる。しきい値はトークン数で定められており
     バイト数から一意に換算できないため、この大きさが上限に収まるかは確かめずには言えない。
     一覧系ツールの `limit` は、上限に収まることを確かめられる形で要素型ごとに定める。
   - **未検証**: `_meta["anthropic/maxResultSizeChars"]` を宣言したときの実挙動(しきい値が
     宣言値へ置き換わること)は出典の記述のみで、自分では測っていない。宣言手段の方は
     ブリッジ基盤が一次資料で確定させている(生成関数のオプションへJSONオブジェクトを渡す)ので
     未検証ではない。したがって応答サイズ予算は設定で変更可能に
     実装し、宣言が効くことを**宣言あり・なしのA/B対照**で
     **MCP経路の検査**で確認する——ホストのパイプ経路を叩く自動E2E検査ではクライアント側の
     退避を観測できないため、`claude -p` のヘッドレス実行で確かめる。**効かない場合は、
     文字数での予算設計そのものが成り立たない**——しきい値がトークン数で決まり、トークン数と
     文字数の換算は一次資料が定めていないため、安全な文字数を導けない。この場合は応答サイズ
     予算の再設計(固定モデルに対する代表応答のトークン数を実測し、その実測に基づいて予算を
     定める)を設計変更としてユーザーへ報告する。
   - **未検証**: 画像コンテンツが25,000トークンに対してどう数えられるか(寸法からの見積りか
     Base64の文字数か)は出典に記載が無く、測っていない。**出力画像の既定値はこの数え方に
     依存する**ため、既定の応答が警告になるかを実機で確かめ、必要なら既定を下げる(下記
     「値の表現」の出力画像)。

   → IPCの16MiB上限は名前付きパイプの上限であって応答サイズの設計目標ではない(実効
   上限はトークン数で定められており、バイト数の上限とは単位が異なる)。本計画の応答サイズ
   設計はこの上限から定める(下記「ページングと応答サイズ」)。
7. **ツール数と遅延読み込み**
   - 出典: Claude Code の MCP ドキュメント(`code.claude.com/docs/en/mcp` の
     「Scale with MCP tool search」節)と Tool search tool のドキュメント
     (`platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool`)
   - 確かめた結果: Claude Code はサーバーごとの固定のツール数上限を課さず、遅延読み込み
     (tool search)が既定で有効である。遅延対象のツールは1要求あたり最大10,000件。検索は
     ツール名・説明・引数名・引数説明を対象とし、既定で上位5件を返す。ツール説明文と
     サーバー説明は各2KB(バイト)で切り詰められる。遅延読み込みには `tool_reference` 対応
     モデル(Claude Sonnet 4.5 / Haiku 4.5 / Opus 4.5 以降)が要り、`ENABLE_TOOL_SEARCH` の
     `auto` は定義合計が文脈の10%に達した時点で遅延へ切り替わる。
   - 突き合わせた実測: 本計画の対象(台帳の提供465能力をシグネチャ単位へ展開すると1,447
     シグネチャ。同名オーバーロード集約後のツール数は1,354件)について、説明を1行の最小限に
     したツール定義JSONは**372,671バイト**(1件平均275バイト)、ツール名だけのJSONは
     **26,327バイト**であった。1,354件は上限10,000件の範囲内であり、遅延読み込みが働けば
     起動時に文脈へ載るのは26KB相当のツール名とサーバー説明のみである。
     → ツール数そのものは制約にならない。**ただしこの結論は遅延読み込みが働くことを条件と
     する**: 非対応モデルや `ENABLE_TOOL_SEARCH=false` では372KB相当の定義が文脈に載るため、
     本計画は対応モデルでの利用を前提とし、その旨をツール仕様書へ記載する。残る制約は
     **検索で意図したツールを引けるか**であり、下記「能力→ツールの写像規則」のツール名・
     説明文の設計で扱う。

## 確定する設計値

### 共通契約(共通契約仕様書へ移送)

- **状態の取得**: 読み取り系ツールはホスト側で値をキャッシュせず、呼び出しのたびに
  読み取り元から取得する。読み取り元は対象で決まる: 現在のPMX状態は `GetCurrentState`/
  ビュー・システム情報等はそのコネクタ/長寿命オブジェクトはハンドルの実体。
- **編集の分類と状態契約**: エディタの状態または外部へ作用するツールを3分類し、分類ごとに
  コミット点と失敗時の状態(未変更/変更済み/結果不明)を確定する。分類は次の順に評価し
  **最初に該当した一つ**とする(排他)。いずれの分類も処理全体を**単一のUIスレッド
  Invoke内**で実行する(途中にエディタの手動操作が割り込まない)。
  - 1: **複製編集型**(GetCurrentState→複製を変更→Update の経路を使うもの): コミット点は
    `Update` の成功。`Update` 前の例外は未変更。`Update` 自体の例外は結果不明(その旨を
    エラー本文に含む)。`Update` 成功後の表示更新の失敗は変更済みとして、警告を付けた
    成功応答を返す。
  - 2: **直接変更型**(上記以外で、SDK呼び出しがモデルデータ・長寿命オブジェクト・外部
    (ファイル等)へ作用するもの。頂点編集・ウェイト編集・初期化・UIモデル変更・保存等):
    コミット点は当該SDK呼び出しの正常返却。呼び出し前の例外は未変更、呼び出し中の例外は
    結果不明(その旨をエラー本文に含む)。
  - 3: **表示・セッション型**(上記以外の表示・設定・セッション操作。モデルデータ・
    長寿命オブジェクト・ファイルへは作用しない): 呼び出し前の検証エラーは未変更。
    呼び出し中の例外は結果不明として扱う(その旨をエラー本文に含む。モデルデータ・
    ファイルが変更されないことのみ保証する)。
  - タイムアウト・キャンセル時の状態は、ホストへの要求送信の前後で決まる(この注意を
    共通契約仕様書に明記する): 要求送信前の失敗・キャンセル(待ち行列・接続確立・
    handshake中。接続確立・handshake中のブリッジ125秒超過を含む)は未変更。要求送信後の
    タイムアウト・キャンセル・切断(HOST_-32002・BRIDGE_TIMEOUT・送信後キャンセル・
    BRIDGE_CONNECTION_LOST)は結果不明であり、クライアントは読み取りツールで状態を
    確認する。接続の扱いは02/03の確定契約どおり: ホストの120秒タイムアウト
    (HOST_-32002)では接続は維持され、遅延完了した処理の結果は破棄されて届かない。
    ブリッジの125秒超過・要求送信後のキャンセルではブリッジがその接続を破棄し、次回
    呼び出しで再接続する。
  - 警告はエンベロープの任意フィールド `warnings`(文字列配列)で返す(成功・失敗の
    どちらのエンベロープにも付けられる。ブリッジはMCPツール結果の本文に警告を併記する)。
- **表示更新の選択**: 複製編集型ツールが `Update` 後に呼ぶ表示更新は行ごとに確定する:
  能力対応表の複製編集型の行に必須列「更新指定」(`Update` へ渡す部分更新指定と、その後に
  呼ぶ表示更新APIの組)を設ける。既定は全体 `Update` の後に **モデル実体・フォーム一覧・
  描画のすべてを更新する(UpdateModel・UpdateList・UpdateView)** とし、部分更新を使う
  行は対応する部分指定と必要な更新のみを記す。一次資料で表示更新が不要とされる経路は
  その旨を記して省略する。
- **競合の制約**: エディタ上の手動編集とMCP操作の競合は検出しない(検出手段がSDKに無い)。
  この制約は共通契約仕様書に明記し、ツールは常に呼び出し時点の最新状態へ適用する。
- **インデックス参照**: 現在のPMX状態にあるオブジェクトの指定は、呼び出し時点の状態に
  おけるインデックス(0始まり)で行う。範囲外はドメインエラー `TOOL_INDEX_OUT_OF_RANGE`。
- **長寿命オブジェクトのハンドル**: PMX状態の外で生存するSDKオブジェクト(UIモデル・
  イベントコネクタ・イベントリスナ・テキストコントロール・ビルダ生成物等)は、ホストが
  接続単位のハンドルID(正整数)で保持し、ツールはハンドルIDで参照する。
  - 所有者はホスト。接続の切断・エディタ終了時にホストが全ハンドルを自動解放する。
  - ハンドルは生成に関与した依存元ハンドルの集合(複数可。例: UIモデルイベントリスナは
    生成元のUIモデルと、引数に取るイベントコネクタの両方)を記録し、解放は子→依存元の
    逆依存順で行う。いずれかの依存元の明示解放時は、依存する子を先に自動解放して失効
    させる。
  - 型別の解放方法: UIモデル=Release/イベントコネクタ=PXCBridgeのReleaseEventConnector/
    Viewイベントリスナ=IPXEventConnectorのReleaseViewEventListener/UIモデルイベント
    リスナ=IPXUIModelのReleaseEventListener/テキストコントロール=Dispose/ビルダ生成
    データ=参照破棄のみ。
  - 解放済み・不明・**期待する型と不一致**のハンドルは `TOOL_INVALID_HANDLE`。二重解放は
    2回目を `TOOL_INVALID_HANDLE` とする。
  - **タイムアウト破棄時の後始末**: ホストの120秒タイムアウト(HOST_-32002)で遅延完了
    した結果を破棄する場合、当該要求の処理が生成したハンドル(依存物を含む)はホストが
    破棄時に解放・失効させる(クライアントへ届かないハンドルIDを残さない。この後始末は
    ステップ1のテスト対象に含める)。
  - **解放失敗時の規則**: 逆依存順解放の途中で解放APIが例外を出した場合、当該ハンドルは
    台帳上**失効として記録**し(SDK側の解放は結果不明)、後続の解放は続行する。
    `session_release_handle` は失敗したハンドルを `warnings` に列挙した成功応答を返し、
    再試行はしない(失効済みのため以後は `TOOL_INVALID_HANDLE`)。切断・エディタ終了時の
    自動解放も同様に続行・記録する。
- **イベントの配送**: Viewイベント・UIモデルイベントはpull方式とする。ホストは購読中の
  イベントを接続単位のキュー(上限1000件。超過時は古い順に破棄)に蓄積する。push通知は
  提供しない。取得ツール `view_poll_events` の契約:
  - 引数: `limit`(既定100・最小1・最大1000。範囲外・非整数は `TOOL_INVALID_ARGUMENT`)。
  - 応答: `events`(各要素は `seq`=接続内で1から単調増加する連番・`type`=イベント種別の
    識別子・`sourceHandle`=そのイベントを購読しているリスナのハンドルID・`payload`=
    イベント固有値)・`dropped`=前回取得以降にキュー超過で破棄した件数(返却時に0へ
    リセット)・`remaining`=取得後のキュー残数。クライアントは `seq` の欠番と `dropped` で
    欠落を検知できる。
  - `type` の識別子はVMEテンプレートと同じ規則「宣言型名(IPX/IPE接頭辞を除き
    snake_case化)+ピリオド+イベント名(snake_case化)」で機械導出する(Viewリスナと
    UIモデルリスナの同名イベントも衝突しない)。全 `type` 分岐にわたる識別子の一意性を
    シグネチャ単位ゲートで検査する。
  - 排出は応答サイズ予算のホスト側判定点(下記の `value` ゲート)に収まる
    件数だけを1回の応答として分割せずに行う(超える場合は件数を減らして返す。単一イベントで超える場合は
    そのイベントを破棄して `dropped` に計上する)。
- **Undo契約**: 複製編集型のツールは1呼び出し=1回の `Update` 呼び出し。`LockUndo`/
  `UnlockUndo` は独立ツールとして公開しない(呼び出しをまたぐロックの残留を防ぐ)。
  代わりに**複製編集型ツール共通**の任意引数 `suppressUndo: true` に写像し、指定時は
  その呼び出し内で Lock→編集→Unlock を必ず対で実行する(編集・Updateの成否や例外の有無に
  よらず、最後に必ずUnlockする)。Unlockの失敗はロックを残留させない処置を行う: その場で
  1回再試行し、なお失敗した場合は「Undoロック残留」をホスト常駐状態(接続をまたいで保持)に
  記録して当該応答に明記する(Update成功後なら警告付き成功、それ以外は各分類の失敗時状態の
  ままエラー本文に残留を追記)。残留記録がある間は、各ツール呼び出しの冒頭・接続終了時の
  後始末・新規接続のhandshake直後、のそれぞれでUnlockの回収を試み、成功したら記録を解除して
  以後の最初の応答に警告で報告する。呼び出し冒頭の回収に失敗した場合、当該ツールが
  複製編集型・直接変更型なら `TOOL_OPERATION_FAILED`(Undoロック残留中のため中止)で実行
  せず返し、読み取り・表示・セッション型は実行して応答に警告を付す。台帳の
  CAP-004/005は、担当どおりセッション群の対応表に記載し、
  割当先を特定ツールではなく「共通引数 suppressUndo(共通契約)」とする(能力対応表には
  共通契約への割当を表す行種別を設け、シグネチャ単位ゲートはこの割当も割当済みと数える)。
  一次資料の
  LockUndo の保証はUpdate時のUndo登録に限られるため、直接変更型・表示・セッション型では
  `suppressUndo` を受け付けない(指定時は `TOOL_INVALID_ARGUMENT`)。「Undo粒度がUpdate
  単位になること」はエディタのUndo操作を要するため、手動確認一覧へ種別「契約」・(a)の類型で
  登録し、検証手順書の受入シナリオ「編集と取り消し」で検証する。確定した内容(Undo粒度が
  Update単位であること)はツール仕様書へ記す。
- **ドメインエラーの搬送**: ホストのツール系メソッドは、ドメインエラーをJSON-RPCの
  `error` ではなく `result` 内のエンベロープで返す: 成功は `{"ok":true,"value":...}`、
  失敗は `{"ok":false,"error":{"code":"TOOL_...","message":"..."}}`(どちらも任意で
  `warnings`)。
  ブリッジは `ok:false` をMCPツール結果の `isError`+「コード: メッセージ」本文へ変換する。
  成功時の変換も次のとおり確定する: MCPクライアントへ内部エンベロープは見せず、`value` を
  JSON文字列化したテキストコンテンツ1件として返す(構造化出力機能は使わない)。
  `warnings` がある場合は同じテキストコンテンツの末尾に「警告: 」行として併記する。
  画像を返すツールは画像コンテンツを先頭に置き、構造化値・警告があれば後続のテキスト
  コンテンツに載せる。`tool-schemas.json` の出力スキーマはMCP公開結果(`value` の構造)を
  記述する。
  ツール処理内で捕捉した例外(SDK呼び出し失敗・ファイル入出力失敗等)は
  `TOOL_OPERATION_FAILED` として例外の内容と状態契約上の帰結(未変更/変更済み/結果不明)を
  本文に含めて返す。JSON-RPCの `error`(03で HOST_ 形式へ変換)に残るのは、要求の解釈・
  ディスパッチ・応答生成などホスト基盤の異常(02のエラーコード表)だけとする。
- **ツールエラーコード**: `TOOL_INDEX_OUT_OF_RANGE`(範囲外)/`TOOL_INVALID_ARGUMENT`
  (引数の値が不正)/`TOOL_INVALID_HANDLE`(ハンドル不正)/`TOOL_CONFIRM_REQUIRED`
  (危険操作で `confirm: true` が無い)/`TOOL_NOT_APPLICABLE`(現在の状態・提供範囲で
  適用不能。理由を本文に含む)/`TOOL_OPERATION_FAILED`(実行失敗。上記)/
  `TOOL_RESPONSE_TOO_LARGE`(応答サイズ予算に収まらない。一覧系は件数を減らしても
  収まらない場合、それ以外は単体で超える場合。下記)。
- **ページングと応答サイズ**: 応答サイズの実効上限はMCPクライアント側で決まる(前提6)。
  IPCの16MiB上限は名前付きパイプの上限であって、ここでの設計目標ではない。
  - **応答サイズ予算**: 設定値(MCPクライアントへ渡るテキストコンテンツ全体の文字数)で、
    **未設定時の既定は100,000文字**。全ツールの `tools/list` 応答へ `_meta["anthropic/maxResultSizeChars"]` として
    同じ値を宣言し(ブリッジが付与する)、ゲートも同じ単位(文字数)で行う。宣言値とゲートを
    同値・同単位に揃えることで、バイト数・トークン数への換算に依らず判定できる。
    - 選定: 注釈のハード上限は500,000文字だが、これをそのまま使うと1応答で文脈の大半を
      占める。**ハード上限500,000文字の5分の1にあたる100,000文字を採る**——上限いっぱいを
      常用しないための余白を4倍取る、という比の方針である。**この値が文脈占有量について
      何かを保証するものではない**: 500,000文字はクライアント側の文字数の上限であって文脈窓の
      大きさではなく、応答が実際に消費する文脈量は内容によって変わる。トークン数との換算は
      一次資料が定めていないため根拠に使わない(宣言により、しきい値の判定は文字数で決まる
      ので換算は不要である)。予算値は設定で変更可能に実装する(前提6の未検証への備え)。
    - **計測対象と予約枠**: ブリッジが出力するテキストコンテンツは「`value` のJSON文字列化」
      に「`warnings` の『警告: 』行」を連結したものである(下記「ドメインエラーの搬送」)。
      **ホスト側の判定点(以下「`value` ゲート」)は `value` のシリアライズ結果に対する
      「予算 − 警告枠2,000文字」**であり、以下「予算内に収まる」はこの `value` ゲートを
      指す(**予算は設定値なので固定の文字数では書かない**。既定の予算100,000文字なら
      98,000文字になる)。`warnings` は
      「切り詰めた旨の注記を含めて」連結後2,000文字を超えないよう末尾を切り詰める。
      ブリッジは連結後の最終テキストを**予算そのもの**で再検査し、超える場合は
      `TOOL_RESPONSE_TOO_LARGE` を返す(ホスト側の見落としに対する最後の砦)。
  - **一覧系ツールの引数と応答**: `offset`(既定0・最小0)と `limit`(最小1)を受け取り、
    `total`(総数)・`items`・`nextOffset`(続きがある場合のみ)を返す。負数・非整数・
    範囲外は `TOOL_INVALID_ARGUMENT`。`offset` が `total` 以上の場合は空の `items` の
    正常応答とする。`view_poll_events` の `limit`(既定100・最大1000)は下記の型別逆算の
    例外とする(イベントは1件あたりの大きさが型で決まらず、予算内で分割しない排出により件数を制御
    するため)。例外である旨をスキーマ正本に記録し、規則適合検査の期待値に含める。
  - **`limit` の既定と最大は要素型ごとに逆算する**(全型共通の固定値は持たない。要素型に
    より1件あたりの大きさが1桁以上違うため): 共通契約の整備で要素型ごとに**1件あたりの想定文字数**
    を機械算出する。算出規則は、値範囲・長さ上限を持つ項目はその最大長、**長さ上限を持たない
    文字列項目(名前・コメント等)は想定長256文字**、配列・入れ子は要素の想定文字数×想定要素数
    (**要素数の上限が一次資料にあればその値、無ければ想定8要素**)とする。
    **256文字と8要素は実測でも仕様上の上限でもなく、`limit` の既定と最大を機械的に算出する
    ために置く取り決めである**。この2値の当否は応答が上限に収まることの保証には関わらない
    ——想定を超える応答は下記の件数縮小が吸収するので、誤差が効くのは安全性ではなく既定件数の
    使い勝手だけである。実運用で既定件数が過大・過小と分かった場合は、この取り決めを見直す
    (見直しは設計変更としてユーザーへ報告する)。そのうえで
    `最大` = (`value` ゲート − 一覧応答の枠1,000) ÷ 1件あたり想定文字数(切り捨て・最小1)、
    `既定` = `最大` の半分(切り捨て・最小1)とする。「一覧応答の枠」は `value` の内側の
    `total`・`nextOffset`・配列の構文分に充てる(`value` ゲートは `value` 全体に対する枠で
    あり、両者は入れ子の関係にある)。型別の値は**予算の設定値から算出する**ので、予算を
    変えた場合はスキーマ正本の再生成が要る(この依存を共通契約仕様書へ明記する)。型別の値は機械生成してスキーマ正本へ書き出し、
    手書きしない。**想定長は上限ではない**ため実際の応答が予算を超えることはありうる。
    それは下記の件数縮小が吸収する。
  - **予算超過時の挙動**: ホストは `value` ゲートに収まる件数だけを返し、`nextOffset` と
    `warnings`(要求件数と実際に返した件数を明記)で縮小を明示する。既定の呼び出しが
    エラーにならないことを優先する。先頭1件だけで `value` ゲートを超える場合に限り
    `TOOL_RESPONSE_TOO_LARGE` を返し、その旨を本文に含める。一覧系以外のツールで
    `value` が単体で `value` ゲートを超えた場合も `TOOL_RESPONSE_TOO_LARGE` とする。
- **値の表現**: 次の対応表で確定する。
  - SDXベクトル/行列: 数値配列(V2=[x,y]・V3=[x,y,z]・V4/Q=[x,y,z,w]・M=行優先16要素)。
  - 列挙型: 列挙子名の文字列。色: [r,g,b] または [r,g,b,a] の0〜1数値。
  - バイト列: Base64文字列。
  - 戻り値のないシグネチャ(void): 成功エンベロープの `value` は null とし、出力スキーマは
    null型として生成する。
  - 寸法・座標系のDrawing値: Size=[幅,高さ]・Point=[x,y]・Rectangle=[x,y,幅,高さ]。
  - フォント: `{family, size, style}`(styleは列挙子名)。ブラシ: Brush型の引数は色配列で
    指定し、ホストが単色ブラシを構築する(入力表現が色のみのため非単色ブラシは自然に
    対象外となる。シグネチャ自体は提供され、除外は不要)。
  - SDKオブジェクト参照(親ボーン・剛体の関連ボーン・SoftBodyの材質等): 要素の
    インデックス(整数)で表現し、「関連なし」はJSONの null で表現する。更新スキーマでは
    **項目の省略=変更しない**、**null指定=関連の解除**と区別する(nullを許容しない
    プロパティへのnull指定は `TOOL_INVALID_ARGUMENT`)。null許容の判定は一次資料の記載を
    正としてスキーマ正本の項目にnullable属性で記録し(参照型プロパティは既定で
    null許容)、参照型項目のnullable属性の存在をスキーマ対応検査に含める。null解除の
    実挙動は行単位の自動E2E検査の「null解除」で検証する。
  - System.Object(共有オブジェクト等): 任意のJSON値(null・真偽・数値・文字列・配列・
    オブジェクトの再帰構成)として写像し、ホストはJSON値と相互変換可能な形で保持する。
    取得した値がJSONで表現できない.NETオブジェクトの場合は `TOOL_NOT_APPLICABLE`
    (表現不能の旨を本文に含む)を返す。
  - 出力画像(ビューポート取得等): PNGのBase64とし、MCPの画像コンテンツとして返す。画像
    コンテンツは `anthropic/maxResultSizeChars` の対象外で `MAX_MCP_OUTPUT_TOKENS`
    (既定25,000トークン)の対象のままである(前提6)。応答サイズ予算はテキストコンテンツの
    値なので画像へは適用せず、**寸法で上限を定める**: 任意引数 `maxLongSide`(既定**512**・
    最小256・最大2048。範囲外・非整数は `TOOL_INVALID_ARGUMENT`)を受け取り、長辺がこれを
    超える場合は縦横比を保って縮小する。縮小した場合は元寸法と縮小後寸法を `warnings` に
    載せる。既定512を採る根拠は、**画像の数え方が未検証である以上、既定値は上限超過の
    可能性が低い側に置く**という判断である(前提6。寸法に比例する数え方なら余裕があるが、Base64の
    文字数で数えるなら大きい画像は上限を超えうる)。512は内容の判別に足りる大きさであり
    (前提5の実測で確認したビューポートの実寸730×562に対して約0.7倍)、より大きい画像が
    要る利用は `maxLongSide` で最大2048まで明示的に引き上げられる。**検証の範囲は既定512で
    クライアント側の警告が出ないことに限る**——`maxLongSide` は縮小のみで拡大はせず、
    ビューポートの実寸を超える指定をしても実寸の画像しか返らないので、長辺2048の応答は
    実機のビューポートをそれ以上に広げない限り作れない。したがって**最大2048の妥当性は
    未検証として残す**(引き上げは利用者の明示指定であり、警告が出ても既定の利用は損なわれ
    ない)。既定512で警告が出る場合は既定を下げる。
  - 入力画像(テクスチャ設定等): PNGまたはBMPのBase64で受け取り、ホストで32bit ARGBの
    Bitmapへ変換する(最大4096x4096。変換不能・形式不正は `TOOL_INVALID_ARGUMENT`)。
  - **網羅ゲート**: 提供対象全シグネチャの引数・戻り値型を機械的に列挙し、型→JSON表現の
    対応表を共通契約仕様書に網羅掲載する(未対応型ゼロを実装ステップ1の完了条件とする。
    上記で表現できない型が現れた場合は、計画外の設計変更としてユーザーへ報告する)。
- **危険操作**: `confirm: true` 必須の対象は次の3基準で判定する(02の方針の具体化。
  能力対応表の必須列「危険操作フラグ」に記録し、台帳の備考への「危険操作」追記も本計画の
  実装ステップで行う):
  (a) エディタ終了(CAP-006)。
  (b) ファイルへ書き込むシグネチャ(上書きの有無によらず常に確認必須。既知の該当:
  CAP-012/016のPMD・PMX保存、CAP-013の材質名保存、CAP-166のビュー設定保存、CAP-339の
  IPXPmxのToFile、CAP-445のIPEVmdのToFile)。
  (c) 現在のPMX状態を一括初期化するシグネチャ(CAP-007/014の初期化、CAP-339の
  IPXPmxのClearを現在モデル対象——`pmxHandle` 省略時——で呼ぶ場合。`pmxHandle` 指定時の
  Clearはメモリ上の生成物が対象のため確認不要)。
  対応表作成時に各群の全シグネチャへこの基準を適用し、該当行にフラグを付ける(既知の
  該当に漏れが見つかった場合も基準側を正とする)。基準(a)(b)(c)は機械述語として
  スクリプトに実装し、述語から導出した期待フラグ集合と対応表のフラグ・台帳の危険操作
  備考の三者一致をシグネチャ単位ゲートで検査する(フラグの欠落・過剰を独立に検出する)。
  述語は意味的な過剰一致を避けるため次のとおり確定する:
  (a)=フォームコネクタのClose。(b)=メンバー名がSaveで始まるかToFileであるもの
  (Save始まりでファイルへ書き込まないメンバーが存在しないことをステップ1のシグネチャ
  列挙で確認し、存在した場合は述語を宣言型×メンバー名の明示集合へ置き換える)。
  (c)=フォームコネクタのInitializePMD・InitializePMXと、IPXPmxのClearのcurrent経路の行
  (宣言型×メンバー名で特定。IPXMaterialMorphOffset等の別型のClearは該当しない)。

### VME(モーションイベント)の提供範囲(ツール仕様書へ移送)

- VMEの「宣言的な記述」は**事前定義テンプレート方式**とする: 提供するイベントは、VME
  Operator系能力が持つ**数値引数のオーバーロード**(値・速度・加速度等の定数指定)に対応する
  テンプレートをJSONで指定する形(`{type, target, frames, params}`)に限定する。
- デリゲート・ラムダを要するオーバーロード(StateProc系)と任意式の評価は提供しない。
  該当オーバーロードは除外一覧ファイルに登録し、能力台帳の該当能力の備考に「デリゲートを
  要するシグネチャは非対応」と明記して正本間の不一致を解消する(いずれも実装ステップ1で
  行う。シグネチャ単位ゲートの割当対象からも除外される)。
- テンプレートは裁量を残さず機械導出する: `type` は「宣言型名(IPE接頭辞を除き
  snake_case化)+ピリオド+メンバー名(snake_case化)」とし、同名メソッドを持つ別
  Operator型と衝突しない一意な識別子にする。`params` は該当シグネチャの引数を値表現の
  対応表で写像したもの、`target` は操作対象を一意に特定する組 `{kind, name, path}`
  (`kind`=アクセサ種別(ボーン・モーフ・カメラ・照明等)、`name`=対象名(カメラ等の
  単一対象では省略)、`path`=同一対象内に同種Operatorへの経路が複数ある場合のアクセサ名
  snake_case(カメラの位置・注視点・上方向等。一意なら省略))、`frames` は
  該当シグネチャのフレーム引数に従う(単一フレーム版は要素1つ、範囲版は[開始,終了]の
  要素2つ、フレーム引数を持たないシグネチャは `frames` を省略とし、`frames` の有無・
  要素数でオーバーロードを機械判別する)。**フレーム引数の識別はリフレクションで得られる
  引数名を正とし、名前集合は閉じたものとして確定する**(frame・start・end・frameSt・
  frameEd。ステップ1のシグネチャ列挙で実際の引数名を照合して確定し、この集合に無い
  フレーム相当の名前が現れた場合はユーザーへ報告する。同じ型の引数が複数あるオーバー
  ロードも引数名で判別する)。`frames` へ写像した引数は `params` から除外し、残りの引数を `params` とする。
  引数名から判別できない組み合わせが現れた場合は計画外の設計変更としてユーザーへ報告する。
  同一 `type` の同名オーバーロードは `frames` の有無・要素数と `params` の構成で機械判別
  できる場合に同一テンプレートへ集約する。テンプレート一覧は、VMDアクセサ階層(対象種別→アクセサ経路→
  Operator)とOperatorシグネチャの機械列挙から生成してツール仕様書に記載する(アクセサ
  経路の網羅と「`type`+`target` の kind/path+引数判別」の組の一意性をシグネチャ単位
  ゲートで検査する。ホストはこの組からSDK呼び出し先を一意に解決する)。
- 評価順・フレームの意味論はSDKのVME実行系に従う(独自の評価器は作らない)。

### 能力→ツールの写像規則(ツール仕様書へ移送)

- ツール名は `<群プレフィクス>_<snake_case動詞句>`。群プレフィクスは `model` / `session` /
  `view` / `motion`(台帳の担当 モデル/セッション/ビュー/変形・モーション に対応)。
  動詞句はシグネチャのメンバー名をPascalCaseからsnake_caseへ**機械変換**したものとする。
  出所修飾は常に**後置**とする: 型の公開メソッド(規則(b))は衝突の有無によらず型役割表の
  要素名詞(単数形)をメンバー名の後ろに付け(例: `model_clear_pmx`・`model_normalize_pmx`)、
  コネクタメソッドは同一群内で名前が衝突する場合のみ出所の型名(インターフェース名から
  IPX/IPE接頭辞を除きsnake_case化)をメンバー名の後ろに付けて区別する。この変換は
  スクリプトが行い、対応表のツール名が変換結果と一致することを規則適合検査で照合する
  (取り違え割当は名前不一致で検出される)。ツール名の群内一意も機械検査する(重複ゼロ)。
- **ツール説明文と検索での発見可能性**: ツールは1,354件になり、MCPクライアントは定義を
  遅延読み込みして**ツール名・説明・引数名・引数説明に対する検索**で必要なものだけを
  読み込む(前提7)。したがって説明文は文脈節約のための飾りではなく検索の入力であり、次を
  設計値とする。
  - 説明文は機械生成とし、先頭に「対象(型役割表の要素名詞)・動作・出所の型名」をこの順で
    置く。続けて台帳備考の契約注記(利用非推奨等)と一次資料の記載を載せる。
  - 説明文は**UTF-8で2,000バイト以内**に収める(クライアントが各2KBで切り詰めるため。説明文
    には日本語の契約注記を載せるので文字数でなくバイト数で数える。一次資料は「2KB」としか
    記しておらず2,000バイトか2,048バイトかを区別していないので、**安全側の2,000バイト**を
    採る)。上限超過は生成スクリプトのゲートで不合格とする。
  - **出所修飾の検査**: 「群内で衝突する動詞句」を機械的に定める——ツール名から出所修飾を
    除いた動詞句が同一群内で2件以上に現れるものを抽出する(語の例示に頼らない閉じた述語)。
    抽出された動詞句を持つツールについて、ツール名に出所修飾が後置されていること、および
    説明文の先頭に対象と出所の語が現れることをゲートで検査する。
  - **検索で意図したツールを引けるか**はゲートでは検査できないため、`claude -p` の
    ヘッドレス実行による**群単位の検査**として自動実行する(下記「行単位の検査は
    自動実行する」の末尾)。
- コネクタのメソッド能力は原則1能力=1ツール。get/setプロパティ対の能力は `get_<名>` /
  `set_<名>` の2ツールとする。プロパティ名が同一群内で衝突する場合(タブ選択・位置等が
  複数コネクタにある場合)も、メソッドと同じ規則で出所の型名を**後置**して区別する。
- **共通契約フローへの割当**: 現在PMXの取得・反映そのものであるシグネチャ
  (GetCurrentState・Update、およびPXCBridgeの同等のPMX取得・更新)は、独立ツールを
  設けず「共通契約への割当」行種別で対応表に記載する(CAP-004/005と同じ扱い)。これらは
  全編集ツールの複製編集フローと読み取りツール群の状態取得として内部実行され、IPXPmx
  全体をJSON値として往復させることはしない(モデル内容の読み書きはlist/get/update系
  ツールが担う)。同様に、PXCBridgeのビルダ初期化(BuilderInitialize・
  PrimitiveBuilderInitialize)はホストの起動時に内部実行する共通契約割当(内部フロー:
  接続初期化)とし、初期化に用いる `IPXCPluginConnector` は、ホスト起動時に
  GetCPluginRunArgsClone(引数はホストプラグイン自身のモジュールパス)で取得した
  RunArgs複製から1回だけ得て常駐期間中保持し、エディタ終了時に破棄する(再取得は
  しない)。GetCPluginRunArgsClone(CAP-078)自体も独立ツールとして公開せず共通契約割当
  (接続初期化)とし、台帳が要求する利用非推奨の注記は共通契約仕様書のこのフローの
  記述に明記する。**常駐アクセスオブジェクトの取得**(PXCBridgeのビルダ・プリミティブ
  ビルダ・ビュー制御・システム制御など、コネクタ型のオブジェクトを返すシグネチャ)も
  独立ツールを設けず共通契約割当(内部フロー: 接続初期化。戻り値はホスト保持の常駐
  アクセスオブジェクトへ束縛)とする——それらのメンバー機能はコネクタ型のメンバー写像で
  個別ツールに現れるため、取得自体は公開しない。**通常プラグイン側の入口**も同様に扱う:
  ホストはBootupで受領した IPERunArgs を常駐保持し(この保持要求は02の常駐基盤への
  追加要件として、ステップ1でアーキテクチャ仕様書に記載する)、各コネクタ・ビルダは
  IPERunArgs のルート(ホスト・コネクタ・ビュー等の経路専用型)からのプロパティ解決で
  取得する。経路専用型はコネクタ型として型役割表に載せ、その取得プロパティ・経路は
  共通契約割当(接続初期化。戻り値は常駐アクセスオブジェクトへ束縛)とする。**自動注入引数**: SDKシグネチャに現れる
  `IPXCPluginConnector` 型の
  入力引数(PXCBridgeの各メソッド等)は、行種別によらず(通常ツール行・共通契約割当行の
  双方で)ツールスキーマへ公開せず、ホストが常駐保持するコネクタを自動注入する。
  スキーマ対応検査は、通常ツール行では自動注入対象型の引数を公開スキーマの期待項目から
  除外して行に自動注入の記録があることを検査し、共通契約割当行では当該引数を束縛先
  スロット「自動注入コネクタ」へ束縛する(下記の閉集合に含める)。
  また、SDKの解放メソッド(UIモデルのRelease・イベントコネクタ/リスナの
  Release系・テキストコントロールのDispose)は独立ツール化せず共通契約割当とし、
  **`assignment` は `tool`・対象名は `session_release_handle`**、**`slotBinding` は
  ハンドル解放フローの各スロット**とする(割当先とスロット束縛を混同しないよう、分岐は
  `tool` の一択に固定する。解放は常に合成ツール経由で
  行い、ハンドル台帳の失効・依存子の先行解放と連動させる)。共通契約割当の行は
  「スキーマ上の対応」の代わりに**2つのフィールドを別々に**必須で持つ(同じ名前で二重に
  定義しない)。**`assignment`** はその行がどこへ割り当てられるかで、値は下記の行種別の節が
  定める3値の判別和(`tool`/`commonArg`/`internalFlow`)である。**`slotBinding`** は
  **シグネチャの全引数・戻り値(方向含む)それぞれの束縛内容**である。
  内部フローごとの**束縛先スロットは閉集合**として共通契約仕様書に定義する(複製編集
  フロー={PMX複製・更新種別(更新オブジェクト指定)・更新インデックス・Undoロック
  フラグ}/状態取得={PMX複製(戻り値)}/接続初期化={RunArgs複製(戻り値。常駐保持する
  コネクタとモジュールパスはこの複製のプロパティから抽出する)・モジュールパス(入力)・
  常駐アクセスオブジェクト(コネクタ型を返すシグネチャの戻り値)}/
  ハンドル解放={対象ハンドル}。加えて全フロー共通のスロットとして「自動注入コネクタ」=
  `IPXCPluginConnector` 型の入力引数への常駐コネクタの束縛、および「所有側オブジェクト」=
  ホストが保持するコネクタ・親オブジェクトへのレシーバーの束縛)。束縛検査の対象集合は、
  シグネチャの引数・戻り値に加えて、インスタンスメソッドの**レシーバー(this)**を含む。
  レシーバーの束縛規則: レシーバー自身が解放・操作の対象である場合(引数なしの
  Release・Dispose等)は「対象ハンドル」へ、それ以外(各コネクタ・引数ありの解放APIの
  所有側等)は「所有側オブジェクト」へ束縛する。スキーマ対応
  検査はこの行種別に対して、シグネチャから機械導出した引数・戻り値集合と束縛内容の
  **全単射**(欠落・重複ゼロ)、方向の一致に加え、各引数の期待スロット(引数の型・方向・
  名前からスロット種類を機械決定する。一意に決定できないシグネチャはユーザー報告)との
  一致を検査する。共通契約割当行の行単位検査は、束縛先を利用する代表ツールの自動E2E検査
  (suppressUndo指定の編集・状態取得を伴う読み取り・Cプラグイン初期化フローの成立・
  ハンドル解放・切断時に自動解放が実行されること)をその行の検査記録とする。Cプラグイン
  初期化フローの「取得1回で全連携APIが機能すること・IPC再接続後も同一コネクタを再利用
  できること」は前提5で実測済みであり、自動E2E検査では再現の確認にとどめる。
  エディタ終了経路の自動解放と終了時の後始末は、検査最終段のエディタ終了のあとホストの
  ログに全ハンドル解放と破棄の記録があることで判定する。
- **引数方向の写像**: 行キーとスキーマ正本の各項目は引数方向(in/out/ref)を持つ。
  `out` 引数は応答の項目へ写像し入力には含めない。`ref` 引数は要求と応答の両方の項目へ
  写像する。方向どおりの入出力割当をスキーマ対応検査で検査する。
- **オーバーロードのJSON判別**: 同一ツールへ集約する同名オーバーロードは、JSON写像後の
  入力(in・ref の必須項目の名前集合・型・配列要素数。`out` は含めない)で相互に機械判別
  できなければならない。
  判別できない組(例: 文字列版とバイト列版がどちらもJSON文字列になる場合)は同一ツールへ
  集約せず、相違する引数の**表現識別名**を付けた別ツールへ機械的に分割する。表現識別名は
  値の表現の対応表の各項目が持つ機械用のsnake_case識別子(文字列=text・バイト列=
  base64等。型→表現識別名の対応は共通契約仕様書の対応表で一意に固定する)であり、
  分割サフィックスはこの識別名を用いる(共有データ設定の分割例: 末尾に text / base64)。全ツールの全分岐のJSON判別可能性をシグネチャ単位ゲートで検査する。
- データ型能力(型単位)は、まず型の役割を次の判定で一意に決め、役割ごとの規則で写像する
  (判定はこの順に評価し、最初に該当した役割とする):
  0. **コネクタ型**(エディタ機能への接続点となる型のうち、**ホストが単一インスタンスを
     常駐保持するもの**: フォーム・ビュー・システム等の各コネクタ・ブリッジ・RunArgs等):
     インスタンスはホストが保持し、レシーバーとして公開入力を持たない。メンバーは
     コネクタのメソッド・プロパティの規則(1能力=1ツール・get/set)で写像する。
     接続単位で複数生成・解放される型(イベントコネクタ等)はこの役割に該当せず、
     ハンドル操作型として扱う。
  1. **イベント引数型**(公開イベントのハンドラ引数に現れる型): 独立ツールを作らず、
     読み取り可能な全プロパティを該当イベントの `payload` スキーマへ埋め込む。
  2. **ハンドル操作型**(ハンドルでのみ操作する型。UIモデル・テキストコントロール・
     VMD/VMEデータとその構成要素等): ハンドル参照を前提に規則(a)(b)を適用する。
     この型のインスタンスメンバーに対応するツールは、対象を指すレシーバーを**必須入力
     `handle`** として公開する。
  3. **操作対象型**(現在のPMX状態・エディタ状態の一部として編集・取得できる型。
     PMXデータとその構成要素——IPXPmx・頂点・材質等——を含む): 規則(a)(b)を適用する。
     この役割の型がビルダ生成物(ハンドル)としても現れる場合は、別ツールを設けず
     **対象切り替え引数**で同一ツールが両経路を扱う(下記)。
  4. **DTO型**(上記以外で、メソッド・ツールの入力または結果にのみ現れる型): 独立
     ツールを作らず、プロパティを方向別(応答へは読み取り可能な全項目・入力へは書き込み
     可能な全項目)に関連ツールの入出力スキーマへ埋め込む。
- **型役割表**: 上記の役割判定は意味的条件を含むため、判定結果は機械可読の型役割表
  `docs/specs/pmx-editor-mcp-type-roles.json` を正本として確定する(ステップ1で作成。
  母集合は「能力台帳の提供シグネチャに現れる型」——宣言型・引数型・戻り値型の推移閉包——
  に、**接続初期化の経路一覧(下記)に現れる経路専用型**(IPERunArgs・ホスト・コネクタ・
  ビュー等。台帳が行を作らない型)を加え、値の表現の対応表で写像される型(スカラー・
  文字列・列挙・配列とリスト・SDX・Drawing値・画像・ブラシ・フォント)を除いた残りとし、
  シグネチャ機械列挙から導出する。**経路一覧**: IPERunArgsのルートから各コネクタ・
  ビルダへ至る取得プロパティの列は、能力IDを持たないため能力対応表の行にはせず、
  ステップ1で機械可読の経路一覧として共通契約仕様書に確定し、接続初期化の束縛対象・
  過不足ゲートの母集合として照合する。経路一覧の各項目は**一意な経路キー**を持つ。
  **経路一覧の網羅ゲート**: リフレクションの到達グラフ(IPERunArgsを起点にプロパティを
  辿って到達できるコネクタ型・ビルダ型の集合)を機械導出し、型役割表の全コネクタ型・
  ビルダ型が経路一覧にちょうど1件の経路を持つこと(欠落・重複ゼロ)を、経路一覧とは
  独立のこの到達グラフと照合して検査する(一覧の手書きの縮小は照合で検出される)。
  経路専用型・コネクタ型の型役割挙動の検査は経路キー単位で記録し、検査記録の網羅ゲートは
  能力行キーと経路キーの双方の記録が揃うことを検査する。
  提供対象に現れない実装専用型は含まない。出現する全型が「値写像対象」と「型役割対象」の
  どちらか一方に過不足なく分類されること(重複・未分類ゼロ)をゲートで検査し、値写像
  対象は値の表現を正、型役割対象は型役割表を正とする)。各項目は型名・役割に加え、規則(a)の集約に使う要素の名詞(単数形・複数形。
  例: vertex/vertices)と、その型を扱うCRUDツール名(list/get/update/add/remove)を持つ。
  各項目は**判定根拠**(一次資料の該当記載への参照)を必須で持ち、根拠の欠落をゲートで
  不合格とする。役割判定の意味的条件そのものは静的なゲートでは検査できないため、行単位の
  自動E2E検査の「型役割」(ハンドル操作型=2個生成して異なるハンドルになり解放後は
  `TOOL_INVALID_HANDLE` になること/コネクタ型=公開入力なしで呼べること)で検証する。
  規則適合検査は型役割表を独立の期待値として参照し、全公開型が役割を持つこと(未割当
  ゼロ)と、対応表の担当・ツール名が型役割表と写像規則から導出される期待値に一致する
  ことを検査する。
- **対象切り替え引数**: PMXデータを対象とするツールは任意引数 `pmxHandle` を持つ。
  省略時は現在のPMX状態を対象とする(編集は複製編集型: GetCurrentState→Update)。指定時は
  ハンドルが指すPMXオブジェクトを対象とし、編集はその実体を直接変更する(直接変更型として
  扱う。Update・表示更新・Undo登録は行わず、`suppressUndo` は不可)。
- **要素の対象指定**: PMXの要素型(頂点・材質・ボーン等)を対象とするget・update系ツールは、
  相互排他の対象指定として `index`(現在のPMX状態または `pmxHandle` 先のリスト位置)
  **または** `handle`(ビルダ生成した未追加要素のハンドル)のどちらか一方を受け取る
  (両方指定・どちらも無しは `TOOL_INVALID_ARGUMENT`)。`add_` ツールは `handle` 指定の
  生成物を対象リストへ追加でき、**追加の成功はハンドルを消費して失効させる**(以後の
  参照は `TOOL_INVALID_HANDLE`。追加後はインデックスで参照し、同じ内容を再度追加するには
  再生成する)。追加の失敗時はハンドルは有効なまま残る。要素間の参照
  (ボーン参照等)はインデックスのみで指定する(未追加の生成物への参照は提供しない。
  必要な場合は先に追加してインデックスで参照する)。
- **経路別の行展開**: 行キーの経路成分は独立した3軸で表す。
  - **PMX対象軸** `pmx=current`(`pmxHandle` 省略)/`pmx=handle`(指定)。
  - **要素軸** `elem=index` / `elem=handle`(要素の対象指定を持つツールのみ)。
  - **親軸** `parent=index` / `parent=handle`(入れ子リストのツールのみ)。
  許容組合せの導出述語: **pmx軸を持つ(=`pmxHandle` を許容する)のは、対象解決の起点が
  インデックス経由の行のみ**であり、起点は親軸があれば親、なければ要素、どちらも無ければ
  PMX全体とする。すなわち (a)要素軸・親軸を持たないPMX対象ツールの全行、(b)親軸を持つ
  ツールの `parent=index` の行、(c)親軸を持たず要素軸を持つツールの `elem=index` の行。
  それ以外の行(親軸なしで `elem=handle`、または `parent=handle`)は対象がハンドル実体で
  確定するため pmx軸を持たない(`pmxHandle` の指定は `TOOL_INVALID_ARGUMENT`)。
  `parent=handle` の行の `elem=index` は親ハンドル内のリスト位置を指す。機械生成は、
  ツールが持つ引数種別から許容される軸値の直積をこの述語で絞って行を展開し、スキーマ
  対応検査は各行のキーの必須性・相互排他・許容組合せをこの述語から導出した期待集合と
  照合する。各行が独自の編集分類・危険操作フラグ・
  `suppressUndo` 可否を持ち、分類・危険性の経路分岐を行単位で表現する(行単位の
  検査はこの展開により親ハンドル経路——未追加の親への追加を含む——も対象に
  なる)。
- 規則(a)(b)(c)(d):
  (a) プロパティ群 → その型を扱う一覧・取得・更新ツール(例: `model_list_vertices` /
  `model_get_vertex` / `model_update_vertex`)。公開フィールドはプロパティと同じ規則で
  扱う。**アクセサ方向を機械判定**し、getterのみ・readonlyの項目は読み取り専用として
  get/list応答にのみ現れ、updateスキーマから除外する。setterのみの項目は更新のみ。
  コレクション型のgetterプロパティはコレクション規則(一覧・add/remove)で扱い、
  update対象にしない。スキーマ対応検査の「全プロパティ存在」は方向別の期待
  (応答=読み取り可能な全項目・update入力=書き込み可能な全項目)で照合する。
  (b) 型の公開メソッド → 1メソッド=1ツール(例: `model_normalize_pmx`・`model_clear_pmx`。
  所属は常に型の担当群とし、台帳の担当を正とする——ファイル入出力メソッドも例外に
  しない)。
  (c) 型・コネクタの公開イベント → `view_poll_events` の `type` 分岐へ写像する
  (イベントメンバー単位に展開し、対応表の行には担当する `type` 値と `payload` の
  スキーマを記す。リスナ作成ツールは対象イベント全種にホスト側ハンドラを登録して
  キューへ積み、リスナ解放時に購読を解除する)。
  (d) 公開コンストラクタ → ハンドル操作型の型は生成ツール(ハンドル返却)へ写像する。
  ツール名は `create_<型役割表の要素名詞(単数形)>` とする(メンバー名変換の例外規則)。
  同じ型を返すファクトリメソッドが提供対象に存在する場合はファクトリ側を生成ツールとし、
  コンストラクタは除外一覧のコンストラクタ重複カテゴリで除外する。複数コンストラクタは
  同一ツールのスキーマ分岐とし、引数構成で機械判別する(判別不能はユーザー報告)。
  イベント引数型・DTO型のコンストラクタは独立ツールを作らず、埋め込み先スキーマの入力
  からホストが内部で構築する(担当は「スキーマへの埋め込み」)。
- ビルダ系能力(PMX/VMD/VMEオブジェクトの生成)は、生成物を長寿命オブジェクトの
  ハンドルとして返すツールへ写像する(後続ツールはハンドルIDで参照する。未解放分は
  切断時に自動解放する)。
- **合成ツール**: SDKシグネチャに対応しない共通契約由来のツールは `view_poll_events`
  (イベント取得)と `session_release_handle`(明示解放。引数はハンドルID1つで任意の型の
  ハンドルを解放し、依存する子を先に自動解放して解放したハンドルIDの一覧を返す)の
  2つで閉じる。両者は能力対応表に行種別「合成ツール」として登録し、スキーマ正本にも
  載せる(過不足ゲートの期待集合に合成ツール2件を含める。これ以外の合成ツールを追加する
  場合は計画外の設計変更としてユーザーへ報告する)。
- 追加・削除を持つリストは、PMX直下の8種(頂点・材質・ボーン・モーフ・表示枠・剛体・
  Joint・SoftBody)に限らず、提供型のコレクション型プロパティを機械列挙して要素型ごとに
  `add_` / `remove_` ツールを設ける。入れ子リスト(材質の面・ボーンのIKリンク・モーフの
  オフセット等)のツールは、親要素の対象指定を**専用キー `parentIndex` / `parentHandle`**
  (相互排他)で受け取り、操作対象の要素自体の指定(`index` / `handle`)とはキーを分離する
  (未追加の親ハンドルへ未追加要素のハンドルを追加する要求も一意に表現できる)。

  持たせ、スキーマとディスパッチをそこから機械導出する。区分は次の2種:
  **所有コレクション**(要素の実体を保持。頂点・材質・IKリンク等。`add_` は生成物
  ハンドルを消費して実体を追加する)/**参照コレクション**(既存要素へのインデックス参照を
  保持。SoftBodyのピン等。`add_`/`remove_` はインデックス値の追加・削除であり、生成物
  ハンドルは取らない)。区分の判定は一次資料の記載を正として型役割表に記録し、区分
  どおりの挙動を行単位の自動E2E検査の「所有/参照コレクション」で検証する。
- **抽象要素型のコレクション**: コレクションの要素型が抽象基底(モーフオフセット等)の
  場合、型役割表の当該コレクション項目に**許容具象型の一覧**を必須で持たせる。許容
  具象型の機械述語: 型役割表の母集合内で当該基底型を継承し、他の型から継承されない
  **葉インターフェース**を列挙する(スクリプトがこの列挙と一覧の一致を照合する)。
  get系の応答要素には実行時型の判別子 `itemType`(具象型の識別名。型名のsnake_case変換)を
  含め、add/update系は `itemType` によるスキーマ分岐で具象型を選択する。`itemType` 分岐へ
  割り当てるのは具象型の**プロパティ・フィールド**に限り、具象型の**公開メソッド**は
  規則(b)どおり要素の対象指定を持つ独立ツールへ写像する(例: 材質モーフオフセットの
  初期化メソッドは独立ツール)。VME等の型階層にも同じ規則を適用する。

  担当(ツール名/pollの `type` 分岐/スキーマへの埋め込み(埋め込み先のツールまたは

  **更新指定**(複製編集型の行に必須。`Update` の部分更新指定と表示更新APIの組)・

    そろっていること・`observerTool` が実在するツール名であること・`observerArgs` の対応表の

    手書きの対応付けをしない(取り違えを排除する)。

### 実装の進め方(群ごとの縦切り)

**規模の実測**(台帳の提供行を、エディタのプロセス内でリフレクション列挙して得た公開APIの
一覧へ突き合わせ、シグネチャ単位まで機械展開して計数した): 提供シグネチャ 1,447
(モデル522/変形・モーション510/ビュー336/セッション79)、同名オーバーロード集約後の
ツール数 1,354、行単位の検査の対象となる**経路別行展開後の行数 2,268**(PMX要素1,200・
軸なし1,026・pmx直下42)。**これらはいずれも下限値である**——この列挙が入れ子公開型を
落としており、台帳の6行(CAP-467〜472)を突き合わせできていない。**実装ステップで型列挙を
直したうえで再計数し、確定値をツール仕様書へ記録する**。以下の規模の議論はこの下限値でも
成り立つ(2,268行を人手で確認できないという結論は、実数が増えれば強まるだけである)。
2,268行を人手で1行ずつ確認することは現実的でない。したがって**行単位の確認は実機エディタに
対して自動実行するE2E検査で行い、人手の確認は機械化できない類型に限る**(下記「行単位の検査は
自動実行する」)。人手の作業は「エディタを起動して検査コマンドを1回実行する」ことに固定し、
行数に比例させない。

群の実装順は モデル → セッション → ビュー → 変形・モーション。各群で次を繰り返す:
1. 群の能力対応表を作成する(シグネチャ単位へ展開し、全行に担当・入出力スキーマ・
   編集分類を確定する。シグネチャ単位ゲートを検査する)。
2. ホスト側に群のメソッドを実装する(02のラッパ層に追加。UIスレッド委譲・共通契約に従う)。
3. ブリッジ側に群のツールを登録する(03の登録機構でホストへ中継)。
4. 群の行のうち `observableChange` を持つものを**変化の基準結果へ初回追記**したうえで、
   **自動E2E検査**(下記)にかける。群の完了条件は**最終ゲートと同じ一般形**とする——群の
   全行が、**自動E2E検査で合格**・**イベント行の payload 変換のようにxUnitテストで全行
   網羅**・**手動確認一覧に種別「行」として登録され類型の機械述語を満たし実施先が特定されて
   いる**、のいずれかを満たすこと(未分類ゼロ・不合格ゼロ)。**その内側で、`observableChange`
   を持つ行だけ**に次の書き分けを適用する——基準結果が非空なら自動E2E検査で基準の集合との
   一致を判定し、基準結果が空なら手動確認一覧へ類型(c)として登録する。人手が行うのは**MCP経路の代表確認**(その群の代表1ツールを
   Claude Code から呼び出して応答を得る)だけで、**手動確認一覧の行は登録と実施先の特定まで**
   とし、実施と結果の記録は受入検証が行う。結果を進捗ドキュメントへ記録する。
   群内全行と群に属する経路キーの検査記録が揃うことが群の完了条件(記録の網羅は
   能力行キー・経路キーの照合で機械検査する)。
5. 群の対応表とスキーマをツール仕様書へ追記する。

### 行単位の検査は自動実行する

行単位の確認は、起動中の実機PMXエディタに対して**パイプ経由で行を実行する自動E2E検査**
(`scripts/e2e-tools.mjs`。既存の `scripts/e2e-check.mjs` と同じ経路)を主たる手段として行う。
**例外はイベント行**で、payload 変換の網羅は xUnit テストが担う(下記「イベント行の扱い」)。検査項目は
能力対応表とスキーマ正本から**機械生成**する(スキーマ正本は必須/任意・既定値・値範囲・
方向を持つため、下記の検査はすべてそこから導出できる)。人手が行うのは「エディタを起動して
検査コマンドを1回実行し、結果を記録する」ことだけとする。

**行種別(`rowKind`)ごとの検査の適用域**を先に決める(効果の導出はSDKメンバーへの
ディスパッチがある行にしか成り立たないので、行種別を分けずに「全行」と書くと適用できない行が
残る)。`rowKind` は能力対応表の必須フィールドで、担当の写像規則から**次の順に評価し最初に
該当した一つ**とする(排他)。**全行がちょうど1種別を持つこと(未分類・多重分類ゼロ)**を
ゲートで検査する。
- **1. `composed`(合成ツール)**: SDKメンバーへの1対1の中継でないツール。**`view_poll_events`
  と `session_release_handle` の2件**で、この2件がすべてであることをゲートで検査する。効果は
  導出せず**個別に確定する**——`view_poll_events` は読み取りで `postcondition` は `none`
  (排出の正しさはイベント行のxUnitと受入シナリオが担う)、`session_release_handle` は
  `handleConsumed` と `handleCascaded` を持つ。ディスパッチの呼び出し記録は求めない。
- **2. `commonContract`(共通契約割当行)**: 特別規則で共通契約側へ割り当てられる行。個別の
  ツールを持たないので `postcondition` を持たない。**`assignment` を次の3値の判別和で必須
  フィールドとして持つ**(単一のツールへ束縛される行だけではないため、ツール名だけを必須に
  すると正しい割当が表せない)。**対象名の実在を見るだけでは割当の取り違えを防げない**ので、
  **特別規則の表**を機械可読の正本として置き、`assignment` と `slotBinding` が
  そこから導出される値と完全に一致することをゲートで検査する。表は共通契約の整備で作る
  `docs/specs/pmx-editor-mcp-common-assignments.json` を正本とし、**項目はシグネチャ単位**と
  する——識別子は能力対応表の行キーと同じ**宣言型・メンバー名・引数型列・方向**の組で、
  宣言型とメンバー名だけの述語では持たない(同名オーバーロードは期待スロットが異なるため。
  全体更新と部分更新では更新種別・更新インデックスの有無が違い、メンバー名だけでは
  どちらの期待値を当てるか決まらない)。各項目は**その識別子**・**`assignment` の分岐と対象名**・
  **`slotBinding` の期待スロット**を必須で持つ。母集合は特別規則が対象とするシグネチャの全体
  (解放・破棄、Undo制御、現在状態の取得、更新の適用、ビルダの初期化、常駐アクセスオブジェクトの
  取得)を**オーバーロードまで展開したもの**とし、**この表の項目集合が能力対応表の
  `commonContract` 行の集合と行キーで完全一致すること**もゲートに含める(項目数と行数が
  一致するので、1項目が複数行を兼ねることも、同じ識別子の項目が複数並ぶこともない)。あわせて**対象側からの逆参照**
  を検査する——照合先は**この表を再集計した集合ではなく、実際のツール定義・共通引数の定義・
  内部フローの定義がそれぞれ保持する行集合**とする(同じ表から集めた集合どうしを比べても、
  表ごと誤っている場合に独立した歯止めにならないため)。
  - `tool`(ツールへの束縛。公開の解放・破棄メソッド等): ツール名を持ち、**そのツールが実在し
    `rowKind` が `composed` または `directDispatch` であること**をゲートで検査する(解放は
    合成ツールへ束縛されるので、直接ディスパッチ行に限定しない)。
  - `commonArg`(共通引数への割当。Undo抑止の指定等): 共通引数名を持ち、**その引数が共通契約の
    確定値に実在すること**をゲートで検査する。担保は共通契約のxUnitテストが行う。
  - `internalFlow`(内部フローへの割当。現在状態の取得・更新の適用・ビルダの初期化・常駐
    アクセスオブジェクトの取得等): フロー名を持ち、**そのフローが共通契約で確定した名前の
    集合に実在すること**をゲートで検査する。担保は編集分類の状態契約の検査が行う。
- **3. `eventBranch`(イベント行)**: `view_poll_events` の `type` 分岐。独立したツール呼び出しを
  持たないので `postcondition` を持たない。payload変換の網羅はxUnitテストが担い、経路の成立は
  受入シナリオのリスナ確認が担う。
- **4. `schemaEmbedded`(スキーマ埋め込み行)**: 独立したツールを持たず、他のツールの入出力
  スキーマへ埋め込まれる行。**DTO型のプロパティ**に限らず、**操作対象型・ハンドル操作型の
  プロパティ/フィールドをCRUDツールへ集約した行**と**イベント引数型のプロパティ**も
  ここに入る。`postcondition` を持たず、**埋め込み先(ツール名、またはイベントの `type`)を
  必須フィールドで持ち**、その検査で担保する(埋め込み先が実在することをゲートで検査する)。
- **5. `directDispatch`(直接ディスパッチ行)**: 上記のいずれでもなく、**独立したツールを持ち
  SDKメンバーへ中継する行**。コネクタメソッド由来のツール・型の公開メソッド由来のツール・
  公開コンストラクタ由来の生成ツール・`get_`/`set_` ツールがここに入る。`postcondition` と
  下記のディスパッチの呼び出し記録を**必須**とし、効果の導出規則はこの行種別にだけ適用する。

行の性質に応じて生成する検査:
- **ディスパッチの呼び出し記録**(直接ディスパッチ行の全行・全分類): `ok:true` とスキーマ適合だけを合格条件に
  すると、**何も呼ばずに正常応答を返す実装が全分類で合格してしまう**(戻り値のない行の
  成功値は `null` なので、とくに素通りしやすい)。これを塞ぐため、`PMX_EDITOR_MCP_DEBUG_HOOKS=1` の
  ときホストは次を行う。
  - **記録の場所と発行の順序を固定する**: ログ出力は、ツールからSDKメンバーへのディスパッチを
    行う**共通のディスパッチ処理の内側**で、かつ**SDK呼び出しから制御が正常に戻った後の
    継続でのみ**発行する(呼び出しと記録を同一の生成単位に置き、SDK側が例外を投げた場合は
    記録しない)。行ごとの実装コードからは出力しない。**この順序は観測できる**: 例外を
    起こす引数で呼んだときに記録が増えないことを検査に含めれば、記録が呼び出しの後段にある
    ことが確かめられる(記録だけを先に書く実装はここで落ちる)。
  - **記録の内容**: 行キー・**呼び出し連番**(ホストの生存期間で単調増加)・**応答値の
    ハッシュ**。ハッシュの対象は、**共通ディスパッチがSDKの戻り値を値の表現へ写した直後の
    正規化値**とする(写す前の生の戻り値ではない——列挙は列挙子名、SDKオブジェクトはindexか
    ハンドル、SDX・Drawing値は数値配列、というように写像で別物になるため、写す前の値と応答の
    `value` は原理的に突き合わせられない)。`out`・`ref` を持つ行は、応答として組み立てる
    オブジェクトを正規化値とする。戻り値のない行の正規化値は JSON の `null` とする。
    **正規化とハッシュの規則**: 直列化は **RFC 8785(JSON Canonicalization Scheme)** に
    従う(キーの整列は入れ子にも再帰適用、数値の表記、文字列のエスケープ、Unicodeの扱いが
    その仕様で一意に決まる。ホストはC#・実行器はNodeと別ランタイムなので、独自規則を置くと
    直列化結果が食い違いうる)。非有限数は正規化の前に不正として扱い、その行を不合格とする。
    そのUTF-8バイト列の SHA-256 の16進表記(小文字)をハッシュとする。引数と戻り値そのものは記録しない
    (モデルデータをログへ出さない方針を守る)。
  - **検査の判定**: 自動E2E検査は、呼び出しの直前にログ位置を記録し、呼び出し後に
    **その位置より後ろへ当該行の記録が新しく1件増えたこと**と、**応答の `value` から同じ
    正規化・ハッシュ規則で算出した値がログのハッシュと一致すること**を判定する。
  - **保証の境界を3つに分ける**(過大に主張しない)。検査の手段ごとに、何を証明できるかが
    違う。
    - **ホストの外で独立に確認できる**: `kind` が `file` の判定だけ。ファイルの存在・サイズ・
      読み直しはOSとファイルシステムが答えるので、**外部にファイル効果が起きたこと**は
      ホストの実装に依らず確かめられる。**ただしこれもSDKを呼んだ証拠ではない**——SDKへ
      渡さずホスト側で書き出す実装や、用意しておいたファイルを複製する実装も同じ効果を
      作れる。**どの検査もSDKへ到達したことは証明しない**——それを示すにはSDK境界へ
      差し替え層を置く設計が要り、本計画の範囲を超える。外部から独立に確かめられるのは
      ファイル効果までである。どの行がここに入るかは「書き込み先を指定する引数を持つ」と
      いう機械述語で決まり、集合として固定される。
    - **ツール間の契約整合を確かめる**: `readback`・`handle`・画像の `changed`、および上記の
      呼び出し記録とハッシュ照合。**これらはいずれも同じホスト実装を経由する**ので、SDKへ
      渡さずホスト内の代替状態へ保存し読み取りツールがそれを返す実装や、ハンドル台帳だけを
      操作する実装は通る。**したがってSDKへ到達した証拠ではなく**、ツール間の整合と実装の
      取り違え(ディスパッチが作った値の後段での差し替え、記録と応答の経路のずれ、過去の
      記録の使い回し)の検出である。
    - **呼べること以上は確かめられない**: `callLogOnly`。妥当な引数で呼べて応答が
      出力スキーマに適合することは全行と同じく確かめるが、**意味のある結果を返したかは
      確かめられない**。
    この3区分の内訳——各行がどれに入るか——をツール仕様書へ記載する。**「全行を検査した」とは
    書かず、行ごとに何がどこまで確かめられているかを示す**。
- **呼び出し可能性**(全行): 妥当な引数で呼び、エンベロープが `ok:true` で `value` が出力
  スキーマに適合すること(JSON Schemaによる検証)。行の経路キー(PMX要素の index/handle ×
  pmx軸、pmx直下、軸なし)ごとに実行する。**妥当な引数の合成規則**: 値範囲・長さ上限を持つ
  項目はその範囲内の中央値(整数項目は **床関数((最小 + 最大) ÷ 2)**。負の範囲でも
  一意に決まる)、列挙は先頭の
  列挙子、参照インデックスは事前操作で用意した要素の
  index、ハンドルは事前操作で生成したハンドル、共通引数は危険操作行の `confirm` を true、
  `suppressUndo` は未指定(受け付ける行では true の分岐も併せて実行)、`pmxHandle` は行の
  経路キーどおり(current経路なら未指定、handle経路なら発行済みハンドル)、
  それ以外は**型別既定サンプル値表**
  `docs/specs/pmx-editor-mcp-sample-values.json`(共通契約の整備で作成。全公開型に既定と
  第2の2件ずつ。2件は必ず異なる値とし、同一をゲートで不合格とする。
  文字列・パス・`System.Object`・入力画像Base64を含む)から採る。同表は値表現の網羅ゲートと
  同じ型集合を母集団とし、未割当ゼロをゲートで検査する(手書きの取りこぼしを防ぐ)。
- **事前操作**(検査に必要な最小の要素の用意): 行の経路キーと引数の参照先から機械導出する。
  PMX要素のindex/handleを取る行はその要素型を1件追加、親キーを取る行は親を1件追加、
  ハンドル引数を取る行は型役割表の生成ツールでハンドルを1件生成、入力ファイルのパスを取る行は
  検査専用の一時フォルダへ当該形式のファイルを1件用意、を導出規則とする(行ごとの手書きの
  手順は持たない)。**入力ファイルの用意は形式ごとに生成手段を定める**: 拡張子だけの空ファイル
  では正常呼び出しにならないため、形式→生成手段の対応を
  `docs/specs/pmx-editor-mcp-sample-files.json`(共通契約の整備で作成)へ持ち、各項目に次を必須で
  記す: 形式(拡張子)・生成手段の種別(本プロジェクトの保存系ツールで作る/型別既定サンプル値表の
  Base64を復号して書き出す)・**生成に使うツール名と引数**(前者の場合。例: PMXは空モデルを
  `SavePMXFile` 相当のツールで一時フォルダへ保存する)・**参照する型別既定サンプル値表のキー**
  (後者の場合)・生成前に必要な事前状態。提供対象のシグネチャに現れる入力ファイル形式の集合を母集団とし、未割当ゼロを
  ゲートで検査する。導出できない行は下記の手動確認一覧の対象とせず、導出規則の不足として
  規則を拡張する。
- **往復一致**(get/set対・複製編集型): 設定した値を読み戻して一致すること。値表現
  (SDXベクトル・列挙・色・Drawing値等)の相互変換の実地検査を兼ねる。
- **境界値**(値範囲を持つ項目): 最小・最大は成功、最小の1つ外・最大の1つ外は
  `TOOL_INDEX_OUT_OF_RANGE` または `TOOL_INVALID_ARGUMENT`。
- **既定値**(既定値を持つ任意項目): その項目を省略して呼び、読み戻しが既定値と一致する
  こと(一次資料からの誤転記の検出)。
- **null解除**(参照型項目): null を渡し、読み戻しが null であること。
- **所有/参照コレクション**: 追加で `total` が1増え、削除で戻ること。所有は消費した
  ハンドルが以後 `TOOL_INVALID_HANDLE` になること、参照はインデックス値が増減すること。
- **型役割**: ハンドル操作型は2個生成して異なるハンドルになり、解放後は
  `TOOL_INVALID_HANDLE` になること。コネクタ型は公開入力なしで呼べること。
- **編集分類**: 複製編集型は呼び出し後の読み戻しで反映を確認する。失敗時状態(未変更/
  変更済み/結果不明)は、意図的に失敗させられる行(範囲外・不正ハンドル・不正値)で
  読み戻しが分類どおりであることを確認する。
  **外部から観測できる効果を持つ行には、分類を問わず正常系の事後条件を必須とする**
  (直接変更型に限らない。表示・セッション型でも、カメラ視点の設定のように読み取り可能な値を
  変えるものは対象)。行ごとに `postcondition` を能力対応表の必須フィールドとして持たせる。
  **`postcondition` は下記の構造を持つ判定の配列**とし、1行に複数の効果があるときは複数
  並べて**すべて成り立つこと**を合格条件とする(所有コレクションへの追加なら「`total` が
  1増える」と「消費したハンドルが失効する」の2つ、ハンドル解放なら対象と依存する子ハンドルの
  失効を並べる)。各判定は**次の閉じた構造**で機械可読に定める。
  - `effectType`・`effectKey`: その要素がどの効果に対応するかの識別子。値と決め方は下記の
    効果の表による。この組が配列内で重複してはならない。
  - `kind`: `readback`(読み取りツールで読み戻して比べる)/`file`(ファイルの生成)/
    `handle`(ハンドルの状態変化)/`callLogOnly`(外部から観測できる効果を持たず、上記の
    ディスパッチの呼び出し記録だけを合格条件とする)の4値。
  - `observerTool`・`observerArgs`: `readback` と `handle` で必須(ただし `comparison` が
    `anyChanged` の要素では**書かない**——観測群は検査器が機械導出するので、行ごとの記述を
    持たない。書かれていたら構造違反として不合格とする)。観測に使うツール名と、
    引数の束縛。**束縛は式を持たず、「参照元 → 観測ツールの引数名」の対応表だけ**とする。
    **参照元は次の4つの名前空間に限る**(接頭辞で区別する。式・演算は持たない)。
    - `arg:<引数名>` — 検査対象の行へ渡した入力引数。
    - `result:<valuePath>` — 検査対象の行の応答から取った値(新規発行されたハンドルなどを
      観測ツールへ渡すために要る)。`valuePath` の書式は下記と同じ。
    - `setupOut:<名前>` — `setup` の操作が出力した値(操作ごとに出力名を1つ持つ)。
    - `before` — `comparison` が `changed` のときに、`setup` の後・検査対象の行の呼び出し前に
      観測ツールで取っておいた値。この保存は検査器が自動で行う(記述は要らない)。
  - `valuePath`: `readback` で必須(`comparison` が `anyChanged` の要素では書かない)。
    比較する値の位置。**観測ツールの応答の `value` そのもの
    (空文字で表す)か、`value` 直下のプロパティ名1つ**のいずれかとし、入れ子の指定は持たない
    (指定できない深さの値を比べる必要が出た場合は、その値を直接返す観測ツールを選ぶ)。
  - `setup`: 既知状態の用意が要る場合に、**次の閉じたタグの操作の列**を指定する(自由な手順は
    持たない)。各操作は `out`(出力名。省略時は出力なし)を持てる。失敗した場合は当該行を
    不合格とする。
    - `initPmx` — 空モデルへ初期化する。出力なし。
    - `addElement`(`elementType`) — その要素型を1件追加する。出力は追加した要素のindex。
    - `createHandle`(`toolName`) — 型役割表の生成ツールでハンドルを1件作る。出力はハンドルID。
    - `callTool`(`toolName`・`args`) — ツールを1回呼ぶ。`args` の束縛は上記の参照元に
      加えて、**JSONリテラル**と**型別既定サンプル値表への参照**(`sample:<型名>` で既定値、
      `sample2:<型名>` で第2の値)を取れる(読み取り行の既知状態を作るには、書き込み行へ
      渡す具体値がここに要る)。出力は応答の `value`。
    - `makeFile`(`format`) — サンプルファイル表の規則で一時フォルダへファイルを1件作る。
      出力はそのパス。
  - `comparison`: `changed`(事前値と異なる)/`equals`(`expected` と一致)/`exists`(存在
    する)/`invalidated`(以後その値をハンドルとして使う呼び出しが `TOOL_INVALID_HANDLE` に
    なる)/**`deltaEquals`**(事前値との差が `expected` の数値に等しい。件数が1増えることを
    `1` で表す)/**`anyChanged`**(機械導出した観測群のうち少なくとも1つが事前値と異なる。
    `observableChange` 専用で、観測先を行ごとには書かない)の6値。
  - `expected`: `equals` のとき必須。**JSONのリテラル**、または上記の参照元1つ(接頭辞付き)
    のいずれか。参照元を使えば「設定後の値が、その行へ渡した入力値と等しい」を
    `arg:<引数名>` で表せる。演算や合成は持たない。
  - `teardown`: 検査後に戻す必要がある場合に、`setup` と同じタグの操作の列を指定する。
  - `kind` が `file` のとき、検査するパスは `effectKey` が指す引数から取る(別途の指定を
    持たない)。
  **`kind` は行全体ではなく効果ごとに選ぶ**(配列の各要素が1つの効果に対応する)。効果は
  **`effectType` と `effectKey` の組で同定する**——`effectType` は下表の閉じた9値、
  `effectKey` はその効果を行の中で一意にする文字列(引数名・取得メンバー名・コレクション名の
  いずれかで、`effectType` ごとに下表が定める)。行が持つ効果の集合はシグネチャ・型役割・
  コレクション区分から**機械導出**し、**`postcondition` の配列がその集合と
  `(effectType, effectKey)` をキーとして完全一致すること(過不足ゼロ)**をゲートで検査する
  (所有コレクションへの追加で「`total` の増加」だけ書いて「ハンドルの失効」を落とすと、
  集合と一致しないので不合格になる)。**`kind` と観測方法は `effectType` から一意に定まる**
  ので、述語の適用順は要らない。1つの行が複数の `effectType` を同時に持つのは効果が複数ある
  ということであり、競合ではない(所有コレクションへの追加は `countChanged` と
  `handleConsumed` の2つを別要素として持つ)。ただし `observableChange` だけは他の効果種別が
  1つでも導出された行には付かない(下記のフォールバック限定)。

  **操作の向き**(`read`/`write`)を能力対応表の必須フィールドとし、下表の導出条件が使う。
  判定は機械的に行う——**一次資料でプロパティの get アクセサーとして現れるメンバー、および、戻り値が
  `void` でなく `out`・`ref` を持たず、名前が `Get`・`Is`・`Has`・`Can`・`Find`・`Search` の
  いずれかで始まるメソッド**を `read`、それ以外を `write` とする。未割当ゼロをゲートで検査
  する。`write` を `read` と誤って判定した行は、対になる書き込み行が見つからず `none` へ
  落ちるだけで、誤って合格にはならない。

  | `effectType` | 導出条件 | `effectKey` | `kind` | 観測と `comparison` |
  | --- | --- | --- | --- | --- |
  | `fileWritten` | **危険操作の基準(b)の述語に該当**し、パス型の引数を持つ | そのパス引数名 | `file` | そのパスに対する `exists` |
  | `handleConsumed` | 引数にハンドルを取り、型役割表でそのハンドルを消費・失効させると定義されている(所有コレクションへの追加を含む) | その引数名 | `handle` | `invalidated` |
  | `handleCascaded` | 解放・除去によって、引数に取っていないハンドルが従属して失効する | 失効する側を発行した生成ツール名 | `handle` | `invalidated` |
  | `handleCreated` | 型役割表で**生成ツール**と定義されたメンバー(ハンドルを新規に発行する行) | 発行するハンドルの型名 | `handle` | 応答のハンドルが有効であること(`exists`)。**同一性(2個生成して異なること)と解放後の失効は型役割の検査が担う**ので、ここでは重ねて書かない |
  | `countChanged` | コレクションへの追加または除去(所有・参照の区分を問わない) | コレクション名 | `readback` | そのコレクションの件数を返すツールで `deltaEquals` |
  | `stateWritten` | 同一宣言型に、そのメンバーが書く状態を返す公開の取得メンバーが**1つに定まる**(対応規則は下記の3つ) | その取得メンバー名 | `readback` | `equals`(`expected` は書き込んだ引数を `arg:` で指す) |
  | `observableChange` | 操作の向きが `write` で、**他のどの効果種別も導出されず**、**観測群**(下記)が空でない | 空文字 | `readback` | 観測群を呼び出しの前後で読み、**少なくとも1つが変化**(`anyChanged`) |
  | `valueRead` | 操作の向きが `read` で、その値を書く行が下記の対応規則で1つに定まる | そのメンバー名 | `readback` | `setup` で既知状態を作り `equals` |
  | `none` | 上のいずれも導出されない | 空文字 | `callLogOnly` | ディスパッチの呼び出し記録のみ |

  `fileWritten` は**述語を新たに置かず、危険操作の基準(b)をそのまま正本として使う**
  (述語を二重に持つと、片方だけが取りこぼしを直したときに食い違うため)。基準(b)に該当しても
  パス型引数を持たない行(書き込み先を選べない保存)は `fileWritten` を導出しない——この
  分岐の扱いは危険操作の4分岐が定める。`Open`・`Load`・`Import` のパス引数は入力元なので
  該当しない。

  **書き込みと読み取りの対応規則**(`stateWritten` と `valueRead` が共有する。いずれも
  対応先が**1つに定まる場合に限り**導出し、複数候補があれば導出しない)。
  - **set接頭辞とget接頭辞の同名**。
  - **`Update` 接頭辞と同名の取得メンバー**。
  - **引数の一致**: 取得メンバーが**1つ以上の引数を持ち**、その全引数が書き込みメンバーの
    引数と**名前と型で一致**し、書き込みメンバーがそれに加えて持つ値の引数が**ちょうど1つ**
    である。名前が対称でない対(キーを取る共有データの設定と取得のような組)を、宣言表を
    作らずに機械で結べる。引数を取らない取得メンバーをこの規則で結ばないのは、条件が空虚に
    成立して無関係な対ができるのを防ぐため。追加の値引数が2つ以上ある書き込みは、`expected`
    が参照元を1つしか取れないので対応を導出せず、`observableChange` が引き受ける。

  **観測群**は次の3つの合併から機械導出した集合とする。
  - **(i)** 検査対象の行の宣言型に属する、**引数を取らない公開の取得メンバー**。
  - **(ii)** 同じ宣言型の取得メンバーのうち、**全引数が検査対象の行の引数と名前・型で
    一致するもの**(キー付きの設定・除去を、そのキーの取得メンバーで観測する)。
  - **(iii)** **モデルの持続状態を表す固定の集合**——PMXルートの全要素型の件数と現在パス。
    宣言型の外へ広げるのはここだけで、集合は固定なので行ごとの判断を要さない。
    宣言型がフォームコネクタである操作(ファイルを開く・初期化・元に戻す/やり直す)は、
    効果がモデル側に出るため、この集合が無いと観測できない。
  `observableChange` はこの集合を呼び出しの前後で一括して読み、少なくとも1つが変化する
  ことを求める。**これが、対になる取得メンバーが1つに定まらない書き込み——除去・元に戻す・
  やり直す・ファイルを開く・初期化のような操作——を、宣言表を作らずに no-op から守る**。
  **ただし守れる範囲は「他の編集や遅延更新が無い静止環境での検出」に限る**——事前観測・
  対象の呼び出し・事後観測の3手を不可分にする契約は無いので、2回目の事前観測より後に別要因で
  値が動けば、対象が何もしていなくても変化が観測されうる(自動E2E検査は他の操作を同時に
  走らせない専用の実行として動かすが、それは運用上の前提であって契約ではない)。厳密に
  塞ぐには観測列の不可分化か因果を識別する仕組みが要り、本計画の範囲を超える。この限界も
  保証の境界としてツール仕様書へ記載する。

  **偶然の変化を拾わないための3つの制限**を置く。
  - **フォールバックに限る**: 他の効果種別が1つでも導出された行には `observableChange` を
    導出しない。保存やハンドル生成・解放へ無関係な変化の要求が加わって、正しい実装が
    落ちるのを防ぐ。
  - **静止確認**: 呼び出しの前に観測群を**2回続けて読み**、その間に値が動いたメンバーは
    その行の観測群から外す(遅延反映や別要因で動く値を判定に使わない)。外した結果として
    観測群が空になった行は `none` へ落とす。
  - **合否に算入する条件**: 観測群に**引数一致のメンバー**((ii))が1つ以上あれば、それは
    その書き込みが指した状態そのものを読むので、**変化しないことを不合格とする**。引数を
    取らないメンバーだけの場合は、**編集分類が複製編集型・直接変更型のときに限り不合格と
    する**——この2分類は定義上モデルデータ・長寿命オブジェクト・外部へ作用するので、
    読み取れる値のどれかが動くことを要求できる。**表示・セッション型で引数一致のメンバーも
    無い行**(再描画の指示のように、読み取れる値を変えない契約のもの)は、変化の有無を
    **記録するだけで合否に算入しない**——正しい実装を落とさないため。この記録は残余の
    一覧を狭めるのに使う。
  **変化が起こりうる事前状態を作る**。`observableChange` の `setup` は**固定の並び**とする
  ——`initPmx` → **到達できる全要素型を1件ずつ `addElement`** → **さらに1件 `addElement`**
  → **その追加を元に戻す**(`callTool` で元に戻す操作を1回)。最後の2手を置くのは、**元に
  戻す履歴とやり直す履歴の両方を空でなくする**ためである(全要素型を追加しただけでは
  やり直す履歴が空のままで、正しく実装されたやり直しでも何も変わらず落ちる)。この並びで
  モデルは初期状態から離れ、初期化は各要素の件数が、元に戻す/やり直すはそれぞれの操作回数と
  モデル内容が、ファイルを開くは現在パスとモデル内容が、動きうる状態になる(空のモデルへの
  初期化・履歴が空での元に戻す/やり直す・同じファイルを開き直す、のように**もともと何も
  変わらない呼び出しを検査対象にしない**ため)。**書き込む値も事前値と必ず異なるものを選ぶ**——型別
  既定サンプル値表は全公開型に**既定と第2の2件**を持ち、事前値が既定と一致する場合は第2を
  使う(同じ値を書いて変化が出ないのを、実装の不作為と取り違えないため)。
  **それでも変化が起きない行がある**——既に正規化済みのモデルへの正規化、実質的に何も
  加えない取り込みのように、**正しい実装でも冪等になる**呼び出しである。事前状態が起動直後と
  違うかを見るだけではこれを区別できない(事前操作は必ず状態を動かすので、除外条件に入らない)。
  そこで `anyChanged` は**基準結果との比較**で判定する。
  - **基準結果の初回生成は群ごとに行う**(全対象行を一度に呼べるのは全群の実装が終わった後
    なので、一括生成にすると各群の完了条件を評価できない)。**群の実装が終わった時点で、その群の
    行だけを実行して基準結果へ追記する**。追記は当該群の行に限り、既存の行を書き換えない
    (書き換えは下記の再生成の条件でのみ許す)。群の完了条件は、追記後の基準結果を使った
    自動E2E検査の合格と、類型(c)の登録である。
  - **基準結果の取得**: 上記の群ごとの実行で、対象行について固定の事前操作と呼び出しを
    実行し、**観測群のうちどのメンバーが変化したかの集合**を行ごとに記録して
    `docs/specs/pmx-editor-mcp-change-baseline.json` へ書き出す(機械生成。手書きしない)。
    真偽値でなく**変化したメンバーの集合**を持つのは、期待した状態でなく無関係な観測値を
    変える実装を通さないためである。
  - **以後の判定**: 基準結果が空でない行は、**その実行で変化したメンバーの集合が、基準結果に
    記録された集合と完全に一致すること**を合格条件とする(欠けても増えても不合格。欠けるのは
    働かなくなった回帰、増えるのは意図しない副作用なので、どちらも見逃さない)。基準結果が
    空の行は、その事前状態では変化を要求できないので**記録のみ**とする。
  - **再生成は初回生成と別の操作として扱う**(初回生成は未記録の行への追記、再生成は記録済みの
    行の書き換え)。**基準結果の再生成を制限する**: 再生成してよいのは**SDKの版・固定の事前操作・
    サンプルファイル表・ツール契約の設計値・**観測群の規則・効果の導出規則・基準結果の生成
    規則**が変わったとき**だけとする(類型(c)の超過を解消するために観測群の規則を広げる操作は、
    記録済みの空集合を書き換えるので再生成に当たる。この条件を含めないと超過時の第一の出口を
    選べない)。通常の実装修正では
    再生成しない(再生成を許すと、回帰をそのまま新しい基準へ取り込んでしまう)。再生成時は
    **前後の差分を出力し、変化しなくなった行と、空集合から変化した行を明示する**。この条件と手順を検証手順書へ登録する。
  - **基準結果の限界を明記する**: 基準結果は初回の実装に対する実測なので、**初回から何も
    していない行は基準結果ごと空になり、no-op のまま記録のみへ入る**。基準結果は
    **回帰の検出には使えるが、初回の実装が正しいことのオラクルにはならない**。実装から独立した
    オラクル(検証専用の経路でSDKを直接呼び、同じ事前操作に対する観測群の変化を基準にする)を
    置けばここは閉じるが、それは本計画の範囲を超える設計追加である。この境界を保証の境界へ
    加えて記載する。
  - **基準結果が空の行は手動確認一覧へ登録する**: 種別「行」・**類型(c) 自動判定の基準が
    無い**として登録し、実施と結果の記録を受入検証が行う(登録・実施・記録の枠から外さない。
    件数がどれだけになるかは実測前なので、ここでは大きさを見積もらない)。
  - 入力ファイルを取る行で冪等になるのを減らすため、**サンプルファイル表の各項目に
    「生成後のファイルが0バイトでないこと」と、モデル形式の項目では「頂点を1件以上含むこと」
    を必須要件として課す**(空ファイルを生成手段に選ばない)。この2つは生成物を読めば機械で
    判定できるのでゲートに載せる。

  `valueRead` の `setup` は**固定の並び**とする——`initPmx` → 引数の参照先の要素型ごとに
  `addElement` → 対応する書き込み行を `callTool` で1回。長さは参照先の数で決まるので探索を
  要しない(対応する書き込み行が1つに定まらない読み取り行は `valueRead` を導出しない)。
  SDKの戻り値を捨てて固定値を返す実装は既知状態と食い違うので落ちる。

  **`none` に落ちる行**は、`postcondition` を `effectType` が `none`・`kind` が `callLogOnly`
  の要素1つだけ(`effectKey` は空文字)とする。これは上の8つの導出条件の否定なので**集合と
  して一意に決まる**(事前の列挙を要しない)。**残余には読み取りと書き込みの両方が入る**——
  ホストの実行パスや登録プラグイン数のように引数も可変状態も持たない読み取りと、静止確認で
  観測群が空になった書き込みである。加えて、`observableChange` を導出はしたが**合否に
  算入しない行**(表示・セッション型で引数一致の観測メンバーが無いもの)も、判定という点では
  残余と同じ扱いになる。**これらは意味のある結果を外部の検査では確かめられない範囲であり、
  行ごとにその旨をツール仕様書へ明記する**(検査していないものを検査済みに見せない)。

  **画像差分による残余の切り分け**(合否を増やすためではなく、残余として列挙する範囲を
  狭めるため):
  `callLogOnly` に落ちた行のうち**書き込み操作を表すもの**と、`observableChange` を合否に
  算入しない行について、検査器は呼び出しの前後で
  ビューポート画像を取得して比較し、**変化したかどうかを記録する**。変化していればその行は
  少なくとも描画へ届く効果を持ったことになるので、残余の一覧から外して記録する。
  **変化しないことは不合格条件にしない**——描画に出ない項目なのか画像に出ない小ささなのかを
  外から区別できないため。どのメンバーが描画へ現れるかを事前に宣言する表は置かない(一次資料の
  記述から見た目の変化を読み取る作業は転記ではなく意味判断になり、実装時の判断を残すため)。
  **比較の条件は固定する**——`initPmx` の後、頂点3つ([0,0,0]・[10,0,0]・[0,10,0])と
  その3頂点を参照する面1つ・材質1つを追加した最小のモデルを可視・最前面で原点に置き、視点を
  カメラ位置 [0,0,-30]・注視点 [0,0,0] とする(空モデルには描画される形状が無く、何を変えても
  画像が同じになるため)。この記録は残余の一覧を**生成する**ために使い、合否には算入しない。
  `postcondition` の欠落・構造違反・`callLogOnly` の根拠欠落は、いずれもゲートで不合格とする。
- **危険操作**: `confirm` なしの呼び出しが `TOOL_CONFIRM_REQUIRED` になること。`confirm:
  true` 側の実行は、危険操作の3基準と引数の形から**行ごとに機械的に**次の4分岐へ振り分ける
  (基準はシグネチャ単位なので、1つの能力が複数の分岐に入ることがある。既知の該当能力は
  CAP-006/007/012/013/014/016/166/339/445 の9件で、すべていずれかの分岐に入る)。
  - **書き込み先を指定できるファイル書き込み**。述語: 基準(b)に該当し、かつ書き込み先を
    指定する引数を持つ(既知の該当: CAP-012 `SavePMDFile`・CAP-016 `SavePMXFile`・
    CAP-339 の `IPXPmx.ToFile`・CAP-445 のVMD書き出し・CAP-013 `SaveMaterialName`・
    CAP-166 `SaveViewSetting`)。検査専用の一時フォルダ(`%TEMP%` 配下。検査の前後で
    作成・削除する)を宛先にして実行する。**合格条件に副作用の観測を含める**: 呼び出し前に
    宛先が存在しないことを確かめ、呼び出し後に**宛先ファイルが生成され、サイズが0でない**
    ことを判定する。さらに、**本プロジェクトの読み込み系ツールで開き直せる形式**
    (PMX・PMD)は、開き直しが成功することまでを合格条件とする。`ok:true` が返ることだけを
    条件にすると、SDKを呼ばずに正常応答を返す実装でも合格してしまう。
  - **書き込み先を指定できないファイル書き込み**。述語: 基準(b)に該当し、かつ書き込み先を
    指定する引数を持たない。**一次資料(SDKドキュメントXML)の確認により、提供対象にこの述語を
    満たすシグネチャは存在しない**: 保存系はいずれも書き込み先のパスを引数に取る
    (CAP-012 `SavePMDFile` はPMDファイルパス、CAP-016 `SavePMXFile` はPMXファイルパス、
    CAP-013 `SaveMaterialName` は保存材質名ファイルパス、CAP-166 `SaveViewSetting` は
    設定ファイルパス)。よってこの分岐は空であり、実行検査を省く扱いは設けない。
    提供対象に該当が現れた場合は設計変更としてユーザーへ報告する。
  - **現在のPMX状態の一括初期化**。述語: 基準(c)の明示集合に該当する(CAP-007
    `InitializePMD`・CAP-014 `InitializePMX`・CAP-339 の `IPXPmx.Clear` の current 経路)。
    検査の前後で空モデルの初期化を行っているので、実行しても他の検査へ影響しない。ただし
    CAP-007 は**PMD形式**への初期化で実行後の状態が空PMXモデルと異なるため、この行の検査の
    直後に `InitializePMX` を実行して状態を戻す。
  - **エディタ終了**。述語: 基準(a)に該当する(CAP-006)。実行するとエディタが落ちるため、
    検査実行の**最終段で単独実行**し、パイプが切断されホストのログに停止の記録があることを
    もって合格とする(以後の検査は行わない)。

検査間の独立性: 各検査は「空モデルの初期化 → 事前操作 → 実行 → 空モデルの初期化」を単位と
し、検査どうしが状態で依存しないようにする。

**群単位の検査(検索での発見可能性)**: 行単位ではなく群単位で行う(行ごとに想定質問文を
用意すると人手が行数に比例するため)。群ごとに**想定質問文5件**を用意する。
**選定は機械的規則で行う**(担当者の主観で易しい5件を選べないようにする): その群の能力対応表
から、**ツール数の多い順に上位5つの要素型**を取り、各要素型について「その要素型の一覧を
取得したい」「その要素型を1件追加したい」のうち**その群に実在する操作の側**を定型文へ当てる
(両方あれば一覧側)。定型文は「モデルの<要素名詞>を<動作>にはどうすればよいか」とし、
SDKの型名・メンバー名・ツール名を含めない。上位5つに満たない群は、実在する要素型の数だけ
用意する。期待するツール名は写像規則から一意に決まる(各文に対応付けて
`docs/specs/pmx-editor-mcp-search-probes.json` へ記録する。**質問文と期待ツール名は、その群の
実装に着手する前に確定して記録し、以後変更しない**——検査結果を見てから質問文を選べると、
発見可能性の独立した検査にならない。不合格時に見直してよいのはツールの説明文だけで、質問文を
変えるなら設計変更としてユーザーへ報告する。選定規則は「その群の代表的な用途を、SDKの型名・
メンバー名を使わずにユーザーの語彙で述べる」とする)、MCPサーバーを登録した状態で
`claude -p` をヘッドレス実行し、実行結果に含まれるツール呼び出し名に期待ツールが現れるかを
機械判定する。**実行形式は次で確定する**(`--output-format json` の応答は最終結果・セッションID・
メタデータだけで `tool_use` を含まないため、ツール名を取り出せない):
`--output-format stream-json --verbose` で受け、`assistant` メッセージの `tool_use` ブロックの
`name` を集める。あわせて再現性のため、`--model`(前提7の対応モデルのいずれか)・
`ENABLE_TOOL_SEARCH=true`・`--allowedTools` による当該MCPツールの自動許可を固定する
(`-p` の既定の許可モードは Manual で、指定しないとツール呼び出しが許可されずに終わる)。
**モデルは前提7の対応モデルのうち `claude-sonnet-4-6` を検証手順書の固定値とする**
(利用者が別のモデルを常用する場合は、その識別子へ置き換えて再実行する旨も手順書に記す)。
**合格条件は5件中4件以上**。下回った場合は説明文の
語彙を見直して再実行し、**3回で合格しなければユーザーへ報告して判断を仰ぐ**(語彙の設計
判断であり、自動では決められないため)。合否はゲートの「不合格ゼロ」に数える。

**手動確認一覧** `docs/specs/pmx-editor-mcp-manual-checks.json`: 自動で判定できないものを
登録する。項目は**種別**で2つに分け、必須項目と歯止めを種別ごとに定める。

- **種別「行」**: 能力対応表の行のうち自動E2E検査で判定できないもの。**能力行キーと経路キー
  を必須**とし(ゲートはこのキーで対応表と突き合わせる)、類型・手順・期待結果・実施先も
  必須とする。
- **種別「契約」**: 行の合否ではなく、共通契約や前提の未検証項目のうち人手の確認を要する
  もの(Undo粒度がUpdate単位であること、画像応答がクライアント側で警告になるか等)。
  **対象の契約名と、それを定めた設計値の所在**を必須とし、類型・手順・期待結果・実施先も
  必須とする。行キーは持たないので対応表との突き合わせの対象外とする。

理由の類型は次の**3つだけ**の閉集合とする(種別に依らず共通)。

- **(a) UI操作の発火を要する**: 検査対象の挙動が、マウス・キー入力をエディタのUIへ与えない
  限り起きない。種別「行」の機械述語: 当該行が View イベント・UIモデルイベントの発火を
  確認対象に含むこと(イベント種別の識別子が `type` 分岐に存在すること)、または当該行の
  シグネチャがエディタのモーダルUI(ファイルダイアログ等)を開くこと。
  **件数の上限**: この述語だけではイベント行をすべて手動へ移せてしまい(公開イベントが増える
  ほど手動項目が増える)、人手が行数に比例する。そこでイベント行の検査を3つに分け、
  **全イベント行を機械で網羅し、手動はリスナ型ごとの代表1件に固定する**。
  - **payload 変換の全行網羅(xUnitテスト)**: SDKのイベント引数からJSON値への変換は、
    エディタを起動せずに検査できる純粋な写像である。**変換器の入力を、SDKのイベント引数型
    そのものではなく、ホスト側で定義する中立の入力型(イベント種別の識別子と、値表現へ写す前の
    プロパティ値の組)とする**——SDKのイベント引数型に公開コンストラクタや設定可能なプロパティが
    あるかは一次資料に記載が無く、テストから組み立てられる保証がないため、変換器の入口を
    SDK型に固定しない。実機のリスナは受け取ったSDKのイベント引数をこの中立入力型へ詰め替えて
    変換器へ渡す。**この詰め替えは手書きせず、SDKのイベント引数型のリフレクションから機械生成
    する**(ツールからSDKメンバーへのディスパッチと同じ原則。手書きの対応付けがなければ
    プロパティの欠落・取り違えは起こらない)。そのうえで、**各イベント引数型の公開プロパティが
    もれなく中立入力型の項目に現れることを、型の公開プロパティ集合との突き合わせでゲート検査
    する**(インスタンスを構築できなくても、型の形は静的に検査できる)。中立入力型を用いれば
    全 `type` 分岐へ入力を投入でき、全イベント行の payload 変換を網羅できる。行の網羅は
    この2つ——詰め替えの機械生成と公開プロパティ網羅ゲート、および変換の全行xUnit——で担保する。
  - **キュー契約の検査(自動E2E)**: `seq` 連番・`dropped`・`remaining`・`sourceHandle` の
    対応は、キューへイベントが入らないと観測できない。ホストにテスト用の投入経路を設け、
    自動E2E検査から投入して検査する。**投入経路の契約**: IPCの専用メソッド
    `debug_enqueue_event`(中立入力型とリスナのハンドルIDを受け取る)とし、MCPツールとしては
    公開しない。**実イベントと同じ enqueue 関数を通す**(通らなければキュー契約の検査に
    ならない)。有効になるのは環境変数 `PMX_EDITOR_MCP_DEBUG_HOOKS=1` を設定して起動した
    ホストに限り、未設定時は未知メソッド(-32601)を返す。配布パッケージから除外はせず、
    既定で無効という形でこの一点に集約する(ビルド構成を分けると配布物と検査対象が別物になる)。
  - **実機のイベント発火(手動)**: SDKのイベントが実際に発火し、ホストのリスナがそれを
    受け取ってキューへ積むこと。**リスナ型ごとに代表1件**を手動確認一覧へ登録する。
    登録件数が**リスナ型の集合と完全一致すること**(過不足ゼロ)をゲートで検査する
    (上限だけでは0件でも合格してしまうため、下限も課す)。
  この3分割により、イベント行に「検査しない行」は生じない。
- **(b) 目視での判断・観察を要する**: 期待結果が値の一致でなく、描画結果の内容が意図どおりか、
  またはMCPクライアント側の表示がどうなるかの観察であるもの。種別「行」の機械述語: 当該行の
  出力スキーマが画像コンテンツを含み、**かつ**期待結果が値の一致でないこと(値の一致で判定
  できる項目——`warnings` の文字列一致など——は述語を満たさず、自動E2E検査側に置く)。
  **件数の上限**: 画像を返す行を多数手動へ移せないよう、登録は**画像を返すツールごとに
  代表1件**とし、登録件数が画像を返すツールの集合と**完全一致**することをゲートで検査する
  (同じツールの経路違いを個別に手動へ積み増せない)。

- **(c) 自動判定の基準が無い**: 効果が外部から観測できるはずだが、変化の基準結果が空で、
  自動では合否を決められないもの。種別「行」の機械述語: 当該行の `postcondition` に
  `observableChange` の要素があり、**かつ**変化の基準結果の当該行の集合が空であること。
  **件数の上限は50件**とし、**該当する行は全件を登録したうえで、登録件数が50件を超えたら
  ゲートを不合格にする**(超過した行を一覧から落とすのではない。落とすと検査もされないまま
  消えるため、登録は全件必須のままにして、超過そのものを不合格にする)。**50件は、1件あたり
  数分の手作業として一巡が1日に収まる規模として置く取り決めである**——この値の当否は検査の
  正しさに関わらず、人手の量が実行可能な範囲に収まるかだけを決める。**不合格になった場合の
  出口は、観測群の規則を広げてこの類型から外すか、設計変更としてユーザーへ報告するか**の
  いずれかとし、手動へ積み増して通すことはしない。あわせて**件数と内訳を成果物として出す**:
  基準結果の生成時に、この類型の行数と内訳をツール仕様書へ記載する。

利用者の環境を不可逆に書き換える危険操作は、人手に移しても破壊は同じなので手動確認一覧には
入れない(上記「危険操作」の扱いで決着させる)。

**歯止め**: 種別「行」は類型の機械述語で検査し、述語を満たさない登録は不合格とする(恣意的な
手動化を止める。除外一覧・危険操作フラグと同じ様式)。種別「契約」は機械述語を持てないため
**閉集合**とし、一覧に載る種別「契約」の項目がその閉集合と一致することをゲートで検査する
(件数・対象名の両方)。**閉集合は次の2件で確定する**。以後の追加は設計変更としてユーザーへ
報告する。閉集合との一致検査は、項目を登録するのが群ごとの実装なので**本計画の完了条件でのみ**
判定する(閉集合を確定した時点では登録が0件で、一致を問えない)。
- 「Undo粒度がUpdate単位であること」(類型(a))。
- 「既定の `maxLongSide` の画像応答がクライアント側で警告になるか」(類型(b))。

**結果の記録**: 各項目は結果を機械判定できる形で持つ。必須フィールドは次の3つとする。
- `result`: `pass` / `fail` / `not_run` の3値。初期値は `not_run`。
- `evidence`: 結果の裏付け。目視の項目は観察した内容の記述、値で判定する項目は観測値。
  `result` が `not_run` のときは空文字、それ以外では**空文字を許さない**。
- `checkedAt`: **受入検証の実行識別子**。形式は RFC 4122 の8-4-4-4-12桁の16進表記(小文字)
  で、この形式は手動確認一覧のスキーマが強制する。値は受入検証を開始するときに1つ生成し、
  その回の全項目へ同じ値を書く(日時ではなく実行ごとに一意な識別子とする)。`result` が
  `not_run` のときは空文字、それ以外では空文字を許さない。ゲートは、進捗ドキュメントの
  見出し「受入検証の実行識別子」の節に記録された値を基準として照合する(記録先が固定なので
  判断なしに読める。生成と記録の手順は検証手順書が正本)。

受入検証の網羅ゲートは、**全項目の `result` が `pass` であること**(`not_run` と `fail` が
ゼロ)・`evidence` が空でないこと・**全項目の `checkedAt` が、受入検証の開始時に進捗
ドキュメントへ記録した実行識別子と一致すること**(過去の実行の記録を残したまま合格に
できないようにする)を検査する。
**この機械判定が保証するのは、人手による合否記録が全項目そろっていて、その実行識別子の回の
ものであることまでである**——目視した内容そのものの当否を機械が判定するわけではない。

種別「契約」の必須項目「設計値の所在」は、**移送後の恒久文書の見出し**(共通契約仕様書
またはツール仕様書の該当見出し)で記録する。計画書の節名では記録しない。
どちらの種別でも、歯止めを満たさない
のに自動化できないものが現れた場合は、手動へ逃がさず検査生成規則を拡張する。

**所要時間がかかるだけの検査は手動確認一覧に入れない**。長時間放置後のコネクタ再利用
(前提5)は実行器の `--soak` 経路で自動化する。この経路は通常の一巡とは**別の最小構成の実行**と
する(通常の一巡は最終段でエディタを終了させるため、その後に待機できない): 接続して
handshake を行い、**前提5が実測した7経路**(`PXCBridge.BuilderInitialize`・
`PrimitiveBuilderInitialize`・選択頂点インデックス取得・`GetCurrentPmx`・`ViewCtrl`・
`SystemCtrl`・イベントコネクタの生成と解放)を1回実行して成立を確かめ、**8時間**接続を
張ったまま待機し、その後に同じ7経路を保持中のコネクタで再実行して全て成功することを合格
条件とする(ビルダ初期化の2経路も前提5の実測対象なので、長時間保持の回帰検査から落とさない)。**あわせて、ホストのログ全体(起動から終了まで)に「Cプラグインコネクタの取得」の
記録がちょうど1件だけ存在すること**も合格条件に含める——「開始位置以降に増えていない」だけでは
基準位置より前の複数回取得も、取得記録が一度も出ていない場合も通ってしまう。API成功だけを条件に
するのも同様に不足で、待機後に再取得する実装でも合格してしまい「取得1回・常駐保持」の回帰検査に
ならない。**PMXファイルを開き直す検査にも同じログ判定(全区間でちょうど1件)を課す**。
8時間は**1作業日を検証の対象範囲とする方針値**であり、実測や要求仕様から導いた値ではない
(実測は93秒までであることは前提5のとおり)。前提5の未検証のうち
数時間の放置はこれで覆えるが、**24時間の放置は覆えず未検証のまま残る**(残存リスクとして
受容する)。
既定の実行では回さず、受入検証で**単独で**1回実行する(所要8時間で、他の検査と同じエディタ
インスタンスを共有すると通常の検査一式のエディタ終了に巻き込まれるため、同時に走らせない)。
**専用インスタンスで実行する**: 実行前に稼働中のエディタをすべて終了し、この検査のためだけに
エディタを起動する。完走後はそのインスタンスを終了する(取得ログが全区間でちょうど1件である
ことを判定するには、起動から終了までが1つのホストプロセスの生存期間として閉じている必要が
ある)。

手動確認一覧の各項目は受入検証で消化する。**実施先は検証手順書の見出しで記録する**——
類型(a)(b)は受入シナリオの見出し、**類型(c)は専用の見出し「自動判定の基準が無い項目の確認」**
とする(計画書は完了時に削除されるため、計画書名・計画書内のシナリオ番号では記録しない)。記録の主体は受入検証の側とし、本計画は実施先の見出しを登録するところまでを行う。

**MCP経路(Claude Code経由)を全ツールで確認しないことの根拠**: ブリッジの中継はツールに
依らず同一の機構(ブリッジ基盤が確定した「1ツール=ホストの1メソッドへの中継」とエラー変換)である
ため、経路の成立は群ごとの代表1ツールと受入シナリオで担保する。ツール個別の検査は
上記の自動E2E検査(ホストのパイプ経路)が担う(何がどこまで確かめられるかは上記の
保証の境界のとおりで、全行が同じ強さで確かめられるわけではない)。ただし**クライアント側でしか観測できない
事柄**(応答サイズのしきい値が宣言値へ置き換わること・検索で意図したツールを引けること)は
パイプ経路では確かめられないため、`claude -p` のヘッドレス実行による検査で扱う。

**ゲート**: 能力対応表の全行が「自動E2E検査で合格」「xUnitテストで全行網羅されている
(イベント行の payload 変換)」「手動確認一覧に種別『行』として登録され、類型の機械述語を
満たし、実施先の見出しが特定されている」のいずれかであること(未分類ゼロ・不合格ゼロ)。
イベントの代表発火の登録は**リスナ型の集合と完全一致**していること。経路キーについても
同じ網羅を検査する。種別「契約」の項目は
上記の閉集合との一致を検査する。**手動確認の実施と結果の記録は受入検証が行う**ため、
本計画のゲートは登録と実施先の特定までを見る。

   前提の節・自己参照・他の一時文書への依存を、恒久成果物への参照か自己完結した記述へ
   置き換えることである。以下に並ぶ鉤括弧付きの語は、その依存を機械検出するための**検査
   データとしての字形**であり、依存先そのものを指す参照ではない。対象と置換先は次のとおり。
   - 「前提N」→ 確かめた事実そのものの記述。
   - **計画書番号を含む参照**(番号に助詞を続けた形) → 移送先の恒久文書(IPC仕様書・
     アーキテクチャ仕様書)の該当契約への参照。
   - 「ステップN」「実装ステップ」→ 到達状態の記述(いつ行うかでなく、何が成り立っているか)。
   - 「本計画」「本計画書」→ 移送先の恒久文書を指す語、または自己完結した記述。
   - **本計画書の節見出しによる参照**(「下記『…』」「上記『…』」)のうち、**移送対象外の節を
     指すもの** → 参照先の内容そのものの記述、または移送先の恒久文書の該当箇所への参照。
     移送対象の節どうしの参照は移送後も成立するので置換しない。
   置換先を持たない記述——工程そのものが前提の規則(除外一覧のベースライン取得等)と、
   **検証・検査の進め方の記述**(どの検査でどう判定するか)——は**移送せず**、移送先には
   結果だけを書く(恒久仕様書は到達状態を規定し、検証の過程を書かない)。
   移送後の本文に、「前提」+数字・「ステップ」+数字・「実装ステップ」・「本計画」・
   計画書番号の参照、および移送対象外の節を指す鉤括弧付きの節見出し参照が残っていないことを、
   移送の完了条件として検査する(検査文字列を数字付きに限るのは、「前提」「ステップ」の
   普通名詞としての用法を誤検出しないため)。
   この置換は群ごとのツール仕様書追記にも同じく適用する。照合スクリプトの実行
   コマンドと合格条件(過不足ゼロ・未割当ゼロ・分類の未分類/多重分類ゼロ・複製編集型の
   更新指定欠落ゼロ・危険操作フラグの三者一致・型役割の未割当ゼロ・群内重複ゼロ・
   規則適合検査とスキーマ対応検査の合格・除外一覧と台帳の件数一致・台帳の全CAPが
   型列挙結果に現れること・説明文の2,000バイト上限と出所修飾の検査の合格・
   型別 `limit` の逆算値がスキーマ正本と一致すること・**`rowKind` の未分類・多重分類ゼロと
   種別ごとの必須フィールドの充足・`postcondition` を持つ行での欠落ゼロと構造適合・
   直接ディスパッチ行の全行にディスパッチの呼び出し記録があること・`postcondition` の判定が
   それを持つ全行で合格であること**)を
   検証手順書へ登録する。
   **自動E2E検査の基盤**を整備する: 能力対応表とスキーマ正本から検査項目を機械生成する
   生成器と、起動中の実機エディタへパイプ経由で実行して行キー・経路キーごとの合否を出力する
   実行器 `scripts/e2e-tools.mjs`(`--soak` の実行経路を含む)、型別既定サンプル値表
   `docs/specs/pmx-editor-mcp-sample-values.json`、サンプルファイル表
   `docs/specs/pmx-editor-mcp-sample-files.json`、**変化の基準結果**
   `docs/specs/pmx-editor-mcp-change-baseline.json`(`--baseline` の実行経路で機械生成し、
   `anyChanged` の判定に使う。生成と再生成の手順を検証手順書へ登録する)、想定質問文の記録
   `docs/specs/pmx-editor-mcp-search-probes.json`、および手動確認一覧
   `docs/specs/pmx-editor-mcp-manual-checks.json`(空で作成し、**種別**・類型の閉集合・
   手順・期待結果・実施先を全項目の必須とし、種別「行」には能力行キーと経路キー、
   種別「契約」には対象の契約名と設計値の所在を、種別ごとの必須としてスキーマで強制する)。生成規則は
   「行単位の検査は自動実行する」の各項目とし、手動確認一覧の類型の機械述語も同じ照合
   スクリプトで検査する。共通契約の整備の時点では、共通契約に属する行(危険操作の `confirm`
   検査・ハンドルの型役割・ページング境界)で生成器と実行器が動くことを確認する。あわせて、
   宣言あり・なしのA/B対照で宣言が効いていること(前提6の未検証)を、
   パイプ経路では観測できないため `claude -p` のヘッドレス実行で確認する。**確認の具体**:
   **同一の応答に対する宣言あり・なしのA/B対照**で判定する。トークン数と文字数の換算は
   一次資料が定めておらず(保証されているのは既定が25,000「トークン」であることと注釈値が
   「文字」であることだけ)、換算の仮定を置くと検査が成立しないためである。
   - fixture: 一覧応答を **400,000文字**にする(空モデルへ要素を追加し、件数で近づけたうえで
     末尾の文字列項目の長さで調整する。CLIへ投入する前に実際の文字数を測る)。注釈のハード
     上限500,000文字の範囲内である。**この値が25,000トークンを超えることは換算では主張
     しない**——超えたかどうかは下記の判定そのものが示す。
   - 検査専用の設定を2つ用意する。どちらも**環境変数でホストとブリッジへ与え、既定値は
     本番の値**とする(検査以外では効かない)。
     - `PMX_EDITOR_MCP_BUDGET_CHARS`: 応答サイズ予算の文字数(名前・既定 100,000・構文・
       有効範囲・不正時の挙動は、ホスト基盤とブリッジ基盤の設計値として確定済み)。
       検査時は **420,000** を与える。ホストの `value`
       ゲートは常に「この値 − 警告枠2,000文字」で算出する(検査時は418,000文字となり
       400,000文字は通る)。ブリッジが宣言する `anthropic/maxResultSizeChars` の値も同じ
       設定から取る。**環境変数の名前・既定値・構文・有効範囲・不正時の挙動、および
       handshake の `budgetChars` によるホストとの一致の担保は、ホスト基盤とブリッジ基盤の
       設計値として確定済みである**(ここでは再定義しない)。本計画が定めるのは、この予算値を
       どう使うか——警告枠2,000文字と一覧応答の枠1,000文字の内訳、型別 `limit` の逆算、
       100,000文字を選んだ理由——と、検査時の一時的な引き上げだけである。
     - `PMX_EDITOR_MCP_DECLARE_META`: ブリッジが `_meta` を付与するかどうか。既定 1(付与
       する)。A/B対照の「宣言なし」側でのみ 0 を与える。**この設定は
       `PMX_EDITOR_MCP_DEBUG_HOOKS=1` のときだけ有効**とし、未設定時は 0 を与えても付与を
       止めない(テスト用の投入経路と同じ入口に集約する)。**これは外部からの無効化を
       禁止するものではない**——どちらも環境変数なので、利用者が両方を同時に設定すれば
       宣言は止まる。デバッグフックを明示的に有効にした状態は契約の外であり、その状態で
       ツールの `_meta` が付かないことをツール仕様書へ明記する。二重の設定を要求するのは、
       通常の配布・運用で意図せず契約が破れることを防ぐためである。
   - **外部設定の統制**: 宣言なし側の挙動は `MAX_MCP_OUTPUT_TOKENS` に左右されるため、
     A/Bの**両側でこの環境変数を 25000 に固定して実行する**(利用環境に大きな値が設定されて
     いると、結果の差がfixtureや宣言ではなく外部設定に由来してしまう)。
   - 同じ fixture を、宣言あり(`PMX_EDITOR_MCP_DECLARE_META=1`)と宣言なし(同 0)の2通りで、
     上記の検索検査と同じ実行形式(`--output-format stream-json --verbose`・モデル固定・
     `--allowedTools`)で走らせる。判定は次の4通りで閉じる。
     - **宣言なし=ファイル参照 / 宣言あり=本文** → **合格**(宣言が効いている)。
     - 両方とも本文 → 不合格。fixture が既定のしきい値に届いていないか、宣言が無意味かの
       いずれか。fixture はハード上限500,000文字までしか大きくできないので、これ以上の
       切り分けは計画内ではできない。
     - 両方ともファイル参照 → 不合格。しきい値が宣言値まで引き上がっていない。
     - 宣言なし=本文 / 宣言あり=ファイル参照 → 不合格。想定と逆で、宣言が有害か観測系の
       誤りかのいずれか。
     **合格の1通り以外はすべて不合格**とし、4通りのどれであったかと両側の応答を添えて
     設計変更としてユーザーへ報告する。
   また、実行コマンドと合格条件(全行が自動E2E合格・xUnitの全行網羅・手動確認一覧の種別「行」への
   登録のいずれかであること、手動登録は述語を満たし実施先が特定されていること・イベントの
   リスナ型ごとの代表イベントの発火確認の登録がリスナ型の集合と完全一致すること・未分類ゼロ・不合格ゼロ・能力行キーと
   経路キーの双方の網羅・サンプル値表とサンプルファイル表の未割当ゼロ)も検証手順書へ
   登録する。あわせて**MCP経路の2検査**——群単位の検索での発見可能性(実行コマンド・
   想定質問文の所在・5件中4件以上の合格条件・3回で不合格ならユーザーへ報告)と、
   宣言あり・なしのA/B対照(fixtureの作り方・検査専用の環境変数3つ・4通りの判定と
   合格の1通り)——も、実行コマンドと合格条件つきで検証手順書へ登録する(進捗ドキュメントは実行結果の記録先であり、再実行可能な手順の正本は検証手順書と
   する)。
   **ホスト基盤への追加要件**を2件立て、**本ステップの実装対象に含めた上で**アーキテクチャ
   仕様書へ追記する: (1)IPERunArgsの常駐保持、(2)ホストのログの記録内容へ「Cプラグイン
   コネクタの取得」「Cプラグインコネクタの破棄」「ハンドルの解放」を加えること(終了時の後始末を機械判定するために要る。
   実行器はエディタのプロセスIDから `%TEMP%\pmx-editor-mcp-host-<プロセスID>.log` を
   組み立ててログを特定する)。文書への追記だけでは判定に必要な出力が存在しないため、
   どちらもホスト側の実装を伴う。
   一次資料(SDKドキュメントXML)で確認済みの引数の形——CAP-015 `OpenPMXFile` はPMXファイル
   パスを取り真偽値を返す、CAP-013 `SaveMaterialName` は保存材質名ファイルパスを取る、
   CAP-166 `SaveViewSetting` は設定ファイルパスを取る——を台帳の該当備考へ記す(引数の形は
   確定済みで、実装時に調べ直す工程は持たない)。
   危険操作の3基準に該当する能力(既知の該当:
   CAP-006/007/012/013/014/016/166/339/445)の台帳備考に「危険操作」と該当シグネチャを
   追記する。
2. モデル群を「実装の進め方」の縦切りで実装する(複製編集型の状態契約——Update成功後の
   表示更新失敗の警告・Update前例外の未変更保証・Update例外の結果不明報告——のテストと
   自動E2E検査を含む)。Undo粒度の検証はエディタのUndo操作を要するため、手動確認一覧へ
   **種別「契約」・(a)の類型**で登録し、実施先を検証手順書の受入シナリオ「編集と取り消し」
   とする(実施と結果の記録は受入検証が行う)。
3. セッション群を同様に実装する(危険操作の confirm 検査・直接変更型の状態契約を含む)。
4. ビュー群を同様に実装する(ビューポート画像のPNG/Base64返却・イベント購読とpoll・
   UIモデルとテキストコントロールのハンドル運用を含む)。手動確認一覧への登録は次の3種を
   それぞれ独立に行う。
   - **イベント発火(計2件)**: `IPXViewEventListener` と `IPXUIModelEventListener` の
     リスナ型ごとに1件。内容は「実機の操作でイベントが発火し、`sourceHandle` が購読した
     リスナのハンドルIDと一致すること」。種別「行」・類型(a)。実施先は受入シナリオ
     「イベント」。
   - **画像の目視(計3件)**: 画像を返すツールごとに1件(CAP-120・CAP-168・CAP-239)。
     内容は「画像に意図した視点の内容が描かれていること」。種別「行」・類型(b)。実施先は
     受入シナリオ「ビュー」。
   - **画像警告の契約(計1件)**: 「既定の `maxLongSide` の画像応答がクライアント側で警告に
     なるか」。種別「契約」・類型(b)。実施先は受入シナリオ「ビュー」。`maxLongSide` による
   縮小時の `warnings` は文字列の一致で判定できるため手動へ回さず、自動E2E検査で確認する。
5. 変形・モーション群を同様に実装する(ビルダのハンドル運用・VMEテンプレートの列挙・確定を
   含む。デリゲート系シグネチャの除外はステップ1の除外一覧に基づく)。
6. 全群完了後、機械生成した提供対象シグネチャ集合と能力対応表の全行を照合スクリプトで
   突き合わせ、過不足ゼロ・未割当ゼロを全群横断で確認する(この確認は受入検証
   (実装計画書06)でも再実施する)。
7. 全検査を実行して成立を確認し、進捗ドキュメントへ実行コマンドと合否を記録する。
   完了後、本計画書を削除候補として報告する(削除の実行はユーザーの指示があった
   ときのみ)。
