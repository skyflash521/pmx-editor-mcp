# pmx-editor-mcp 型役割仕様書

[役割対象の型](pmx-editor-mcp-role-types.md)の1つ1つへ割り当てる**役割**と、その正本である
`pmx-editor-mcp-type-roles.json` の形と検査を定める。役割は型をツールへどう写すかを決めるので、
型ごとに1つだけ持つ。

## 役割

役割は次の5つで閉じる。**判定はこの順に評価し、最初に当たったものを採る。** 定義は重なりうる——
コネクタ型もエディタ状態の一部として取得できるので操作対象型の定義にも当たる——ので、先に当たった
ものを採ることで役割が1つに定まる。

- `connector`(**コネクタ型**): エディタ機能への接続点のうち、**呼び出し側が実体を用意せずに
  呼べるもの**。ホストが単一インスタンスを常駐保持する型と、インスタンスを持たない静的な型がこれに
  当たる。フォーム・ビュー・システムの各コネクタ、Cプラグインの橋渡し、起動引数、各ビルダ、静的な
  補助処理がこれに当たる。接続ごとに生成・解放される型(イベントコネクタ等)は呼ぶ前に生成が要るので
  当たらず、ハンドル操作型になる。
- `eventArgs`(**イベント引数型**): 公開イベントのハンドラの型引数に現れる型。
- `handleTarget`(**ハンドル操作型**): ハンドルを介してのみ操作する型。UIモデル・テキスト
  コントロール・VMDとVMEのデータとその構成要素がこれに当たる。
- `operationTarget`(**操作対象型**): 現在のPMX状態・エディタ状態の一部として編集・取得できる型。
  PMXデータとその構成要素——PMX本体・頂点・材質等——がこれに当たる。
- `dto`(**DTO型**): 上記のいずれでもなく、メソッドの入力または結果にだけ現れる型。

## 正本の形

`types` と `issuances` の2つを項目に持つ組とする。`types` の各項目は役割ごとに決まった名前だけを
持ち、どの役割も次の3つを持つ。

- `typeName`: 役割対象の型の名前。名前空間を含む完全名で書き、入れ子は `+` で区切る。総称型は
  山括弧の中へ**その段の型引数の数**を書く(例: `N.IThing<1>`)——役割は型引数の埋め方では変わら
  ないので、開いた定義と閉じた型を同じ1項目で扱う。
- `role`: 上の5つのいずれか。
- `basis`: その役割と判じた根拠の一文。

**独立したツールを持つ役割**——コネクタ型・ハンドル操作型・操作対象型——は、さらに次を持つ。

- `elementNoun`: ツール名と説明文が対象を指す名詞の**単数形**。小文字で始まり、小文字と数字と
  下線だけからなる語とする——ツール名の一部になるためである。
- `elementNounPlural`: 同じ名詞の**複数形**。集合を扱うツールの名前に使う。**コネクタ型は
  持たない**——コネクタ型のツールは対象をツール名で名指しし、どれを操作するかを引数で選ばないので、
  集合を指す語が要らないためである。

イベント引数型とDTO型はこの2つを持たない。独立したツールを作らず、他のツールの入出力へ埋め込む
だけなので、指す名前が要らない。

**コネクタ型**は、さらに次を持ちうる。

- `connectionPath`: 接続の根からその型へ至る**経路**。根から進む一歩の名前を点でつないだもので、
  メソッドの段には丸括弧を付ける(例: `Host.Connector.View`・`ViewCtrl()`)。接続初期化はこの経路を
  辿って実体を得る。**最初の名前は接続の根が宣言または継承するメンバーの名前**なので、どの根から
  辿り始めるかは経路が決める。**同じ型へ道が複数あるときは、一歩の数が最も少ない道を採る。**
  同数のときは[役割対象仕様書](pmx-editor-mcp-role-types.md)が定める接続の根の並びで先の根から
  始まる道を採り、それでも並ぶときは列挙の並びで先に見つかった道を採る。
  **接続の根と、根から辿り着けないコネクタ型は持たない**——根は辿り始める側で、辿り着けない型は
  メンバーの名前をつないだ経路を自分では持たないためである。持つかどうかは書き手が選べず、
  [検査](#検査)が列挙と突き合わせる。

## ハンドル発行の判定

`issuances` は、**ハンドルを新しく発行しうるシグネチャ**を1件ずつ持つ。母集合は列挙から決まり、
[提供対象](pmx-editor-mcp-role-types.md)のうち、ハンドル操作型の公開コンストラクタと、値の型が
ハンドル操作型(配列の印を外して見る)であるメソッドからなる。**取得プロパティは入れない**——
プロパティは型ごとの取得・更新のツールへ集約され、生成のツールにならないためである。提供対象に
限るのは、そこに無いシグネチャはツールにならないので発行を判じても使い道が無いためである。
各項目は次を持つ。

- `signatureKey`: 公開API列挙の行キー。
- `issues`: 新しい実体を発行するか。既にある実体を返すだけなら偽。**列挙からは決まらない**ので、
  書き手が配布物の記載を読んで判じる。
- `kind`: 発行するときだけ持ち、`constructor`(公開コンストラクタ)・`factory`(コネクタ型の
  メソッド)・`receiverBound`(ハンドル操作型のメソッド)のいずれか。レシーバーから決まる値で、
  下記の検査が列挙と突き合わせる。
- `basis`: そう判じた根拠の一文。

項目は行キーの序数の昇順に並べ、同じ行キーは二度現れない。

## 並び

`types` の項目は型名の序数の昇順に並べ、同じ型は二度現れない。並びを固定するので、型を足すときは末尾ではなく
その位置へ入れる。**要素名詞は単数形と複数形をまたいで表の中で一意にする**——ツール名と説明文が
対象を指す語なので、二つの型が同じ語を名乗ると、どちらのツールかが名前から決まらない。

## 検査

型役割の照合が、次を検査する。

- 表の型と役割対象の母集合が**一対一で一致すること**。これが無いと、型を丸ごと書き落としても、母集合に
  無い型を混ぜても、残った項目だけが条件を満たして通ってしまう。
- 接続の根がすべてコネクタ型であること。根は接続初期化が最初に触る接続点そのものである。
- イベント引数型が、列挙の公開イベントのハンドラの型引数と**両向きで一致すること**。この役割だけは
  列挙から必要十分に決まるので、書き手の判断を挟まない。**引数の型を取り出せないハンドラのイベントが
  1件でもあれば、照合は判定を出さずに止まる**——`System.EventHandler` とその総称型だけが型引数の
  位置を決められるので、それ以外のハンドラでは必要十分の根拠が立たない。
- ハンドル発行の判定の集合が、列挙で決まる母集合と**一対一で一致すること**。母集合に無い
  シグネチャを書いても、母集合のシグネチャを書き落としても落ちる。この照合は、母集合を決める
  途中でレシーバーから種別を決められないシグネチャが在れば、**判定を出さずに止まる**——値の型が
  ハンドル操作型のメソッドで、宣言型がコネクタ型でもハンドル操作型でもないもの、および宣言型が
  ハンドル操作型の静的メソッドがこれに当たる。前者はレシーバーが閉じた3つの種別のどれにも当たらず、
  後者はレシーバーを持たない。
- 発行するとしたシグネチャの `kind` が、レシーバーから導いた種別と**一致すること**。
- コネクタ型の接続の経路が、列挙から辿った経路と**一致すること**。列挙が経路を持つ型は同じ経路を
  書き、持たない型は書かない。手で縮めた経路も、書き落とした経路も、余分に書いた経路もここで落ちる。
  この照合は、**経路を辿り直す側が各段で名前から一つの先を選べること**を先に確かめる。同じ名前の一歩が
  二つの型を指すと、その段でどちらへ進むかを選べない。接続の根の並びは一つの段として数え、経路の先頭の
  名前はどれか一つの根のものでなければならない。
- コネクタ型が、接続の根から辿り着ける型か、辿り着ける型の基底型か、メンバーを1件以上宣言してその
  すべてが静的な型であること。どれにも当たらない型は、呼び出し側が実体を用意しなければ呼べない。基底型を認めるのは、
  辿り着ける型の実体がその基底型の実体でもあり、基底型自身は辿り着く先にならないためである。静的な型を
  認めるのは、実体を持たないので保持する先が要らないためである。

次の条件は正本を読む時点で確かめる。型名・行キー・根拠、そして書いたなら接続の経路が空でないこと
(空白だけも不可)。経路の有無は項目が在るかどうかで表すので、空の経路は「持たない」と見分けられない。
役割が上の5つのいずれかであること。役割ごとに決まった名前だけを持つこと。要素名詞が上記の語の形で
あること。発行の判定が真偽であり、発行するときだけ種別を持ち、その種別が上の3つのいずれかであること。
そして上記の並びと一意であること。

**機械で確かめられるのはここまでである。** ハンドル操作型・操作対象型・DTO型の切り分けは型の使われ方
という意味の判断で、列挙からは決まらない。新しい実体を発行するのか既にあるものを返すだけなのかも同じ
で、戻り値の型からは決まらない。書き手が判じ、その判断を根拠の一文が後から追える形にする、という
ところまでを規則とする。
