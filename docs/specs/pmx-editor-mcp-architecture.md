# pmx-editor-mcp アーキテクチャ仕様書

pmx-editor-mcp の構成・ライフサイクル・運用の正本。エディタ側プラグイン(以下ホスト)と、
stdioを使うMCPサーバーの外部プロセス(以下ブリッジ)の両方を定める。両者の間で交わすプロトコルは
[IPC仕様書](pmx-editor-mcp-ipc.md)が定める。ツール化する能力の一覧は
[PEPlugin SDK 能力台帳](pmx-editor-mcp-capability-ledger.md)が持つ。

## プロジェクト構成

- [PmxEditorMcp.HostPlugin.csproj](../../src/HostPlugin/PmxEditorMcp.HostPlugin.csproj):
  net48のクラスライブラリ。成果物名は `PmxEditorMcp.dll`。プラットフォームは AnyCPU で、
  実行対象は x64版エディタ `PmxEditor_x64.exe` のプロセス。参照アセンブリは
  `Microsoft.NETFramework.ReferenceAssemblies` 1.0.3 で解決する。
- [tests/HostPlugin.Tests](../../tests/HostPlugin.Tests) の
  `PmxEditorMcp.HostPlugin.Tests.csproj`: net48・xUnit。UIスレッドとエディタ実機に依存
  しないロジックを対象とする。
- [PmxEditorMcp.Bridge.csproj](../../src/Bridge/PmxEditorMcp.Bridge.csproj):
  net10.0のコンソール実行プロジェクト。成果物名は `PmxEditorMcp.Bridge.exe`。NuGetパッケージ
  `ModelContextProtocol` 2.2.0 と `Microsoft.Extensions.Hosting` 10.0.0 を参照する。後者は
  前者が推移的に持たないGeneric Hostの実装で、直接参照が要る。
- [tests/Bridge.Tests](../../tests/Bridge.Tests) の `PmxEditorMcp.Bridge.Tests.csproj`:
  net10.0・xUnit。接続先解決・エラー変換など、プロセス外部に依存しないロジックと、試験用の
  ホストを相手にした通信を対象とする。ブリッジの `InternalsVisibleTo` の対象でもある。
- 4つのプロジェクトはすべて [PmxEditorMcp.sln](../../PmxEditorMcp.sln) に含める。

## ビルドとデプロイ

### PMXエディタ導入ディレクトリの指定

PMXエディタの導入先は環境ごとに異なるため、リポジトリ直下のGit管理外ファイル `local.props`
(`.gitignore` に登録済み)へ `PmxEditorDir` プロパティとして定義する。追跡下の
[Directory.Build.props](../../Directory.Build.props) が行うのはImportだけで、`local.props` が
存在するときだけ読み込む(無い環境ではImportをスキップするだけで、`Directory.Build.props` の
評価は失敗しない)。

未定義のまま進むことを止めるのはホストcsprojの `EnsurePmxEditorDir` ターゲットで、ビルドと
デプロイの前に走り、`PmxEditorDir` が空なら「local.props に PmxEditorDir を定義せよ」という
明示エラーで失敗させる。

### PEPlugin.dll の参照

`$(PmxEditorDir)\Lib\PEPlugin\PEPlugin.dll` を HintPath で参照する。ホストは `Private=false` とし、
配布物のDLLを成果物へコピーしない。PMXエディタ配布物の利用規約がパッケージ内データの再配布を
禁じているため、各自の導入物を参照するだけにする。

**テストは `Private=true` とし、ビルド出力へ複製する。** テストはエディタと別のプロセスで動き、
そのプロセスには配布物が読み込まれていないので、複製しなければSDKの型を実装した差し替えを読み込め
ない。ビルド出力は配布物にも版管理にも入らないため、再配布には当たらない。

### デプロイ

ホストcsprojの `Deploy` ターゲット(`Build` に依存)が、成果物を
`$(PmxEditorDir)\_plugin\User\` へ変更時のみコピーする。

```
dotnet build src/HostPlugin/PmxEditorMcp.HostPlugin.csproj -t:Deploy
```

**ホストDLLの置き場はこの1つとする。** デプロイはすべてのエディタを終了してから行い、反映は
次回のエディタ起動からになる。手順と確認の正本は[検証手順書](../conventions/verification.md)、
どちらの制約も理由は[設計判断の理由](#設計判断の理由)。

## プラグインのライフサイクル

クラス `PmxEditorMcpPlugin`(PEPluginClass派生)が実体で、オプションは起動時実行とメニュー登録
(メニュー文言「PMX Editor MCP」)。

### 起動時実行

起動時実行はエディタのUIスレッドで呼ばれる(実機で確かめてある)。ここで不可視Formを生成して
ハンドルを確保するので、以後のUIディスパッチはこのFormを通せばUIスレッドへ届く。続けて
[接続の常駐保持](#接続の常駐保持)を済ませ、そのうえで稼働世代を
1つ作り、IPCサーバースレッド(背景スレッド)を開始する。ただし
[応答サイズ予算の設定](#応答サイズ予算の設定)が不正なときは待受を開始せず、状態区分は
「開始せず(応答サイズ予算の設定が不正)」になる。

この経路の例外はすべて捕捉してエディタを巻き込まない。ログへ記録できるのはログの初期化より
後で起きた例外に限る(初期化前の例外は捕捉されるだけで記録が残らない)。

### 接続の常駐保持

起動時実行で受け取った**接続の根**(`IPERunArgs`)を常駐期間中そのまま保持する。エディタの機能へ
至る各コネクタ・ビルダは、この根から辿って得る。

続けて、根が持つホストプラグイン自身のモジュールパスを渡して**Cプラグイン連携のコネクタ**を
一度だけ得て、同じく常駐期間中保持する。取得の経路は一次資料が利用非推奨としているので、
**常駐中に取り直さない**。**この2つは待受を開始する前に済ませる**——待受が先だと、開始から取得
までの間に届いた要求が、コネクタの無い状態で走る。

**コネクタを得られなくても根は保ち、待受も続ける**。失敗は記録に残す。この連携が無くてもほかの
機能は根から辿って動くので、根の保持まで失わせない。

手放すのは**エディタの終了時**([Dispose](#dispose))だけで、メニューからの停止は手放さない
——停止と開始を繰り返しても取り直さないためである。手放したあとに二度手放しても記録は増えない。
終了時の手放しは受付を止めた後に行うので、**その時点で処理中だった要求はコネクタを失いうる**。
エディタが終わる経路なので、応答を返し切ることより資源を手放すことを先にする。

### 稼働世代

受付停止フラグ・公開中のパイプインスタンス・IPCサーバースレッドの参照を1つの「稼働世代」として
まとめて保持し、開始のたびに新しい稼働世代を作る。停止手順・状態判定・UIディスパッチの可否は
すべて稼働世代の単位で決まり、停止した稼働世代での禁止を新しい稼働世代へ持ち越さない。

### メニュー再実行と状態表示

メニューの再実行では、稼働状態(状態区分・パイプ名・接続状態・応答サイズ予算・ログパス)を
メッセージボックスで表示し、そこからホストの停止・開始を選べる(起動時実行のやり直しはしない)。
状態区分は次の4つで、メニュー再実行のたびに判定する。ホストがそもそも生成できていない
(起動時実行が失敗した)ときは、状態区分を出さず「ホストが常駐していない。エディタを起動し直す。」
の警告だけを表示して何もしない。

| 状態区分 | 意味 |
|---|---|
| 稼働中 | 要求を受け付けている |
| 停止処理中 | 停止した稼働世代のIPCサーバースレッドがまだ終わっていない |
| 停止済み | 開始できる |
| 開始せず(応答サイズ予算の設定が不正) | 設定が不正なため待受を開始していない |

「稼働中」なら「停止しますか?」、「停止済み」なら「開始しますか?」を既定「いいえ」のはい/いいえで
確認し、はいのときだけ停止・開始を行う。その結果は表示しない(状態は次のメニュー再実行で分かる)。
開始が受け付けられなかったときは、開始できなかった理由をログへ記録する。「停止処理中」と
「開始せず(応答サイズ予算の設定が不正)」では問いを出さず、なぜ開始できないかを状態表示の本文に
含める。停止・開始の操作は排他ロックで直列化し、呼び出しスレッドを仮定しない。

### 停止手順

メニューからの停止と `Dispose` が共有する。排他ロックの下で、

1. 現在の稼働世代の受付停止フラグを立てる。
2. その稼働世代が公開しているパイプインスタンスがあれば閉じる(`PipeOptions.Asynchronous` で
   生成しているため、`WaitForConnection` と読み取りのブロックが即座に解ける)。
3. 以後その稼働世代ではUIディスパッチを行わない。

**呼び出しスレッドをブロックしてIPCサーバースレッドの終了を待つことはしない。** 理由は
[設計判断の理由](#設計判断の理由)。

### 待受ループ

IPCサーバースレッドの1回の反復は、排他ロックの下で自分の稼働世代の受付停止フラグを確認し、
立っていればループを抜け、立っていなければ新しいパイプインスタンスを生成して稼働世代へ公開する
ところから始める。ロックを解いてから `WaitForConnection` と要求処理を行う。停止手順が
「フラグを立てる」と「公開中のインスタンスを閉じる」を同じロックの下で行うため、フラグ確認を
すり抜けて生成されたインスタンスが閉じられないまま待受に残ることはない。

停止で閉じられたインスタンスは、待受中なら `WaitForConnection` が例外で戻り、接続中なら
読み取りが0バイトを返して戻る(いずれも切断として扱う)。ループ内の例外は捕捉してログへ記録し、
フラグが立っていればループを抜ける(立っていなければ次の反復へ戻る)。停止した時点で要求を
処理中だった場合は、その要求の処理を終えてから次の反復へ入り、そこでフラグを見て終了する。

パイプインスタンスの生成に失敗したときは500ミリ秒置いて次の反復へ戻り、失敗の原因が解消するまで
繰り返し試みる(直ちに再試行すると失敗が続く間ずっと回り続けるため)。この間も状態区分は
「稼働中」のままとし、記録は連続する失敗の最初の1回と復帰の1回に限る(同じ記録の反復で
ローテーションが有用な履歴を押し流すのを避ける)。

### メニューからの開始

「停止済み」からのみ受け付ける。

- 「停止処理中」は前の稼働世代のIPCサーバースレッドがまだ終了していない状態(停止した時点で
  処理中だった要求が残っている等)である。この間に新しい稼働世代を開始すると、旧世代が処理中の
  要求と新世代が受ける要求が並行し、要求の直列処理とUIディスパッチの直列性が崩れるため開始しない。
  この状態は前の稼働世代のスレッドの終了で解消し、次のメニュー再実行では「停止済み」と判定されて
  開始できる。
- 「開始せず(応答サイズ予算の設定が不正)」からの開始は、環境変数を読み直しても同じ結果になるため
  受け付けない。

開始は新しい稼働世代を作ってIPCサーバースレッドを開始する。パイプ名はエディタのプロセスIDで
決まるため停止・開始をまたいでも同じ名前になり、衝突しない。不可視Formは起動時に生成したものを
作り直さずに使い続ける。

### Dispose

(1)[停止手順](#停止手順)を実行する(IPCサーバースレッドが残っていても背景スレッドなのでプロセス終了で
回収されることを許容する) (2)[常駐保持したCプラグイン連携のコネクタを手放す](#接続の常駐保持)
(3)不可視FormをClose/Disposeする (4)`base.Dispose()` を呼ぶ。

### UIスレッドへの委譲

PEPlugin APIの呼び出しは必ず不可視Formの `Invoke` でUIスレッドへ委譲する。`Invoke` で開始した
UI処理は中断しない。

## ブリッジの構成

ブリッジは、MCPクライアントとホストのあいだに立つ外部プロセスである。MCPクライアントとは
stdioで、ホストとは名前付きパイプでやり取りする。

### MCPサーバーとしての構成

- トランスポートはstdio。サーバー名は `pmx-editor-mcp`、バージョンはブリッジのアセンブリ
  バージョン。
- **ログ・診断は標準エラー出力へ出す。** 標準出力はプロトコルの通り道なので、既定のログ出力先を
  すべて取り除いたうえで、すべての水準を標準エラー出力へ送る。
- 登録するツールは「1ツール=ホストの1メソッドへの中継」を基本形とする。ツール群の登録は
  ツール契約仕様書と[能力台帳](pmx-editor-mcp-capability-ledger.md)が定める。
- ツールは `McpServerToolCreateOptions` の `Meta` へ `JsonObject` を設定し、
  `McpServerTool.Create` で作る。属性(`McpMetaAttribute`)は採らない——属性の値はコンパイル時
  定数であるのに対し、付与する値は環境変数から実行時に決まり、宣言の有無も実行時に切り替える
  必要があるため、属性では表せない。
- 各ツール定義には `_meta` の `anthropic/maxResultSizeChars` を1件付け、値は
  [応答サイズ予算の設定](#応答サイズ予算の設定)のブリッジ側の値とする。宣言するのはホストの
  本文に与えた予算そのもので、先頭へ置く[接続先の知らせ](#接続先の知らせ)の分は足さない——
  予算に足すと、予算を上限まで設定したときに宣言できる値の上限を超えてしまう。メタデータは
  ツールごとに作る(同じ木を使い回すと、書き換えられる木を全ツールが共有する)。
- ツールの一覧はホストへ接続せずに答える。接続はツール呼び出しまで行わない。

### ホストへの接続

接続先のパイプ名は、**待ち受けているホストの列挙**で決める。`\\.\pipe\` の直下を列挙し、
接頭辞 `pmx-editor-mcp-` に続く部分がホストの名乗り方どおりのプロセスID(正の十進、先頭に0を
付けない、ASCIIの数字だけ)である項目をホストの待受として拾う。パイプディレクトリには無関係な
名前が多数並ぶため、接頭辞だけでは絞り込まない。

- ちょうど1つなら、それを接続先とする。**エディタが何個起動していても、待ち受けているホストが
  1つなら接続先は決まる。** 数えるべきは接続できる相手であって、エディタの数ではない——
  プラグインを配置していないエディタ、メニューから停止したエディタ、応答サイズ予算の設定が
  不正で待受を開始しなかったエディタは、プロセスは在っても接続先の候補にならない。
- 0本のときは、プロセス名 `PmxEditor_x64` のプロセスを数えて案内を分ける。0個なら
  `BRIDGE_NO_EDITOR` でエディタの起動を促し、1個以上なら `BRIDGE_NO_HOST` でエディタの
  プラグインメニュー「PMX Editor MCP」での稼働状態の確認を促す。エディタの数はこの分岐以外に
  影響しない。
- 2本以上のときは `BRIDGE_MULTIPLE_HOSTS`。本文は決められないという事実と、候補のパイプ名を
  **プロセスIDの昇順**で改行区切りに列挙したものに留め、どのエディタを対象にするかを利用者に
  確かめるよう促す(列挙の順序は保証されないので、並べ替えないと同じ状況でも本文が呼び出し
  ごとに変わる)。**この本文に環境変数の設定や登録のやり直しといった設定作業を書かない**——
  読むのは呼び出し元のエージェントで、ブリッジの起動設定を書き換える立場にない。

エディタを数えるのは待受が無いときの案内を分けるためだけなので、待受から答えが出る場合は
数えない。環境変数の読み取り・パイプの列挙・プロセスの検索はいずれもOSから取るもので失敗
しうるため、失敗はどの材料を取れなかったかを添えた `BRIDGE_CONNECT_FAILED` へ変換する。

**利用者が接続先を選び分けるための環境変数は設けない。** パイプ名にはエディタのプロセスIDが
入るため、環境変数で指定する形にすると、エディタを起動し直すたびにMCPサーバーの登録をやり
直すことになる。利用者の登録操作は一度で済ませる。複数のホストが待ち受けているときは、対象に
しないエディタのプラグインメニューからホストを停止して待受を1つに絞る。

テストが接続先を固定するための環境変数 `PMX_EDITOR_MCP_TEST_PIPE` だけを設ける。定義されて
いればその名前をそのまま使い、空文字列も指定として扱って黙って列挙へ落とさない。実機では
ホストが待ち受けていると自動発見が曖昧になり、E2Eテストが不安定になるためのもので、利用者
向けの接続先の選び分けには用いない。

接続先は接続のたびに決め直す。エディタの起動・終了でパイプ名は変わるので、一度決めた名前を握り
続けると繋ぎ直しが消えたエディタを指したままになる。

接続のライフサイクルは、ツール呼び出し時に未接続なら接続して handshake(protocol=1)を行い、
以後は接続を維持して再利用する。切断を検出したら次の呼び出しで再接続する。handshake の成功応答は
`result` がオブジェクトであること・`protocol` が1であること・`hostVersion` が文字列であること・
`budgetChars` が整数であることを検証する。

パイプを開く待機の上限は **5秒**。接続先を決めた時点でそのパイプは待ち受けていたので、開けない
のは待って解決する話ではなく、決めてから開くまでの短い隙だけを見込む。超過は
`BRIDGE_CONNECT_FAILED` とし、本文では原因を断定せず、エディタの終了・ホストの停止・別の接続
による使用中を可能性として並べる(ホストは同時接続を1本に限るため、いずれも同じ形で表れる)。

### 接続先の知らせ

成功したツール結果は、**先頭行で接続先のパイプ名を必ず名乗る**(`接続先: <パイプ名>`)。直前に
名乗った相手と違うときは、変わった事実と前の相手も伝える(`接続先が変わった: <前のパイプ名> から
<今のパイプ名> へ。以前の応答は別のエディタのものである。`)。

毎回名乗るのは、呼び出し元が過去の知らせを覚えていることに依存させないためである。文脈が失われ
ても、その応答だけを見れば相手が分かる。名乗った相手は繋ぎ直しをまたいで覚えておくので、間に
失敗を挟んでも、変わった事実は次に成功した結果で伝わる。

**ブリッジ自身とホスト基盤の失敗**の結果は「エラーコード: メッセージ」の形式を保ち、接続先の行を
足さない。呼び出しが成立していないので知らせも消費されず、接続先が変わった事実は次に成功した結果で
伝わる。**ツールのドメインの失敗**は違う——呼び出しは成立していて知らせを消費するので、名乗りを
捨てると変わった事実がどの応答にも現れなくなる。したがってドメインの失敗の本文には接続先の行を
置く(形は[共通契約仕様書](pmx-editor-mcp-common-contract.md)が定める)。

知らせは応答と同じ戻り値で確定させ、確定の位置は要求の直列区間の中とする。応答を返した後で別に
取りに行く形だと、間に入った並行呼び出しが繋ぎ直したときに、応答と知らせの相手が食い違う。

### 呼び出しの直列化と待つ上限

- 同時に未完了となり得るホスト要求は1件に限る。接続の確立(handshakeを含む)から応答の受領までを
  排他区間とし、並行したMCPツール呼び出しは到着順の待ち行列で処理する。単なる排他では待っている
  側のどれが次に通るかが決まらないため、順番待ちは並びとして持つ。
- 接続・handshake・ホスト要求の待機上限は **125秒**(ホスト側の処理タイムアウト120秒に往復の
  余裕5秒を加えた値)。待ち行列で順番を待つ時間はこの上限に数えない。
- 待機上限超過・読み取り中断・要求送信後のMCP呼び出しキャンセル時は、その接続を無効化して閉じる
  (遅れて届く応答を次の要求の応答として誤読しないため)。次の呼び出しで新規に接続・handshakeする。
  **実行されたか不明な要求を自動で再送しない。**
- 待ち行列で未送信のMCP呼び出しがキャンセルされた場合は、待ち行列から除外するだけとし、接続は
  閉じない(応答待ち中の先行要求を巻き添えにしない)。
- 待ち行列から取り出された後、接続確立またはhandshakeの途中でキャンセルされた場合は、その接続処理を
  中止し、部分的に確立した接続は閉じて再利用しない。

### 要求と応答の検査

- **送信前検査**: ホストへ送る要求本文のUTF-8バイト数を送信前に検査し、上限
  ([IPC仕様書のサイズ制限](pmx-editor-mcp-ipc.md#サイズ制限))を超える場合は送信せず
  `BRIDGE_REQUEST_TOO_LARGE` を返す(ホスト側の切断を誘発しない)。接続は維持する。
- **応答の検証**: 読み取りは同じ上限付きで行い、改行が来ない巨大応答も上限で打ち切る。厳格な
  UTF-8でデコードし、JSON-RPC応答の構造と要求idとの一致を検証する。解析で許す入れ子の深さは、
  ホストが組み立てうる深さの応答を受け取れる値とする。
- エラー応答は識別子が null であることも許す。ホストは要求の識別子を判別できないときと応答が上限を
  超えたときに null を載せる契約なので、ここで弾くとホストが返した理由が失われる。

### エラー契約

**ブリッジ自身とホスト基盤の失敗**はMCPツール結果(`isError`=true、テキストコンテンツ1件)で返し、
本文は「エラーコード: メッセージ」の形式とする。**ブリッジのプロセスは落とさない。**

ホストのJSON-RPC `error` は、コードを `HOST_<数値コード>`(例 `HOST_-32601`)へ写し、メッセージは
ホストのものをそのまま用いる。ホストが応答のあとに切断する契約のコード
([IPC仕様書のエラーと切断の規則](pmx-editor-mcp-ipc.md#エラーと切断の規則))を受けたときは、
接続を捨ててから返す——保つと次の呼び出しが死んだ接続を使って必ず落ちる。

ブリッジ自身のエラーコードは次のとおり。

| コード | 事象 | 接続 |
|---|---|---|
| `BRIDGE_NO_EDITOR` | エディタ未起動。起動の案内を含む | — |
| `BRIDGE_NO_HOST` | エディタは起動しているが待ち受けているホストがない。稼働状態の確認先を含む | — |
| `BRIDGE_MULTIPLE_HOSTS` | ホストが複数待ち受けている。候補のパイプ名を含む | — |
| `BRIDGE_CONNECT_FAILED` | 接続先を決められない、または接続の確立に失敗 | — |
| `BRIDGE_HANDSHAKE_MISMATCH` | handshakeの不成立 | 閉じる |
| `BRIDGE_BUDGET_MISMATCH` | ホストの応答サイズ予算がブリッジ自身の値と一致しない | 閉じる |
| `BRIDGE_CONNECTION_LOST` | 応答待ち中の切断・読み取り中断 | 閉じる |
| `BRIDGE_PROTOCOL_ERROR` | handshake成立後のホスト応答の不正 | 閉じる |
| `BRIDGE_TIMEOUT` | 待機上限超過 | 閉じる |
| `BRIDGE_REQUEST_TOO_LARGE` | 送信前検査での要求サイズ超過 | 維持 |

`BRIDGE_HANDSHAKE_MISMATCH` は、handshake処理中にホストが返すJSON-RPCエラー(プロトコル番号
不一致の -32001 を含む)と、handshake成功応答の内容不正を、`HOST_` 形式ではなくこのコードへ
変換する。**分類の原則**: handshakeの応答受領まで(成立前)の応答の不正はこのコード、成立後の
応答の不正は `BRIDGE_PROTOCOL_ERROR`。応答を受け取る前の切断は応答の不正ではないので
`BRIDGE_CONNECTION_LOST` とする——そうしないと、ホストが消えただけの場合に版やプロトコルの
食い違いを示唆する説明が要求元へ返る。

`BRIDGE_BUDGET_MISMATCH` の本文にはホストとブリッジの両方の値を含める。照合は**毎回の
handshake で**行うので、切断後の再接続でホストの設定が変わっていた場合もここで捕まる。ブリッジの
プロセスは終了させず、一致するホストへ接続できた時点で通常の動作へ戻る。閉じた接続を同じ呼び出しの
中で張り直すことはせず、次の呼び出しで新規に接続する。

## 応答サイズ予算の設定

ホストとブリッジは、それぞれ環境変数 `PMX_EDITOR_MCP_BUDGET_CHARS` から応答サイズ予算の文字数を
読む。**値の構文と有効範囲は両者で同一**とする。

- 未設定時の既定は **100,000**。
- 値の構文はASCII数字のみからなる10進表記。符号・前後の空白・先頭のゼロ・ASCII以外の数字は
  受理しない。
- 有効範囲は **10,000 以上 500,000 以下**。
- 構文違反・範囲外のときは既定値へ落とさない。

構文違反・範囲外のときの振る舞いは、担う役割が違うので両者で異なる。

- ホストは**IPCの待受を開始せず**、理由をログへ記録してメニュー再実行の状態表示にも出す
  (エディタは巻き込まない)。環境変数はエディタの起動時に一度だけ読む。
- ブリッジは**標準エラー出力へ理由を1行出して終了コード 2 で終了する**。理由に載せる値は、
  1行に収まるよう制御文字と行区切りを符号位置の表記へ置き換え、長い値は切り詰めて元の長さを添える。

ホストが読み取った値は handshake 応答の `budgetChars` に載せる
([IPC仕様書のハンドシェイク](pmx-editor-mcp-ipc.md#ハンドシェイク))。ブリッジは自分が読み取った
値をツール定義の `_meta` へ載せ([MCPサーバーとしての構成](#mcpサーバーとしての構成))、毎回の
handshake で `budgetChars` と照合する。一致しなければ接続を閉じて `BRIDGE_BUDGET_MISMATCH` を
返す([エラー契約](#エラー契約))。

**この値をどう使うか**(警告枠との内訳・`limit` の逆算・この値を選んだ理由)は共通契約仕様書が
定める。ホストとブリッジは値を読んで載せ、照合するところまでを担う。

## 危険操作の公開方針

危険操作(エディタ終了・ファイルの上書き保存・モデル初期化)に対応するツールは、引数
`confirm: true` の明示を必須とし、無い場合は実行せずエラーを返す。対象ツールの指定は
[能力台帳](pmx-editor-mcp-capability-ledger.md)の備考とツール契約仕様書が行う。

## ログと診断

- 出力先は `%TEMP%\pmx-editor-mcp-host-<エディタのプロセスID>.log`(インスタンス間で競合しない)。
- 1MiB(1,048,576バイト)を超えると同名 `.1` へローテーションする(1世代)。ローテーションに
  失敗しても追記は続ける(ローテーション先が開かれ続けている間に記録全体が止まるのを避ける。
  閾値を一時的に超えることは許容する)。
- 記録内容は、起動・停止(メニューからの停止・開始を含む)・接続・切断・返したエラー応答の
  エラーコード・ホスト内部の例外(スタックトレース付き)・処理タイムアウト・Cプラグインコネクタの
  取得と破棄・ハンドルの解放と全ハンドルの解放。**ハンドルのIDを記録してよいのは台帳に在るものだけ**
  とし、台帳に無いIDは記録しない——要求の相手は任意の値を置けるので、そのまま写すと要求の内容を
  記録することになる。
- Cプラグインコネクタの取得と破棄を記録するのは、**取得が常駐期間を通じて一度だけであること**と
  **終了時に手放したこと**を、後から記録だけで確かめられるようにするためである。**確かめる側は
  ローテーション先(`.1`)も併せて読む。** それでも溢れた常駐では取得の行が残らないので、そのときは
  記録から確かめられない——記録の総量が閾値の2世代を超えるほど長く動かした場合の限界である。
- ハンドルは、解放の1件ごとに加えて**まとめて解放したことを件数とともに**記録する。1件も無くても
  記録する。これで**終了時にまとめての解放が走ったこと**を記録から確かめられる。それより前に何件を
  発行したかは記録しないので、**発行の総数と突き合わせる形では確かめられない**。
- エラー応答の説明の本文は要求の値を指すことがあるため記録しない。エラー応答は相手がいくらでも
  起こせるので、記録は接続ごとにコードの最初の1回と、接続が切れたところで繰り返した回数の合計に
  限る。これが抑えるのは1つの接続内での反復までで、接続し直しを繰り返す相手は、接続・切断の記録と
  ともにログを増やせる。

- 処理タイムアウトの記録にはメソッド名を含める。無いと記録から得られるのは「何かが超過した」
  だけになり、UIスレッドを占有したまま固まった操作を後から突き止められない。含めてよいのは
  メソッドの検索に一致した名前(基盤メソッドを含む)だけで、一致しなかった名前は接続の相手が
  任意の文字列を置けるため記録しない。
- **要求の内容は記録しない**(モデルデータを含みうるため)。ここでいう要求の内容とは `method`
  以外のすべて——他の項目・契約外の余分なメンバー・本文をそのまま写したもの——を指す。ログへ記録
  される例外のうち要求の値に触れうるもの(要求処理の予期しない例外と待受ループの例外)は、その
  メッセージにも要求の値を引用しない。要求元へ返すだけで記録しない説明(不正な引数の説明など)は
  この制限の対象外で、問題の値を指してよい。
  ホストの外から来る例外のメッセージは制御できないため、そこへ要求の値が引き写されて記録される
  ことは残存リスクとして受け入れる(制御できる箇所を塞いだうえでの残余で、ツールの失敗を追う
  手掛かりがメッセージしか無い)。
- 現在のログパスはメニュー再実行の状態表示で確認できる。

## 設計判断の理由

- **PEPlugin API呼び出しをUIスレッドへ委譲する**: PEPlugin APIのスレッドセーフティを仮定しない
  ため。不可視Formの `Invoke` でワーカースレッドからUIスレッドへ到達できることは実機で確かめて
  ある([能力台帳の実機確認](pmx-editor-mcp-capability-ledger.md#実機確認で確かめたこと))。
  委譲先を起動時実行で作った不可視Formにしているのは、起動時実行がUIスレッドで呼ばれるため、
  そこで作ったFormのハンドルがUIスレッドに属すると分かっているからである。
- **ホストDLLの置き場を `_plugin\User\` の1つにする**: `_plugin` 直下と `User` の両方にDLLが
  あると、エディタは2つともロードする(起動ログが2行・メニュー項目が2つになることを実測した)。
  こうなると同じパイプ名のホストが2つになり、インスタンス数1の待受を後発が作れず「すべてのパイプ
  インスタンスがビジーです」で失敗する。配布物が利用者の作成したプラグインの置き場として `User`
  を勧めているため、残す1つをこちらにした。
- **デプロイはすべてのエディタを終了してから行い、反映は次回のエディタ起動から**: 起動中の
  エディタはロード中のプラグインDLLを掴んでおり、同名での上書きコピーは配置先のロックで失敗する
  (`Copy` タスクが `MSB3027` と `MSB3021` を出すことを実測した)。ロード中のDLLを退けて別名の
  新DLLを置くことはできるが、同名では上書きできない。
- **ブリッジは起動時にホストへ接続しない**: 接続を起動時に張ると、エディタより先にブリッジが
  起動した場合に立ち上がれない。ツール呼び出しまで遅らせれば、`tools/list` はブリッジ自身の設定値
  だけで答えられ、エディタの起動順に縛られない。
- **応答サイズ予算の一致を毎回の handshake で照合する**: ブリッジは `tools/list` を自分の設定値で
  答えるので、ホストの値と食い違うと、宣言したしきい値と実際に返る量が合わなくなる。起動時に
  一度だけ確かめる形では、切断をまたいでホストの設定が変わった場合を捕まえられない。
- **停止手順で呼び出しスレッドをブロックしない**: メニューからの停止も `Dispose` もUIスレッドから
  呼ばれうる。ここでIPCサーバースレッドの終了を待つと、UIスレッドへの `Invoke` を待っている要求
  処理があるときに相互待ちになり、待ちが必ず空振りするため。代わりに、終わりきっていない状態を
  「停止処理中」として状態表示に出し、開始を受け付けないことで直列性を守る。
