# pmx-editor-mcp アーキテクチャ仕様書

pmx-editor-mcp の構成・ライフサイクル・運用の正本(現時点ではエディタ側プラグイン——以下
ホスト——を定める)。ホストと外部プロセスの間で交わすプロトコルは
[IPC仕様書](pmx-editor-mcp-ipc.md)が定める。ツール化する能力の一覧は
[PEPlugin SDK 能力台帳](pmx-editor-mcp-capability-ledger.md)が持つ。

## プロジェクト構成

- [PmxEditorMcp.HostPlugin.csproj](../../src/HostPlugin/PmxEditorMcp.HostPlugin.csproj):
  net48のクラスライブラリ。成果物名は `PmxEditorMcp.dll`。プラットフォームは AnyCPU で、
  実行対象は x64版エディタ `PmxEditor_x64.exe` のプロセス。参照アセンブリは
  `Microsoft.NETFramework.ReferenceAssemblies` 1.0.3 で解決する。
- [tests/HostPlugin.Tests](../../tests/HostPlugin.Tests) の
  `PmxEditorMcp.HostPlugin.Tests.csproj`: net48・xUnit。UIスレッドとエディタ実機に依存
  しないロジックを対象とする。
- 両プロジェクトは [PmxEditorMcp.sln](../../PmxEditorMcp.sln) に含める。

## ビルドとデプロイ

### PMXエディタ導入ディレクトリの指定

PMXエディタの導入先は環境ごとに異なるため、リポジトリ直下のGit管理外ファイル `local.props`
(`.gitignore` に登録済み)へ `PmxEditorDir` プロパティとして定義する。追跡下の
[Directory.Build.props](../../Directory.Build.props) が行うのはImportだけで、`local.props` が
存在するときだけ読み込む(無い環境ではImportをスキップするだけで、`Directory.Build.props` の
評価は失敗しない)。

未定義のまま進むことを止めるのはホストcsprojの `EnsurePmxEditorDir` ターゲットで、ビルドと
デプロイの前に走り、`PmxEditorDir` が空なら「local.props に PmxEditorDir を定義せよ」という
明示エラーで失敗させる。

### PEPlugin.dll の参照

`$(PmxEditorDir)\Lib\PEPlugin\PEPlugin.dll` を HintPath で参照する。`Private=false` とし、
配布物のDLLは成果物へコピーしない。PMXエディタ配布物の利用規約がパッケージ内データの再配布を
禁じているため、各自の導入物を参照するだけにする。

### デプロイ

ホストcsprojの `Deploy` ターゲット(`Build` に依存)が、成果物を
`$(PmxEditorDir)\_plugin\User\` へ変更時のみコピーする。

```
dotnet build src/HostPlugin/PmxEditorMcp.HostPlugin.csproj -t:Deploy
```

**ホストDLLの置き場はこの1つとする。** デプロイはすべてのエディタを終了してから行い、反映は
次回のエディタ起動からになる。手順と確認の正本は[検証手順書](../conventions/verification.md)、
どちらの制約も理由は[設計判断の理由](#設計判断の理由)。

## プラグインのライフサイクル

クラス `PmxEditorMcpPlugin`(PEPluginClass派生)が実体で、オプションは起動時実行とメニュー登録
(メニュー文言「PMX Editor MCP」)。

### 起動時実行

起動時実行はエディタのUIスレッドで呼ばれる(実機で確かめてある)。ここで不可視Formを生成して
ハンドルを確保するので、以後のUIディスパッチはこのFormを通せばUIスレッドへ届く。続けて稼働世代を
1つ作り、IPCサーバースレッド(背景スレッド)を開始する。ただし
[応答サイズ予算の設定](#応答サイズ予算の設定)が不正なときは待受を開始せず、状態区分は
「開始せず(応答サイズ予算の設定が不正)」になる。

この経路の例外はすべて捕捉してエディタを巻き込まない。ログへ記録できるのはログの初期化より
後で起きた例外に限る(初期化前の例外は捕捉されるだけで記録が残らない)。

### 稼働世代

受付停止フラグ・公開中のパイプインスタンス・IPCサーバースレッドの参照を1つの「稼働世代」として
まとめて保持し、開始のたびに新しい稼働世代を作る。停止手順・状態判定・UIディスパッチの可否は
すべて稼働世代の単位で決まり、停止した稼働世代での禁止を新しい稼働世代へ持ち越さない。

### メニュー再実行と状態表示

メニューの再実行では、稼働状態(状態区分・パイプ名・接続状態・応答サイズ予算・ログパス)を
メッセージボックスで表示し、そこからホストの停止・開始を選べる(起動時実行のやり直しはしない)。
状態区分は次の4つで、メニュー再実行のたびに判定する。ホストがそもそも生成できていない
(起動時実行が失敗した)ときは、状態区分を出さず「ホストが常駐していない。エディタを起動し直す。」
の警告だけを表示して何もしない。

| 状態区分 | 意味 |
|---|---|
| 稼働中 | 要求を受け付けている |
| 停止処理中 | 停止した稼働世代のIPCサーバースレッドがまだ終わっていない |
| 停止済み | 開始できる |
| 開始せず(応答サイズ予算の設定が不正) | 設定が不正なため待受を開始していない |

「稼働中」なら「停止しますか?」、「停止済み」なら「開始しますか?」を既定「いいえ」のはい/いいえで
確認し、はいのときだけ停止・開始を行う。その結果は表示しない(状態は次のメニュー再実行で分かる)。
開始が受け付けられなかったときは、開始できなかった理由をログへ記録する。「停止処理中」と
「開始せず(応答サイズ予算の設定が不正)」では問いを出さず、なぜ開始できないかを状態表示の本文に
含める。停止・開始の操作は排他ロックで直列化し、呼び出しスレッドを仮定しない。

### 停止手順

メニューからの停止と `Dispose` が共有する。排他ロックの下で、

1. 現在の稼働世代の受付停止フラグを立てる。
2. その稼働世代が公開しているパイプインスタンスがあれば閉じる(`PipeOptions.Asynchronous` で
   生成しているため、`WaitForConnection` と読み取りのブロックが即座に解ける)。
3. 以後その稼働世代ではUIディスパッチを行わない。

**呼び出しスレッドをブロックしてIPCサーバースレッドの終了を待つことはしない。** 理由は
[設計判断の理由](#設計判断の理由)。

### 待受ループ

IPCサーバースレッドの1回の反復は、排他ロックの下で自分の稼働世代の受付停止フラグを確認し、
立っていればループを抜け、立っていなければ新しいパイプインスタンスを生成して稼働世代へ公開する
ところから始める。ロックを解いてから `WaitForConnection` と要求処理を行う。停止手順が
「フラグを立てる」と「公開中のインスタンスを閉じる」を同じロックの下で行うため、フラグ確認を
すり抜けて生成されたインスタンスが閉じられないまま待受に残ることはない。

停止で閉じられたインスタンスは、待受中なら `WaitForConnection` が例外で戻り、接続中なら
読み取りが0バイトを返して戻る(いずれも切断として扱う)。ループ内の例外は捕捉してログへ記録し、
フラグが立っていればループを抜ける(立っていなければ次の反復へ戻る)。停止した時点で要求を
処理中だった場合は、その要求の処理を終えてから次の反復へ入り、そこでフラグを見て終了する。

パイプインスタンスの生成に失敗したときは500ミリ秒置いて次の反復へ戻り、失敗の原因が解消するまで
繰り返し試みる(直ちに再試行すると失敗が続く間ずっと回り続けるため)。この間も状態区分は
「稼働中」のままとし、記録は連続する失敗の最初の1回と復帰の1回に限る(同じ記録の反復で
ローテーションが有用な履歴を押し流すのを避ける)。

### メニューからの開始

「停止済み」からのみ受け付ける。

- 「停止処理中」は前の稼働世代のIPCサーバースレッドがまだ終了していない状態(停止した時点で
  処理中だった要求が残っている等)である。この間に新しい稼働世代を開始すると、旧世代が処理中の
  要求と新世代が受ける要求が並行し、要求の直列処理とUIディスパッチの直列性が崩れるため開始しない。
  この状態は前の稼働世代のスレッドの終了で解消し、次のメニュー再実行では「停止済み」と判定されて
  開始できる。
- 「開始せず(応答サイズ予算の設定が不正)」からの開始は、環境変数を読み直しても同じ結果になるため
  受け付けない。

開始は新しい稼働世代を作ってIPCサーバースレッドを開始する。パイプ名はエディタのプロセスIDで
決まるため停止・開始をまたいでも同じ名前になり、衝突しない。不可視Formは起動時に生成したものを
作り直さずに使い続ける。

### Dispose

(1)[停止手順](#停止手順)を実行する(IPCサーバースレッドが残っていても背景スレッドなのでプロセス終了で
回収されることを許容する) (2)不可視FormをClose/Disposeする (3)`base.Dispose()` を呼ぶ。

### UIスレッドへの委譲

PEPlugin APIの呼び出しは必ず不可視Formの `Invoke` でUIスレッドへ委譲する。`Invoke` で開始した
UI処理は中断しない。

## 応答サイズ予算の設定

ホストは環境変数 `PMX_EDITOR_MCP_BUDGET_CHARS` から応答サイズ予算の文字数を読む。

- 未設定時の既定は **100,000**。
- 値の構文はASCII数字のみからなる10進表記。符号・前後の空白・先頭のゼロ・ASCII以外の数字は
  受理しない。
- 有効範囲は **10,000 以上 500,000 以下**。
- 構文違反・範囲外のときは既定値へ落とさず、**IPCの待受を開始せず**、理由をログへ記録して
  メニュー再実行の状態表示にも出す(エディタは巻き込まない)。
- 環境変数はエディタの起動時に一度だけ読む。

読み取った値は handshake 応答の `budgetChars` に載せる
([IPC仕様書のハンドシェイク](pmx-editor-mcp-ipc.md#ハンドシェイク))。**この値をどう使うか**
(警告枠との内訳・`limit` の逆算・この値を選んだ理由)は共通契約仕様書が定める。ホストは値を
読んで載せるところまでを担う。

## 危険操作の公開方針

危険操作(エディタ終了・ファイルの上書き保存・モデル初期化)に対応するツールは、引数
`confirm: true` の明示を必須とし、無い場合は実行せずエラーを返す。対象ツールの指定は
[能力台帳](pmx-editor-mcp-capability-ledger.md)の備考とツール契約仕様書が行う。

## ログと診断

- 出力先は `%TEMP%\pmx-editor-mcp-host-<エディタのプロセスID>.log`(インスタンス間で競合しない)。
- 1MiB(1,048,576バイト)を超えると同名 `.1` へローテーションする(1世代)。ローテーションに
  失敗しても追記は続ける(ローテーション先が開かれ続けている間に記録全体が止まるのを避ける。
  閾値を一時的に超えることは許容する)。
- 記録内容は、起動・停止(メニューからの停止・開始を含む)・接続・切断・返したエラー応答の
  エラーコード・ホスト内部の例外(スタックトレース付き)・処理タイムアウト。エラー応答の説明の
  本文は要求の値を指すことがあるため記録しない。エラー応答は相手がいくらでも起こせるので、
  記録は接続ごとにコードの最初の1回と、接続が切れたところで繰り返した回数の合計に限る。これが
  抑えるのは1つの接続内での反復までで、接続し直しを繰り返す相手は、接続・切断の記録とともに
  ログを増やせる。

- 処理タイムアウトの記録にはメソッド名を含める。無いと記録から得られるのは「何かが超過した」
  だけになり、UIスレッドを占有したまま固まった操作を後から突き止められない。含めてよいのは
  メソッドの検索に一致した名前(基盤メソッドを含む)だけで、一致しなかった名前は接続の相手が
  任意の文字列を置けるため記録しない。
- **要求の内容は記録しない**(モデルデータを含みうるため)。ここでいう要求の内容とは `method`
  以外のすべて——他の項目・契約外の余分なメンバー・本文をそのまま写したもの——を指す。ログへ記録
  される例外のうち要求の値に触れうるもの(要求処理の予期しない例外と待受ループの例外)は、その
  メッセージにも要求の値を引用しない。要求元へ返すだけで記録しない説明(不正な引数の説明など)は
  この制限の対象外で、問題の値を指してよい。
  ホストの外から来る例外のメッセージは制御できないため、そこへ要求の値が引き写されて記録される
  ことは残存リスクとして受け入れる(制御できる箇所を塞いだうえでの残余で、ツールの失敗を追う
  手掛かりがメッセージしか無い)。
- 現在のログパスはメニュー再実行の状態表示で確認できる。

## 設計判断の理由

- **PEPlugin API呼び出しをUIスレッドへ委譲する**: PEPlugin APIのスレッドセーフティを仮定しない
  ため。不可視Formの `Invoke` でワーカースレッドからUIスレッドへ到達できることは実機で確かめて
  ある([能力台帳の実機確認](pmx-editor-mcp-capability-ledger.md#実機確認で確かめたこと))。
  委譲先を起動時実行で作った不可視Formにしているのは、起動時実行がUIスレッドで呼ばれるため、
  そこで作ったFormのハンドルがUIスレッドに属すると分かっているからである。
- **ホストDLLの置き場を `_plugin\User\` の1つにする**: `_plugin` 直下と `User` の両方にDLLが
  あると、エディタは2つともロードする(起動ログが2行・メニュー項目が2つになることを実測した)。
  こうなると同じパイプ名のホストが2つになり、インスタンス数1の待受を後発が作れず「すべてのパイプ
  インスタンスがビジーです」で失敗する。配布物が利用者の作成したプラグインの置き場として `User`
  を勧めているため、残す1つをこちらにした。
- **デプロイはすべてのエディタを終了してから行い、反映は次回のエディタ起動から**: 起動中の
  エディタはロード中のプラグインDLLを掴んでおり、同名での上書きコピーは配置先のロックで失敗する
  (`Copy` タスクが `MSB3027` と `MSB3021` を出すことを実測した)。ロード中のDLLを退けて別名の
  新DLLを置くことはできるが、同名では上書きできない。
- **停止手順で呼び出しスレッドをブロックしない**: メニューからの停止も `Dispose` もUIスレッドから
  呼ばれうる。ここでIPCサーバースレッドの終了を待つと、UIスレッドへの `Invoke` を待っている要求
  処理があるときに相互待ちになり、待ちが必ず空振りするため。代わりに、終わりきっていない状態を
  「停止処理中」として状態表示に出し、開始を受け付けないことで直列性を守る。
