# pmx-editor-mcp 日本語名仕様書

SDKの公開プロパティ1件ごとに付ける日本語名の付け方の規則を定める。名前は
ツールの説明文の索引語と、発見可能性を測る想定質問文が引く語である。名前の多くは配布物の記載から
導けるので、[`pmx-editor-mcp-property-names.json`](pmx-editor-mcp-property-names.json) が値として
持つのは**導けない項目、すなわち名前を起こした項目だけ**である。

型ごとの役割・要素名詞・ツール名は別の表が持つ。この表を型ごとの項目へ入れ子にしないのは、
鍵が違うためである——型ごとの表の鍵は役割対象の型だが、この表の鍵は宣言型で、継いだプロパティの
宣言型は基底型であり、その基底型自身が役割対象とは限らない。入れ子にすると同じ項目が役割対象の
数だけ重複し、下記の「同じ宣言型の同じ名前は1件」と衝突する。

## 対象

**役割対象の型**が持つ**読み取り可能な公開プロパティ**を対象とする。役割対象の型の母集合は
[役割対象仕様書](pmx-editor-mcp-role-types.md)が定め、能力台帳と除外一覧とSDKの列挙から機械で導く
——本書は値としてそれを持たず、日本語名の照合が同じ3つを引数に取るのはこのためである。

宣言したプロパティに限らず、基底型から継いだものと、対象アセンブリ外の型が持つものを含む——役割
対象にはイベント引数の外部型が入り、その型の項目も応答へ埋め込むためである。同じ宣言型の同じ名前は
1件として数える。

宣言型は、名前空間を含む完全名で書く。入れ子は `+` で区切り、総称型は山括弧の中へその段の型引数を
並べ(複数あればカンマで区切り、空白を入れない)、配列は角括弧、参照渡しは末尾の `&` で表す——
列挙が書き出す型名と同じ表記で、照合はその表記で突き合わせる。同じ総称型でも開いた定義と閉じた型は
別の項目になる——プロパティの型が違い、応答の形も違うためである。

## 記載の取り出し

配布物のドキュメントXMLからその member の**記載**を取り出す操作を、次の一つの手順で定める。名前を
採るのも、決め方を分けるために数えるのも同じ文字列を見るので、別々に定めると食い違う。

1. その member の `summary` を取る。
2. 行ごとに前後の空白を落とし、空行を捨てる。
3. **最初の行だけ**を採る。
4. その行に縦棒があれば**最初の縦棒より前**を採り、その末尾の空白を落とす。
5. 空白で区切った**末尾の1トークン**が `get`・`set`・`get/set` のいずれかに一致したら、そのトークンと
   その直前の空白を除く。一致しなければ何も除かない。

残った文字列がその member の記載である。空になる member は記載を取り出せなかったものとして扱う。

最初の行だけを採るのと、縦棒より前だけを採るのは、どちらも同じことをしている——配布物のXMLは名前に
続けて値の意味の補足を書く箇所を改行と縦棒の両方で作るので、補足を落とさないと名前にならず、接尾辞も
末尾に来ないので除去が効かない。末尾を1トークンとして見るのは、末尾の文字列だけを見て除くと
`get/set` から `set` だけが落ちて `get/` が残り、除いた後の空白も残るためである。

## 名前の決め方

名前は2通りに決まる。

- **記載を採る**: その型の中で他の項目と重ならない記載がある項目。名前はその記載をそのまま採る。
  **この名前は正本に書かない**——記載と宣言型とメンバー名から導けるので、書けば導き直しを忘れた
  ときにずれが残る。記載の位置である member 名も、宣言型とメンバー名から一意に導ける。
- **名前を起こす**: **使える記載が無い項目**——記載自体が無いものと、記載はあるが同じ型の別項目と
  同じ名前になるものの両方を含む。この項目だけが正本に載り、宣言型・メンバー名・日本語名・
  **意味の根拠**・名前の由来の一文を持つ。根拠は次のどちらかとする。
  - `documentSection`: 配布物の資料が意味を説明している場合。配布物からの相対パスと、開始行・終了行
    (どちらも1から数え、両端を含む)を持つ。綴りで探す形にしないのは、同じ綴りが資料の別の箇所にも
    現れる項目と、資料に一度も現れない項目の両方があるためで、綴りの出現では位置が一意にならない。
  - `memberShape`: 資料が意味を説明していない場合。宣言型・メンバー名・プロパティの型に拠る。前の2つは
    項目自身の鍵で、型は列挙が持つ。値としては持たせない。対象アセンブリ外の型の項目はこれを使う。
    実行環境の外部文書へは依存しない——版と言語が固定できず、配布物の中で解決できないためである。

**どちらに当たるかは書き手が選べない。** 上の手順で取り出した記載を同一の宣言型の中で数え、その数が
1のときだけ記載を採り、0または2以上のときは名前を起こす。数える母集合は対象の項目のうち記載が
取れたものに限り、同じ宣言型にあっても対象外の member の記載は数に入れない。これを課さないと、一意な
記載がある項目を勝手に起こしたり、同じ記載を持つ項目群の1件だけを記載のまま残して残りへ別の名前を
付けたりできてしまい、名前が重ならないので下の重複の検査にも掛からない。

## 検査

日本語名の照合が、次を検査する。

- 各項目が、列挙で得た宣言型・メンバー名の組に**実在すること**。二度現れないこと。
- 名前を起こす項目が**過不足なく載っていること**——記載を採れる項目が載っていれば、導ける名前を
  書いたことになる。記載を採れない項目が載っていなければ、その名前がどこにも決まらない。
- `documentSection` の根拠で、相対パスの資料が実在し、終了行がその資料の行数に収まること。
- 同一の宣言型の中で日本語名が重複しないこと。**導いた名前と起こした名前の両方**で見る——導いた
  名前どうしは記載が一意なので重ならないが、起こした名前とは重なりうる。

次の条件は正本を読む時点で確かめる。日本語名が空でないこと。根拠の種別が上記2つのいずれかである
こと。由来の一文が空でないこと。`documentSection` の開始行が1以上で、終了行が開始行を下回らない
こと。そして、項目が宣言型・メンバー名の序数の昇順に並び、同じ宣言型の同じメンバー名が二度現れない
こと——並びを列挙側と同じ定義にそろえるので、項目を足すときは末尾ではなくその位置へ入れる。

**機械で確かめられるのはここまでである。** 起こした名前が的確かどうかを測る検査は置かない——想定
質問文の検査は質問文へこの日本語名を埋めて引くので、名前が不適切でも文字列が一致すれば通り、名前の
良否を測る検査にならない。起こした名前は書き手の判断で決め、その判断を由来の一文と根拠が後から
追える形にする、というところまでを規則とする。
