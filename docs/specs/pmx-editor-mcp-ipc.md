# pmx-editor-mcp IPC仕様書

エディタ側プラグイン(以下ホスト)と外部プロセスの間で交わすプロトコルの正本。ホスト自身の
構成・ライフサイクル・運用は[アーキテクチャ仕様書](pmx-editor-mcp-architecture.md)が定める。

## トランスポート

名前付きパイプを使う。パイプ名は `pmx-editor-mcp-<エディタのプロセスID>` の1本のみ。
名前の書式は本仕様書が定めるが、どのホストへ——どのパイプ名へ——接続するかの決め方は
接続する側(ブリッジ)の契約であり、アーキテクチャ仕様書が定める(現時点では未記載)。

## 接続

- パイプインスタンス数1(同時接続1)。切断されたら待受に戻る。
- 要求はホストインスタンス内で直列処理(同時実行1)する。
- パイプは **`PipeOptions.Asynchronous` で生成する**(APIの呼び方は同期のままでよい)。
- 伝送モードはバイト(メッセージの境界はパイプでなく改行区切りが決める)。入出力のバッファは
  各65536バイト。

## アクセス制御

PipeSecurityで現在ユーザーのSIDのみに FullControl を許可する。

## メッセージ形式

UTF-8(BOMなし)。1メッセージ1行で、出力の区切りはLF、入力はLF・CRLFの両方を受理する。本文は
JSON-RPC 2.0のサブセット。

- **要求**: `jsonrpc`(固定 `"2.0"`・必須)・`id`(数値または文字列・必須。通知=id無し要求は
  使用しない)・`method`(文字列)・`params`(オブジェクト。省略可)。
- **応答**: `jsonrpc`・`id`(要求と同値)・`result` または `error{code,message}`。`id` と
  `message` の例外は[エラーと切断の規則](#エラーと切断の規則)が定める。

シリアライザは `JavaScriptSerializer`(`System.Web.Extensions`)。既定の `MaxJsonLength` は
2,097,152文字で、そのままでは16MiBの本文を扱えない。解析では `MaxJsonLength` を 33,554,432 に
設定する(16MiBのUTF-8本文は最大 16,777,216文字なので、その2倍)。組み立てでは
`MaxJsonLength` を `int.MaxValue` にしてシリアライザ側の上限を実質外し、上限の判定は本文の
バイト数で行う([エラーと切断の規則](#エラーと切断の規則))。

## 読み取り

生バイトを上限付きで読む。累積バイト数が上限を超えた時点で読み取りを打ち切り、全文をメモリに
保持せずに上限超過として扱う(改行の到来を待たない)。デコードは厳格なUTF-8で行い、不正な
バイト列は構文不正として扱う。

## ハンドシェイク

接続後の最初の要求は `handshake`(params: `protocol`=1)でなければならない。成功応答の
`result` は次の形。

```json
{"protocol":1,"hostVersion":"<ホストDLLのアセンブリバージョン文字列>","budgetChars":100000}
```

`budgetChars` はホストが読んだ応答サイズ予算の文字数(数値)で、接続する側が自分の設定値と
照合するための項目である。値の決め方は
[アーキテクチャ仕様書の応答サイズ予算の設定](pmx-editor-mcp-architecture.md#応答サイズ予算の設定)。

handshake 済みの接続で引数が有効な handshake を再度受けたときは、状態を変えず同じ成功応答を
返す(引数が不正・番号が不一致のときは[エラーと切断の規則](#エラーと切断の規則)どおりに扱う)。
プロトコル番号の変更は互換を壊す変更のたびに行う。

## 基盤メソッド

`handshake` と `ping`(result: 文字列 `"pong"`)。

```
要求 {"jsonrpc":"2.0","id":1,"method":"ping"}
応答 {"jsonrpc":"2.0","id":1,"result":"pong"}
```

ツールに対応するメソッドはツール契約仕様書が定める。

## サイズ制限

1メッセージ=1行の本文(区切りのLF/CRLFを含まない)のUTF-8バイト数で上限16MiB。入力・出力の
両方向に適用する。

**これは名前付きパイプの上限であり、応答サイズの設計目標ではない。** MCPクライアント側の出力
上限は**トークン数**で定められており、バイト数の上限を満たしてもその上限を満たす保証にならない。
実効の応答サイズ予算は共通契約仕様書が別に定める。16MiBを応答サイズの設計値として流用しないこと。

## 判定の順序

1件の要求に対して次の順で適用し、最初に当たったところで応答を決める。

1. 入力メッセージの上限超過
2. UTF-8のデコードとJSON構文
3. 要求構造
4. handshake ゲート
5. handshake のプロトコル番号
6. メソッドの検索
7. 引数の検査
8. 実行(処理タイムアウト・予期しない例外・応答の上限超過)

この順により、最初の要求が構造不正のときは -32600 を返して接続を維持し(-32003 で切断しない)、
構造が妥当で `method` が handshake 以外(空文字列を含む)のときは -32003 で切断する。

## エラーと切断の規則

応答の `id` は、各項で特に断らないかぎり要求と同値とする。要求idを判別できないときは null とする。

| code | 事象 | 接続 |
|---|---|---|
| -32700 | JSON構文不正(UTF-8として不正なバイト列を含む) | 切断 |
| -32600 | 要求構造の不正 | 維持 |
| -32601 | 未知メソッド | 維持 |
| -32602 | 不正な引数 | 維持 |
| -32603 | 要求処理中の予期しない例外 | 維持 |
| -32001 | プロトコル番号不一致の handshake | 切断 |
| -32002 | ホスト側の要求処理が120秒を超過 | 維持 |
| -32003 | handshake 前に handshake 以外の要求 | 切断 |
| -32004 | 入力メッセージの上限超過 | 切断 |
| -32005 | 出力(応答)の上限超過 | 維持 |

- **-32700**: 本文を解析できないため要求idを判別できず、`id` は null。
- **-32600**: トップレベルがJSONオブジェクトでない・`jsonrpc` の欠落や `"2.0"` 以外・
  `method` の欠落・`method` が文字列以外・`id` の欠落や許容外の型。`method` が空文字列の
  ときは構造不正とせず、以降(handshakeゲート→メソッドの検索)の判定へ進む。`id` の不正と
  `params` の不正が同時にあるときは -32600 を先に判定する(応答に要求idを載せられるかが
  これで決まるため)。
- **-32602**: `params` がオブジェクト以外(配列・文字列・数値・真偽値・null)であることと、
  メソッドが要求する引数を満たさないことの両方が不正な引数にあたる。
- **-32603**: 応答の組み立てが上限以外の理由——循環参照・シリアライズできない値——で失敗した場合を
  含む。handshake 済み状態は維持し、例外はスタックトレース付きでログに記録する。
- **-32001**: 非互換の接続拒否。`protocol` の欠落・数値以外は番号の不一致ではないため -32001 と
  せず、不正な引数として扱う。
- **-32002**: 一度だけ返す。開始済みのUI処理は中断できないため、その完了までは次の要求を読み
  取らない(直列保証を維持する)。完了後の結果は破棄し、二重応答しない。超過はログに記録する。
  タイムアウト値はテストから差し替えられる。
- **-32004**: JSON解析前に判定するため要求idは使わず、`id` は null。
- **-32005**: 組み立てた本文のUTF-8バイト数が上限(16MiB)を超えたとき、結果を破棄して返す。
  大きな応答の回避はツール契約仕様書のページングが担う。**判定にシリアライザの例外を使わない**
  (理由は[設計判断の理由](#設計判断の理由))。組み立てはシリアライザ側の上限を外して行い、得られた
  本文を自分で測って判定する。文字数で重ねて判定しない: UTF-8のバイト数は文字数以上なので、
  バイト数の判定が文字数の判定を含む。上限はテストから差し替えられる。入力と違って
  組み立て後の全量が一度メモリに載るが、応答の量はツール契約仕様書のページングが抑えるため許容する。

上のどのエラーでも、組み立てたエラー応答のUTF-8バイト数が上限を超えるときは `id` を null にし、
なお超えるときは `message` を空にして、コードだけは返す(いずれもキー自体は残す)。接続を切るか
どうかはコードごとの扱いを変えない——ここで書き込みに失敗させると、接続を保つはずのエラーが
すべて切断に化ける。

## 設計判断の理由

- **パイプ名にエディタのプロセスIDを含め、1本だけにする**: エディタは複数同時に起動しうる。
  名前がプロセスIDで決まると、どのホストが名乗り出るかという所有権の問題も、そのホストが消えた
  ときの再選出の問題も生じない。実際にエディタを2つ起動し、それぞれのパイプへ独立に接続できる
  ことを実測した。名前はエディタのプロセスIDだけで決まるので、ホストの停止・開始をまたいでも
  変わらない。
- **パイプを `PipeOptions.Asynchronous` で生成する**: このオプションを付けずに生成すると、
  別スレッドからの `Dispose` は即座に返るのに `WaitForConnection` も接続後の読み取りも3秒経って
  戻らなかった(同期I/Oの完了まで実際のハンドルクローズが遅延されるため)。このオプションを
  付けると、同期APIのまま `WaitForConnection` が2msで例外となり、読み取りは0バイトを返して
  即座に戻る。APIの呼び方は同期のままでよく、必要なのは生成時のこの指定だけ。
- **シリアライザに `JavaScriptSerializer` を使う**: `System.Web.Extensions` は .NET Framework に
  同梱されており、プラグインDLLに同梱する依存を増やさずJSONを扱える。配布物へ余分なDLLを置かせない
  ことを優先した。
- **出力の上限をシリアライザの例外でなく本文のバイト数で判定する**: `MaxJsonLength` の超過は
  循環参照と同じ例外型で返り、メッセージも実行環境の言語に翻訳されるため区別できないことを実測した。
  例外で判定すると、-32603 とすべき失敗まで -32005 へ落ちる。
