# 計画書の規約

実装計画書へ書かないものと、**その修正を認める場合の閉じた一覧**、**不適合をレビューでどう扱うか**の
正本。

対象は実装計画書——実装の着手前に手順を確定し、実装が済めば削除される一時ドキュメント——とする。
進捗・引き継ぎを記録する文書は対象外。

計画書へ足した記述は、レビューを一度余計に掛けたうえで捨てることになる。**書くほど工数が増え、
残る成果は増えない。**

## 1. 正本に属する設計を書かない

**確定した設計——設計値・規則・表・手順——を計画書へ書かない。** 決まった時点で正本へ直接書く
(その正本がまだ無ければ作る)。

## 2. 書いてよい記述

計画書は、次の一手を設計判断なしに着手できる状態にするための文書とする。置いてよいのは、
**その計画で何を実装するかの一文・着手順とステップの区切り・各ステップの完了条件(テストの方針を
含む)・前提とその裏取り・未検証として残る事項・仕様書とコードの食い違いとその処置**である。それ以外は
**過剰**とし、置かない。判定の母集団は、差分が計画書へ追加・変更する記述の全件とする。過剰の類型を
挙げる。

- **正本へ属する記述**([§1](#1-正本に属する設計を書かない)に当たるもの)。**移した記述の代わりに
  道しるべを残さない**——読み手は正本を読む。上の許可項目の中で正本を名指しすることは別である。
- **既にある記述の言い直し。** 同じ内容の要約・再掲・節をまたぐ重複、語句だけを整えた書き換え。
- **規則・検査の必要性を説く理由づけ。** 「これを課さないと〜してしまう」の類は、その規則を
  持つ正本へ書く。計画書には結論だけ置く。
- **着手の判断に要らない背景。** 経緯、検討して採らなかった案、案どうしの比較の記録。
- **実装すればコードが正本になる細部。** 内部の分割・命名・制御の流れなど。**正本を持つ設計値**
  ——フラグ名・終了コード・モジュール配置・エラーのコードなど、規約か仕様書が持つもの——は
  これに当たらない。確定させたうえで、その正本へ書く。
- **既に実装した範囲の記述。** 済んだ手順は計画書から消える側で、書き直す対象ではない。
- **この計画で実装しない範囲の記述。** 将来の構想、次の計画へ回す事柄。

## 3. 修正は原則禁止とし、認める形を限る

**計画書を作成したコミットより後の変更はすべて修正とし、原則として行わない。** 認めるのは次の
W1〜W5だけで、**この一覧は閉じている**。どれにも当てはまらない修正は、内容の当否を問わず却下する
——正確になること・詳しくなること・読みやすくなることは、消える文書では認める理由にならない。

- **W1 削る。** 記述の削除、および計画書そのものの削除。
- **W2 正本へ移す。** 計画書の記述を正本へ移し、計画書側は消す。**他の計画書がその記述を名指しして
  いたら、移送先の正本への名指しへ付け替えるところまでを含む。**
- **W3 前提と裏取りを直す。** 未確定の設計判断(推奨・選択肢・「実装時に判断」が残っている)を
  確定させる修正と、前提の裏取りを直す修正——未検証のまま残っていた前提を裏取りする、観測が誤って
  いたと分かった前提を書き改める。
- **W4 着手を妨げる誤りを直す。** **これから着手する手順**が誤っていて、直さないと着手できない
  場合に限る。実装済みの範囲との食い違いは、そろえるのではなくW1で消す。
- **W5 ステップの構成を変える。** 要件・設計が変わり、ステップの追加・削除・差し替え・順序変更が
  要る場合。**増やしてよいのはステップの見出しと完了条件の行だけ**で、変わった設計の中身は正本へ
  書く(W2)。

**W1・W2は計画書が純減する。W3〜W5で増やしてよいのは、着手に要る最小限の行だけである。**
どのWに当たるかは修正ごとに言えなければならず、言えないものは却下する。判定は修正の動機ではなく
差分で行い、レビュー指摘への対応としてなされた修正も同じく判定する。

## 4. 不適合の扱い

[§2](#2-書いてよい記述)に反する記述、または[§3](#3-修正は原則禁止とし認める形を限る)のW1〜W5の
どれにも当たらない修正が差分にあれば、不適合とし、レビューの指摘対象とする(収束を妨げる)。
解消は**元へ戻す**か**削除**か**正本への移送**のいずれかで、計画書の中で書き足しても書き直しても
解消しない。

逆に、**解消が計画書への書き足しになる指摘は、W3・W4・W5に当たる場合だけ受け入れる。** それ以外は
反証するか、正本の側の修正として立て直す。
