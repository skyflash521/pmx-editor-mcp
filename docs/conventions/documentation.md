# ドキュメント規約

**いまの実装がどう振る舞うかは、コードとテストで決まる。** ドキュメントへ書くのは、そこから
読み取れない範囲に限る。食い違っているとき、正しいのは次の側である。

- **[仕様書の中身](#仕様書の中身)**——外部で形が決まっているデータ構造の仕様と、製品の要求——は
  **ドキュメント**。
- **生成の一次入力**は **`catalog/` に置いたもの**。
- **いまの実装がどう振る舞うかの記述**は **コードとテスト**。

## 仕様書の中身

仕様書として書くのは、次の2つに当たるドキュメントだけとする。

- **外部で形が決まっているデータ構造の仕様。** ファイルフォーマットのように、形を決めたのが
  こちら側ではない仕様。
- **製品の要求。** 何を成し遂げるかと、何を目標にしないかと、**どこまでを保証するか**。自動では
  確かめられない範囲も、保証の切れ目としてここへ書く。**どれを先に出すかの順序は書かず**、
  一時のドキュメントへ書く。

**この2つに当たらない記述は仕様書へ書かない。** 外部のMCPクライアントへ見せるツールの形も、
プロセス間で交わすメッセージの形も、仕様書へ書かない。

## データと同梱ドキュメント

次の2つは仕様書ではないので、仕様書の場所へは置かない。

- **検査と生成が読むデータ。** SDKの能力台帳と機械可読の定義群がこれに当たる。外部の観測から
  決まる値と、生成と照合の一次入力になる定義の両方を含む。**置くのは値と定義だけ**とし、値の
  意味づけ・導出の規則・突き合わせの規則はコードとテストへ書く。
- **配布パッケージへ同梱するドキュメント。** 製品の成果物であって、この製品の作り方を述べる
  ドキュメントではない。

## ドキュメントの場所

| 内容 | 場所 |
|---|---|
| 検査と生成が読む値と定義 | `catalog/` |
| 外部で形が決まっているデータ構造の仕様 | `docs/specs/` |
| 製品の要求 | `docs/conventions/requirements.md` |
| 作業の取り決め | `docs/conventions/` |
| 配布パッケージへ同梱するドキュメント | `docs/package/` |

- **一次入力は、コードで表せる形であってもコードへ書かない。**
- **`catalog/` へ置くのは値と定義に限る。**
- **`docs/conventions/` へ置くのは、作業の取り決めと製品の要求に限る。** 製品がどう振る舞うかは、
  作業の取り決めへ書かない。
- **規約が定めるのは正しい状態で、判定の順序でも場合分けの網羅でもない。** 手順そのものが主題の
  規約はこの限りでない。

## 仕様書ではなくテストと定義へ書く

- 振る舞いは仕様書ではなく、**それが破れたら落ちるテストか検査**へ書く。両方にあるとき、
  正しいのは検査の側とする。**[仕様書の中身](#仕様書の中身)はこの限りでない**——製品の要求は文が
  正しく、検査を変えても要求は変わらない。要求が変わるのは、文が変わったときだけである。
- 値の一覧・対応表・命名の規則は、**コードか、検査が読む定義**として書く。

## コードコメント

- **コメントは仕様書ではない。** 振る舞い・規則・値の一覧・対応表をコメントで説明し直さず、
  コードとテストへ書く。
- **仕様書へ書けない記述の逃げ場にコメントを使わない。**

## 同じ記述を2か所に書かない

- コードかテストが表している記述と同じ意味の文を、ドキュメントへ書かない。
  **[仕様書の中身](#仕様書の中身)と `README.md` はこの限りでない**——`README.md` は、前提と
  手順に要る値をコードから引いて書く。
