# リリース手順

配布パッケージを GitHub Release として出すまでの手順を定める。初回も2回目以降も同じ手順に従う。

## 原則

- [バージョンを決める](#1-バージョンを決める)から[公開前の検証](#3-公開前の検証)までは develop で
  行い、まとまりごとにコミットする。
- **main へのマージ、タグの作成と push、Release の作成は、それぞれ明示の指示を受けてから行う。**

## 1. バージョンを決める

前のリリースのタグから develop の最新のコミットまでの変更を見て、上げる桁を[バージョン付け](versioning.md)に
従って決め、[Directory.Build.props](../../Directory.Build.props) の `Version` を書き換える。
初回は書き換えず、いまの値でリリースする。

## 2. 変更履歴を書く

リポジトリ直下の `CHANGELOG.md` の先頭へ、そのバージョンの節を足す。初回はファイルを作り、節の本文を
「初回リリース。」の1行にする。あわせて [README.md](../../README.md) の冒頭の、文書の場所を並べた表へ
`CHANGELOG.md` の行を足す。

形は [changelog.ps1](../../scripts/changelog.ps1) が確かめる。

書くのは、エンドユーザーから見える変更だけである。

| 区分 | 書く変更 |
|---|---|
| 互換性の無い変更 | [互換性の無い変更](versioning.md#互換を保つ範囲)。0.x で PATCH・MINOR に入れたものもここへ書く |
| 追加 | 新しいツール・引数・機能 |
| 変更 | ツールの改名・削除、引数・応答の形の変更、そのほかの挙動の変更 |
| 修正 | エンドユーザーから見える不具合の修正 |

- 当たる変更の無い区分は置かない。見える変更が1つも無いリリースは、区分を置かずに「内部改善のみ。」と
  書く。
- 1つの変更を1行で書く。何がどう変わり、エンドユーザーに何が起きるかを書く。
- コミットのハッシュ・内部の型名・行番号を書かない。
- 日付は節を書き上げた日にする。
- 出したリリースの節は、後から書き換えない。

## 3. 公開前の検証

次をすべて通す。

1. `pwsh -File scripts/verify.ps1 -All`
2. `pwsh -File scripts/verify-live.ps1 -All`
3. 配布パッケージから導入した状態の検査。[インストール指示書](../package/INSTALL.md)のとおりの
   新規導入・更新・アンインストールと、受入シナリオ1〜9がすべて合格すること。

## 4. main へ入れる

develop から main への PR を作り、PR の検査が合格したことを確かめる。
マージの指示を受けたらマージする。

## 5. タグを打つ

main のマージコミットへ `git tag -a` でタグを打ち、そのタグだけを push する。

```
git tag -a v<バージョン> -m "pmx-editor-mcp v<バージョン>" <マージコミット>
git push origin v<バージョン>
```

## 6. Release を作る

タグが指すコミットを新しい作業ツリーへ取り出し、リポジトリ直下の `local.props` をその作業ツリーへ
写してから走らせる。

```
pwsh -File scripts/release.ps1
```

失敗したら、原因を直してから同じタグのまま走らせ直す。タグの指すコミットを直さないと通らない
ときは、そのタグを消したり打ち直したりせず、PATCH を上げて[1](#1-バージョンを決める)からやり直す。
