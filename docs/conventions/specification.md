# 仕様書の規約

仕様書へ**書いてよい記述の閉じた一覧**、**書かない記述**、**どちらかを書く時点で決める判定**、
**不適合をレビューでどう扱うか**の正本。

対象は [docs/specs/](../specs/) の文書と、そこに置く機械可読ファイル(`.json`)の両方とする。
**検査が直接読む入力であることは、そこへ実装の詳細を置いてよい理由にならない。**

例外は**検査の期待値**——コード、または検査が読む一次入力(SDKの署名一覧など)から導出した値と
突き合わせ、食い違いを検出するために置く値——で、これは正本ではなく照合の相手なので対象外とする。
**期待値と称するには、突き合わせる検査が、変更を確定させる前に必ず走る検査として登録されて
いなければならない。** 走らない照合を根拠に置いた値は、期待値ではなくただの写しである。

## 1. コードが本体である

**実装の詳細の正本はコードであって、仕様書ではない。** 仕様書が正本を持つのは、到達状態の仕様・
外部契約・そこで課す制約である。この分担を越えて、コードの内側を仕様書へ書き写さない。

**実装の詳細を、コードと仕様書の二か所に置かない。** 二重に持てば、片方だけが変わって残りが嘘に
なる。嘘になったことは誰も検知しないので、読み手はどちらが正しいか判断できなくなる。

## 2. 書いてよいのは、コードで書けない要求仕様だけ

置いてよいのは次だけとし、**この一覧は閉じている**。いずれも**概念**——満たすべきこと・約束・制約
——であって、満たし方ではない。

- **要求と目的。** 何を満たさなければならないか。
- **外部契約。** 外から観測できる約束——公開する名前、引数と応答の**意味**、エラーの区分、
  状態の不変条件・前後条件、互換性の約束。**値そのものが契約であるもの**(識別子・エラーコード・
  単位・境界値・上限)はここに含む。
- **制約と前提。** 依存する外部(SDK・エディタ・プロトコル)の性質、実測で裏取りした事実、
  守らなければならない上限。
- **採った設計の理由。** なぜその契約・制約にしたのか。結論を支える範囲に限り、**検討の経緯や
  採らなかった案の比較は含まない**。
- **受入条件。** 満たされたことを何によって確かめるか。
- **対象範囲の宣言と、正本の委譲。** その文書が何を定めるか、および別の正本が持つ事柄はどれか。
  **どこが正本かを一度述べるまで**とし、移した内容の要約や道しるべを添えない。

## 3. 書かない記述(実装の詳細)

- **アルゴリズムと処理手順。** 計算・探索・照合の順序、分岐や再試行の流れ、走査の仕方。
- **内部構造。** クラス・メソッド・ファイル・モジュールの名前と分割、呼び出し関係、依存の向き。
- **内部のデータ構造。** 内部で保持する型・フィールド・保持の仕方(外から観測できるものは外部契約
  であり、これに当たらない)。
- **コードを読めば分かる説明。** 実装の要約・言い換え、コード片の転記、処理の追跡。
- **速さの出し方。** 上限や応答性の**要求**は制約として書き、それをどう実現するかは書かない。
- **検査の実装。** 検査が満たすべき条件は受入条件として書き、スクリプトの中身は書かない。

## 4. 判定は書く時点で当てる

**仕様書へ実装の詳細を書かせない。** 書いたものを後で消す規約ではなく、書く前に落とす規約とする。
次のどちらかに当たれば実装の詳細であり、**書かない**。

- **満たし方が一通りに決まる記述。** その記述どおりに作れば実装がその写しになるもの——手順・構造・
  呼び出しの順序をそのまま述べたもの——は、要求ではなく実装の指示である。**要求仕様は、複数の
  実装が満たせる形で書ける。** 書けないなら、それは要求ではない。**値そのものが契約であるものは
  この判定の対象外**とする——値を1つに決めること自体が要求だからである。
- **外から見える約束を変えずにコードの内側だけを変えたとき、直す必要がある記述。** アルゴリズムの
  差し替え・内部の名前替え・分割の変更で古くなるなら、それはコードの写しである。

**コードがまだ無いことは、この判定を変えない。** 実装より先に書けば要求仕様になる、ということは
ない——先に書いた記述も、上の2つに当てて落とす。

判定の母集団は、差分が仕様書へ追加・変更する記述の全件とする。動機ではなく差分で行い、レビュー指摘への
対応としてなされた記述も同じく判定する。**正確であること・詳しいこと・親切であることは、書いてよい
理由にならない。**

## 5. 不適合の扱い

**この規約に反する記述が差分にあれば**、不適合とし、レビューの指摘対象とする(収束を妨げる)。

**仕様書に手を触れない差分でも二重化は成立する。** 実装の差分が仕様書側の既存の記述を写しに変えた
場合も不適合とし、実装のレビューはそこまでを見る。対象は**実装の詳細に当たる事実に限る**——値そのものが
契約であるものは、コードが同じ値を持っても写しにならない。見る範囲は**その差分が追加・変更した
コードが持つことになった事実と対応する記述**だけで、仕様書の全体を洗い直さない。**これは取りこぼしの
始末であって、先に書いてよい根拠ではない。**

解消は**削除する**か、**要求の言葉へ書き直す**(手順の記述→満たすべき条件の記述)かのいずれかで、
説明を足しても注記を添えても解消しない。コードにしか無かった事実なら、仕様書へ移さずコードに残す。

この規約の適用範囲は**差分**とする(写しに変わった既存の記述も、その差分が変えたものなので範囲内で
ある)。それ以外の、既存の仕様書に残る不適合の一括除去は、指示があったときだけ行う。
